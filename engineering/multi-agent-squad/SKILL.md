你正在把一个**大目标**变成一支**多 agent 团队**。你自己是 **Lead（领航员）**——这是唯一常驻的角色。

**核心认知**：多 agent 不是"更多算力"，而是**更多独立上下文**。它买到的是**独立性**（审查者不被实现理由污染）和**并行**（互不阻塞的活同时干）——代价是**共享内存没了**。所以整套纪律都围绕一件事：**怎么在没有共享内存的前提下协作**。

> **本技能是"执行版"（纪律 + 模板 + 判据）**。
> **完整走查版**（含**商业侧角色表** Validator/Pricer/Biller/Grower、DSH 机制的逐项映射与陷阱、
> 交接协议细节、落地路线上的每一环验证方法）在：
> `<库根>\多Agent团队协作编排指南.md`
>
> **什么时候该去读它**：① 你要建**商业项目**的团队（本技能只到工程角色）；
> ② 你不确定某个 DSH 机制该怎么用；③ 你要按"一小环一小环"从 0 把团队搭起来。

## 一、三条铁律（违反任何一条，团队立刻退化成"一群各说各话的 agent"）

### 铁律 A：文件是唯一的共享内存

子 agent **看不见你的对话，也看不见彼此**。没写进文件的，等于**没发生**。

> **禁止**：靠"我记得上一轮说过 X"来协作；靠"我在 prompt 里跟它提过"来当交付物。
> **必须**：每条要跨 agent 传递的信息都落**文件**，并给**稳定路径**。

交接文件里必须有**推理**，不只是结论——结论可以猜，推理不能。

### 铁律 B：一个 agent 一个窗口，阶段边界处换人

决策树（**每个阶段结束时都问一次**）：

| 情况 | 动作 |
|---|---|
| 下一阶段需要当前阶段作**一手来源** | **留在同一个 agent**（别交接） |
| 当前上下文对下一步**完全无关** | **回收**，开新 agent |
| 要换目录 / 换平台 / 交给别人 | **写文件**交接，开新 agent |
| 任务能**离线跑**、范围紧 | **派子 agent**（后台） |
| 以上都不是（相关、同环境、你要盯着） | **压缩后继续** |

**最常犯的错**：让一个 agent 从需求一路干到审查。到审查那一步它**已经无法客观**——它记得自己为什么那么写，而那正是审查要排除的东西。

**上下文预算**：单个窗口的"智能区"是**上下文窗口的一部分**（经验值 ≈ 15%）。超过就**无声降智**。别硬撑，在阶段边界换窗口。

> ⚠️ **别把这个比例当固定数字**：它随模型变。**先查当前模型的 `contextWindow`**（DSH 在 `~/.dsh/settings.yaml` 里配），
> 再按 ≈15% 估算。例：1M 窗口 → 约 150k；200k 窗口 → 约 30k。
> **写死一个数字会在换模型时变成错的**，而且会让人在只用掉 15% 容量时就白白换窗口。

### 铁律 C：审查者与实现者必须不同窗口

**同一个 agent 不能既实现又审查自己。**

多 agent 最大的价值就是这条：**独立性是买来的，不是省出来的**。如果 Reviewer 每次都只会说"看起来不错"，说明它看到的是同一批信息，**独立性已经失效**——去检查它是不是被实现者的理由污染了。

## 二、两个机制：硬结构闸门 + 中央状态

这两个机制解决同一个病：**"对齐"这件事原本只存在于聊天记录里，无法被验证，也无法被下一个窗口读到。**

### 机制 1：硬结构闸门（**没过不许开工**）

**规矩**：进入 Builder 阶段之前，`CONTEXT.md` 必须包含**三张图 + 接口契约**。

| 必须有 | 它逼你想清什么 | 会被机器检查什么 |
|---|---|---|
| **实体关系图**（Mermaid `erDiagram`） | 有哪些实体、怎么连 | 有实体**没有任何关系**连到 → 拦下（孤岛实体 = 归属没想清） |
| **状态流转图**（Mermaid `stateDiagram-v2`） | 核心对象的状态与迁移 | 有**死状态**（进了出不来且不是终态）→ 拦下 |
| **接口契约** | 谁调谁、入参出参、**失败怎么办** | 有端点**没写错误处理** → 拦下 |
| **范围边界** | 不做什么 | 缺失 → 拦下 |

**执行**：

```powershell
node scripts/verify-structure.mjs -Project .     # 退出码 1 = 停下，回去补图
```

**模板**：本技能目录下的 [`CONTEXT-TEMPLATE.md`](CONTEXT-TEMPLATE.md)（含三张图的可抄范例与画图规矩）。

**首次真实跑通后的四条经验**（2026-09-12，在一个 640 行的真实项目上跑完整流程记下来的）：

1. **校验器按小标题切"端点块"** → 契约段**开头不要写"本节共 N 个端点"这类汇总**，
   否则那段铺垫会被当成一个"没写错误处理的端点"。汇总写在别处（比如范围与口径一节）。
2. **错误行加粗也可以**（`| **错误** |` 与 `| 错误 |` 等价）。
   —— 这条以前是坑：模板印的是加粗版、校验器只认不加粗版，**照模板抄必然卡住**，已修。
3. **不是每个端点都有错误分支**（静态资源、固定 HTML 页）。别为了过闸门编一行假错误——
   如实写"无错误分支（静态资源）"即可，**校验看的是你有没有回答这个问题，不是你编得像不像**。
4. **接口不止 HTTP**：WebSocket / 事件 / 消息协议同样是契约。
   把它们的**消息表**放进对应端点的条目里（上行/下行各有哪些类型），别只写"WS /ws"。

> **为什么值得为它停下**：这三张图逼你在**写代码之前**发现"这个状态没有出口""这个实体没人引用"
> "这个端点没有错误处理"——**这三样都是 Builder 阶段最贵的返工源**。
> 聊天记录里的"我们说好了"通不过校验器；**图能。**
>
> **实测它抓到了什么**：一个 agent 靠"每个状态必须有出口"这条判据，回头核代码时才发现
> 平票 PK 其实有两条出口（重投、以及重投仍平票就无人放逐）——**它是活的，而在只凭印象画的图里它是个死状态**。
> 另一条"孤岛实体"判据让它把原本打算省略的两个实体画了出来，而**信息隔离红线恰好就落在那两个实体上**。

### 机制 2：中央状态（**单一事实源**）

> **两者是独立的两件事，别混**：
> **硬结构闸门（机制 1）是开工前提** —— 任何项目、任何规模，都要先过，**没有例外**。
> **中央状态（机制 2）是进度账本** —— 适合**多 agent / 多阶段 / 跨会话**的项目；
> **单 agent 单会话就把一件事做完**的场景可以先不建（建了也是空转）。
> 判断标准很简单：**需要回答"我现在走到哪一关"时才建它**。建了就只由 Lead 写（见下）。

**问题**：状态原本散在 `.scratch/*/issues/*.md` 的 `Status:` 行里，靠人扫一遍才能拼出
"现在在哪一关"——**又慢又费 token，且容易看错**。

**做法**：`.scratch/state.json` 一份文件说清四件事：**在哪一关**（`phase`）、**关内哪一步**（`node`）、
**硬结构产物齐没齐**（`artifacts`）、**闸门过没过**（`gates`）。

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/state.ps1 show -Project .          # 读（任何 agent 都能读）
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/state.ps1 validate -Project .      # 校验：阶段/产物/闸门是否自洽
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/state.ps1 phase -Value g3-build    # 切阶段（**仅 Lead**）
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/state.ps1 artifact -Name er_diagram -Value true
```

**权限纪律（硬）**：

> **只有 Lead 能写 `state.json`。** Builder / Reviewer / Researcher 等**一律只读**。
> 写入只走 `state.ps1`（唯一入口），且每次改动都记 `updated_by=lead` 与 `history`，**可事后审计**。
> 理由：多个 agent 同时写一个文件 = 又一个并发踩踏点（正是要避免的老问题）。

**它自带两条闸门校验**（`state.ps1 validate` 会拦）：
- 处于 `g3-build` 及之后，但三图/契约没齐 → **报错**
- `tier=commercial` 但没先过 `tech_redline` → **报错**（两级闸门的联动，见下节）

## 三、团队角色表

**关键设计**：除 Lead 外，**所有角色都不常驻**。它们是被需要时实例化的窗口，用完回收。

| 角色 | 加载技能 | 输入（读文件） | 产出（写文件） | 常驻？ |
|---|---|---|---|---|
| **Lead** 领航员 | 本技能 + `grilling` + `domain-modeling` + `to-spec` + `to-tickets` | 人的模糊想法 | `CONTEXT.md`、`docs/adr/*`、`spec.md`、工单、**`state.json`** | ✅ 唯一常驻，**必须与人实时交互** |
| **Wayfinder** 探路人 | `wayfinder` + `research` | 一大团雾 | `map.md` + 决策工单 + **决策**（不是交付物） | 雾散即退，**不写代码** |
| **Researcher** 研究员 | `research` | 一个具体问题 | 带引用的 markdown | 纯 AFK，**可并行多个** |
| **Architect** 架构师 | `codebase-design` + `improve-codebase-architecture` | 现有代码 + 术语表 | 接口设计、加深机会报告、ADR | 小团队可并入 Lead |
| **Builder** 实现者 | `implement` + `tdd` | **一张工单** | 代码 + 测试 + commit | **一张工单一个窗口** |
| **Reviewer** 审查者 | `code-review` | diff + 规格 + 规范 | 双轴报告 | **两个并行子 agent** |
| **Hardener** 加固者 | `production-readiness` | 可运行的系统 | 加固清单逐项闭环 | 上线前单独入场 |
| **Debugger** 诊断者 | `diagnosing-bugs` | 一个症状 | 反馈回路脚本 + 回归测试 + 根因 | 有 bug 才入场 |
| **Shipper** 发布者 | `launch-and-ops` | 冻结的构建产物 | 上线 + 回滚预案 + 运行手册 | 上线时入场 |
| **Triage** 分诊员 | `triage` | **别人提的** issue/PR | 分诊标签 + agent 简报 | 有外部输入才入场 |
| **Wizard** 向导作者 | `wizard` | 只有人能做的流程 | 交互式脚本 | 按需 |

> 商业能力相关的角色（验证、技术选型、收款、增长）见 `commercial-squad`。

## 四、把角色实例化成子 agent（本节是全部诀窍）

### 3.1 三段式 prompt 模板

```
【身份】你是 <角色名>。你只做 <职责边界>。越界的事停下来报 lead，不要自己决定。

【技能】先读 <SKILL.md 绝对路径>，严格按它执行。
        它定义的阶段、完成标准、反模式都是硬约束。
        <如果还有第二份技能，把路径也列上>

【输入/产出】
  输入：<文件路径列表——这是你唯一的信息来源，不要去猜别的，不要读别的>
  产出：<必须写出的文件路径> + <完成标准>
```

### 3.2 为什么必须**显式点名 SKILL.md 路径**

`model-invoked` 技能靠 description 自动触发，但**跨 agent 时不要指望它**——子 agent 有自己的系统提示和独立上下文，它不知道你这边加载了什么。

> **在 prompt 里写死"先读 X/SKILL.md"，是唯一可靠的技能传递方式。**

### 3.3 实例：Builder 的 prompt

```
【身份】你是 Builder。只负责实现工单 03，不修改其他文件，不做架构决策。
    工单描述不清楚就停下来报 lead，不要臆断。

【技能】读 <库根>\engineering\implement\SKILL.md，
    施工中读 <库根>\engineering\tdd\SKILL.md。
    遵守：红在绿前、一次一个垂直切片、只在预先约定的接缝上测试。
    重构不属于红绿循环，留给评审。

【输入】.scratch/<feature>/issues/03-<slug>.md（唯一需求来源）
       CONTEXT.md（术语，命名必须与它一致）

【产出】代码 + 测试 + commit。
    完成后把「改了哪些文件 / 跑了哪些命令 / 结果」写进该工单的 ## Comments。
    完成标准：工单里每条验收标准都能勾上，且测试套件全绿。
```

### 3.4 实例：Reviewer 的 prompt（注意"防污染"写法）

```
【身份】你是 Reviewer，只审查，不改代码。你没有参与实现，也不要为它辩护。

【技能】读 <库根>\engineering\code-review\SKILL.md。
    沿两条轴，分开汇报，不合并、不跨轴挑冠军：
      标准轴 = 仓库成文规范 + Fowler 坏味道基线（那 12 条全文照搬）
      规格轴 = 工单/规格是否被忠实实现

【输入】git diff <固定点>...HEAD；工单文件路径
【产出】两份报告（各 400 字内）+ 每轴最严重问题
```

### 3.5 实例：Hardener 的 prompt

```
【身份】你是 Hardener。任务是让这个系统**能上线**，不是让它更好看。
    只做 production-readiness 清单里的事，不加新功能。

【技能】读 <库根>\engineering\production-readiness\SKILL.md

【输入】<项目根>；.env.example；<部署方式说明>
【产出】逐项闭环报告：每一项 = 现状证据 / 改动 / 验证方式 / 未解决风险
    没验证过的不许标"已完成"。
```

## 五、主流水线（泳道图）

```
            ┌────────────────────────────────────────────┐
 [人的想法] →│ ① Align 对齐                                │
            │   Lead 跑 grilling（+ domain-modeling）      │
            │   产出：CONTEXT.md 术语、ADR                 │
            └──────────────────┬─────────────────────────┘
                               │ 交接：同一窗口继续（下一阶段要它作一手来源）
            ┌──────────────────▼─────────────────────────┐
            │ ② Spec & Tickets 定规格拆工单               │
            │   Lead: to-spec → to-tickets                │
            │   产出：spec.md + 带阻塞边的工单             │
            └──────────────────┬─────────────────────────┘
                               │ 交接：窗口在这里可以回收（决策已沉淀进文件）
    ┌──────────────────────────▼─────────────────────────┐
    │ ⛔ 硬结构闸门（**没过不许开工**）                    │
    │   node scripts/verify-structure.mjs -Project .      │
    │   要求 CONTEXT.md 含：实体关系图 + 状态流转图 +      │
    │   接口契约 + 范围边界。退出码 1 = 停下，回去补图。   │
    └──────────────────────────┬─────────────────────────┘
    ┌──────────────────────────▼─────────────────────────┐
    │ ③ Build 施工（按工单前沿，可并行）                  │
    │   每张工单 → 一个新 Builder 窗口                    │
    │   内部：implement → tdd（一次一个红绿垂直切片）      │
    └──────────────────────────┬─────────────────────────┘
                               │ 交接：写文件（改了哪些、跑了什么）
    ┌──────────────────────────▼─────────────────────────┐
    │ ④ Review 审查（必须独立）                          │
    │   两个并行 Reviewer：标准轴 / 规格轴                │
    │   产出：双轴报告；不合并、不重排                    │
    └──────────────────────────┬─────────────────────────┘
                               │ 发现问题 → 回 ③（**新** Builder 窗口）
                               │ 通过 → 合并
    ┌──────────────────────────▼─────────────────────────┐
    │ ⑤ Harden 加固 → ⑥ Ship 发布                        │
    │   Hardener 逐项闭环 → Shipper 上线 + 回滚预案        │
    └────────────────────────────────────────────────────┘
```

**旁路**（不走主干）：

- **Bug 来了** → 直接进 `Debugger`；它修完发现"根本没有好接缝"，结论转 `Architect`。
- **说不清的设计问题** → `prototype` 做一次性原型，答案折回 ①。
- **需要外部事实** → `Researcher` 并行跑，结论带进 ①。
- **一大团雾** → 先 `wayfinder` 出决策地图，再在 ② 收敛。

## 六、通信协议（不要"聊天"，要发结构化消息）

成员之间只发这六类消息。**裸聊（"你看下这个"）在多 agent 下等于没发生。**

| 消息类型 | 用途 | 硬要求 |
|---|---|---|
| **HANDOFF** | 交接工作 | 必须是**文件路径**，不是对话摘要 |
| **QUESTION** | 要别人知道的事实 | 指明问题、截止、期望产出 |
| **BLOCKED** | 卡住了 | 卡在哪 / 试过什么 / 需要谁做什么 |
| **REVIEW** | 请求审查 | 附 diff 固定点 + 规格路径 |
| **DONE** | 完成 | 附产出文件路径 + 验收标准**逐条**核对 |
| **DECISION** | 记一个不可逆决策 | 写进 `docs/adr/`，不能只留在对话里 |

### 在你的 harness 里怎么发

| 目的 | 机制 | 注意 |
|---|---|---|
| 派一个**离线、范围紧**的活 | 后台子 agent | 默认后台跑，**不要阻塞等它** |
| 需要**结果才能继续** | 前台子 agent | 只在下一步确实依赖它时用 |
| **批量、多阶段**扇出（审计 N 个文件 / 迁移） | 工作流脚本 | 编排写成脚本，不要一轮轮手工派 |
| 给**已存在**的 agent 追加活 | 发消息（同一会话续轮） | 它**当前轮结束前不会被打断**，不能改已在做的事 |
| 需要**继承当前上下文**的子 agent | 派生型子 agent | 子 agent 会拿到本会话已完成的轮次 |
| 停掉跑偏的 agent | 中断 | 只停当前轮；它自己派的下级还在跑 |

**并行纪律**：互不依赖的活**在一条消息里一起派**，然后**继续干自己的活**——不要派完就空等。

## 七、落地路线：一小环一小环搭（**强烈建议，别跳**）

对应工作区「方法论」表的 `tdd` 纪律：**一次一个垂直切片**。**一上来上 7 个 agent 必失败。**

### 第 0 环：单 agent + 文件纪律
只做一件事：把 `CONTEXT.md` 建起来，每次任务让 agent 读它。
验证：命名开始一致、同一件事不再反复解释。
**这环不过，后面全白搭**——共享语言是多 agent 的公共接口。

### 第 1 环：2 个 agent（Builder + Reviewer）
只加审查者。做一次小改动：Builder 实现 → **新窗口** Reviewer 审 → 回改。
验证：Reviewer 是否**真的**发现了 Builder 没注意的问题。总是"看起来不错"= 独立性失效。

### 第 2 环：加 Lead（3 个 agent）
加"逼问 + 拆工单"。做一次中等功能。
验证：Builder 能否**只看工单文件**就干完活。**老要回头问 = 工单不自足**，回去修工单，不是怪 Builder。

### 第 3 环：加并行
同一前沿上多张**互不阻塞**的工单，**同时**派多个 Builder。
验证：文件不冲突、阻塞边真的起作用。**这步要非常小心——见坑位 1。**

### 第 4 环：按需加角色
有难 bug → `Debugger`；要大范围架构改进 → `Architect`；有外部 issue → `Triage`；
要上线 → `Hardener` + `Shipper`；只有人能做的步骤 → `Wizard`；一大团雾 → `Wayfinder`。

### 第 5 环：反馈闭环
定期跑 `improve-codebase-architecture` 的体检，把结果变成下一轮工作。
作者定位很准：**是体检，不是抢救。**

## 八、坑位清单（多 agent 特供）

1. **两个 agent 同时改同一个文件。**
   纸面上靠 `to-tickets` 的**阻塞边**杜绝；运行时靠工单里"哪些文件归你"当护栏。
   冲突了**别硬合**——用 `resolving-merge-conflicts` 逐块按**两边各自的一手来源**追溯意图。

2. **审查者被污染。**
   让实现者"顺便审一下"是最常见的自欺。**审查必须新窗口、新上下文**，最好两轴分开跑。

3. **交接靠对话摘要。**
   `/compact` 和"你总结一下给下一个 agent"都会**丢 why**——那是**有损的、单向的**。
   交接要落**文件**，且文件里要有**推理**。

4. **工单不自足。**
   衡量标准极明确：**Builder 只看工单能不能干完**。干不完是工单的缺陷。
   自查（`AGENT-BRIEF.md` 原则）：行为式描述 / 不引文件路径行号 / 有可独立验证的验收标准 / 有明确范围外。

5. **让 agent 替人做决策。**
   `grilling` 的铁规：**事实是 agent 的活，决策是人的**。
   别让"系统设计者"顺手替你定了产品方向——多 agent 下这条更危险，因为决策速度快到人跟不上。

6. **一股脑派一堆 agent 并行。**
   垂直切片是"一次一个"的，多 agent 也是。**先串行跑通，再逐段并行**。

7. **无视上下文预算。**
   每个窗口的智能区是上下文窗口的 ≈15%。**在阶段边界换窗口**，别硬撑——降智是无声的。

8. **指望技能自动触发。**
   跨 agent 时**在 prompt 里显式点名 SKILL.md 路径**，最可靠。

9. **子 agent 在错误的方向上跑很久。**
   派活时就把**范围和完成标准**写死；范围紧的活才适合离线跑。
   跑偏了用中断停它，**但记住：它自己派的下级不会跟着停**。

10. **每个 agent 重复读同一批文件、重复查同一件事。**
    这是纯粹的浪费。**把结论沉淀成文件**（调研笔记、`CONTEXT.md`、ADR），让下一个 agent 读结论而不是重跑过程。

## 九、人工闸门（多 agent 放大了改动速度，所以闸门必须前置）

必须停下来等人确认的时刻：

1. **工单拆分完成时**——粒度、阻塞边要人确认。
2. **验收标准确认时**——Builder 说"做完了"之前，逐条对照工单 checklist。
3. **任何不可逆动作**——删数据、改 schema、发布、付款配置、对外接口变更。

> 对应工作区铁律"**改动必须经过用户确认**"。团队越大，这条越硬。
