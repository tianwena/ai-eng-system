一个模糊的想法来了——大到超出单个 agent 会话，而且裹在雾里：从这里通往**目的地**的路还看不见。寻路是**找到那条路**，不是向目的地猛冲。这个技能把路线绘制成仓库 issue 追踪器上一张**共享地图**，然后逐个处理它的**决策工单**——答案是一个**决策**、而非"要执行的构建切片"的那些问题——直到路线清晰。

目的地随每次工程而变，而**给它命名是绘图的第一个动作**——它塑造每一张工单。它可能是一份要交接并迭代的规格、一个在规划开始前必须锁定的决策，或者一处就地完成的变更（比如数据结构迁移）。地图与领域无关——工程工作、课程内容，任何符合这个形状的东西都行。

## 规划，不要执行

Wayfinder 默认是在**做规划**：每张工单解决一个决策，当路清晰时地图就完成了——在有人真的动手去做之前，没有什么还需要决策。那种"干脆直接干了"的冲动，通常正是"你已抵达地图边缘、该交接了"的信号。一次工程可以在它的 **Notes** 里覆盖这个默认（把执行也纳入地图本身），但除此之外，产出**决策，而不是交付物**。

## 用名字来指代

每张地图和每张工单都是一个 issue，所以它有一个**名字**——它的标题。在所有给人读的地方——叙述、地图的 Decisions-so-far——都用**名字**指代它，**绝不用**裸的 id、编号或 slug。一整墙的 `#42, #43, #44` 无法阅读；名字一眼就能看懂。id 和 URL 不会消失——名字**包裹**着它的链接——但它们是**嵌在名字里面**，绝不代替名字。

## 地图

地图是仓库 issue 追踪器上的**单个 issue**，打 `wayfinder:map` 标签——它是**规范产物**。它的工单是地图的**子 issue**。

地图是一个**索引**，不是仓库。它列出已做出的决策，并指向承载其细节的工单；一个决策**只存在于一个地方**——它的工单——所以地图从不重述它，只给要点 + 链接。

**地图、子工单、阻塞关系、前沿（frontier）查询在物理上住在哪里，是追踪器特有的。** issue 追踪器应该已经提供给你了——如果没有，先跑 `/setup-workspace-discipline`。查阅追踪器文档的 "Wayfinding operations" 小节，了解**本**仓库怎么表达它们。如果没有提供任何追踪器，默认用本地 markdown 追踪器。

### 地图正文

整张地图的低分辨率视图，每个会话加载一次。**开放中的工单不会列在这里**——它们是开放的子 issue，靠查询找到。

```markdown
## Destination

<走完这张地图是什么样子——这次工程要寻到的规格、决策或变更。一两行；每个会话在挑工单之前都要先按它定位。>

## Notes

<领域；每个会话都该参考的技能；这次工程的常设偏好>

## Decisions so far

<!-- 索引——每张已关闭工单一行：够判断相关性，然后点链接放大看工单里的细节 -->

- [<已关闭工单标题>](link) — <答案的一行要点>

## Not yet specified

<!-- 见"战争迷雾"：在范围内但还无法开票的雾；随前沿推进而毕业 -->

## Out of scope

<!-- 见"范围外"：已判定在目的地之外的工作；关闭，永不毕业 -->
```

### 工单

每张工单都是地图的**子 issue**；追踪器的 issue id 就是它的身份。它的正文是那个**问题**，尺寸以一个 100K token 的 agent 会话为准：

```markdown
## Question

<这张工单要解决的决策或调查>
```

每张工单带一个 `wayfinder:<type>` 标签——`research`、`prototype`、`grilling`、`task` 之一（见[工单类型](#工单类型)）。

一个会话**认领**工单的方式是把它分配给驱动地图的开发者，**而且要在任何工作之前先做**，这样并发的会话会跳过它。那个受理人**就是**认领：一张开放、未分配的工单就是未被认领的。

阻塞使用追踪器的**原生**依赖关系——这一点至关重要，因为它能在追踪器自己的 UI 里**可视化**地渲染出前沿，人不用打开地图就能看到哪些可以拿。只有缺乏原生阻塞的追踪器才回退到正文约定。当**每一张**阻塞它的工单都关闭时，这张工单就**解除阻塞**；**前沿**就是开放的、未阻塞的、未被认领的子工单——已知世界的边缘。

答案不是正文的一部分——它在解决时被记录（见[走过地图](#走过地图)）。解决工单期间产生的资产从 issue 链接过去，不要粘贴进去。

## 工单类型

每张工单要么是 **HITL**（human in the loop，人在回路里，**和**一个代表自己的人一起做），要么是 **AFK**（agent 独自驱动）。一张 HITL 工单只能通过那场实时交流来解决；agent 永远不能代替人那一侧（一个自问自答的逼问 agent 已经破坏了这个规则）。

- **Research（研究）**（AFK）：读文档、第三方 API，或本地资源（如知识库），以浮出一个决策正在等待的**事实**。由一个 `/research` **子 agent** 解决。当需要当前工作目录之外的知识时使用。
- **Prototype（原型）**（HITL）：通过做一个便宜、粗糙、具体的产物来供人反应，从而提高讨论的保真度——一个提纲、一个粗略草案、一个桩，或者通过 `/prototype` 技能做 UI/逻辑代码。把原型作为资产链接。当关键问题是"它该长什么样"或"它该怎么表现"时使用。
- **Grilling（逼问）**（HITL）：对话。**默认情况。** 总是调用 `/grilling` 和 `/domain-modeling` 技能。
- **Task（任务）**（HITL 或 AFK）：在**做出决策之前**必须先完成的手工工作——没有什么要决策、做原型或研究的，但在它完成之前讨论被卡住。注册一项服务以便评判它的 API、开通访问权限、搬数据以便看见它的形状。这是唯一**动手做**而不是决策的类型——它挣得位置的方式是**解除某个决策的阻塞**，不是交付目的地。agent 能独自驱动的就独自驱动（AFK）；否则给人一份精确的清单（HITL）。工作做完即解决；答案记录做了什么，以及后续工单依赖的任何事实（凭据位置、新 URL、行数）。

## 战争迷雾

地图是**故意**不完整的：看不见的东西就别画。在实际工单之外躺着**战争迷雾**——那些你能感觉到要来、却还无法钉死的决策与调查的朦胧视野，因为它们挂还在开放的问题上。解决一张工单会驱散它前方的雾，把现在变得可规格化的东西**毕业**成新工单——一张接一张，直到通往目的地的路清晰、不再剩任何工单。

地图的 **Not yet specified** 小节就是写下那片朦胧视野的地方：怀疑存在的问题、以后再回访的领域。它是**朝向**目的地的未知前沿——这里的一切都在范围内，只是还不够清晰到能开成工单。视野允许你写多松就多松、写多满就多满；它同时也是给协作者的指路牌，让人看出这次工程走向何方。

**是雾还是工单？** 判据是你**现在**能不能把问题陈述精确——**不是**你现在能不能回答它。

- **开成工单**：当问题已经足够锐利——即使它被阻塞、你现在还动不了。
- **留在 Not yet specified**：当你还不能把话说得那么锐利。不要预先把雾切成工单大小的碎块：它比工单更粗，等前沿到达时，一块雾可能毕业成好几张工单，也可能一张都不毕业。

**Not yet specified** 排除已经决定的东西（Decisions so far）、已经是实际工单的东西，以及范围外的东西（下一节）。

## 范围外

雾只会**朝着**目的地聚集。目的地固定了范围，所以在它之外的工作是**范围外**——它不是雾，也不属于 **Not yet specified**。它在地图上拥有自己的 **Out of scope** 小节：你有意识地判定在**这次**工程之外的工作。让它落到这里的是**范围**，不是清晰度。

范围外的工作永不毕业——前沿停在目的地——所以只有当目的地被重新画定时它才会回来，而且那时是一次全新的工程，不是续做。

判定某事范围外是一个**界定范围的动作**，不是路线上的一个步骤。当一张已存在的工单被发现在目的地之外时——绘图时错圈进来，或被某个解答暴露出来——**关闭它**（关闭的工单明确地不在前沿上），并在 **Out of scope** 小节留一行：要点 + 为什么范围外，链接到那张已关闭的工单。它**不**进 **Decisions so far**，那里记录的是实际走过的路线——范围边界不是路线上的一个步骤。

## 调用方式

两种模式。两种都一样：**每个会话绝不要解决超过一张工单**——研究类工单除外。

### 绘制地图

用户带着一个模糊的想法调用。

1. **给目的地命名。** 跑一场 `/grilling` 和 `/domain-modeling` 会话，钉死这张地图要寻到什么——规格、决策或变更。目的地固定范围，所以它**最先**被敲定。
2. **测绘前沿。** 再逼问一次，这次**广度优先**：在整个空间里扇开，而不是在任何一条线索上深挖，浮出开放的决策和现在就能采取的最初几步。**如果这次没有浮出任何雾**——通往目的地的路已经清楚，整段旅程小到一个会话就能装下——你不需要地图。停下来，问用户想怎么办。
3. **创建地图**（标签 `wayfinder:map`）：填好 Destination 和 Notes，Decisions-so-far 空着，把雾草拟进 **Not yet specified**。
4. **创建你现在能规格化的工单**，作为地图的子 issue——然后**第二遍**再接阻塞边（issue 需要先有 id 才能互相引用）。接线会把它们分成"前沿"和"被阻塞"；你暂时无法规格化的一切留在雾里——**Not yet specified** 小节。
5. **发射研究子 agent。** 对你刚创建的每张 `research` 工单，起一个 `/research` 子 agent 并行解决它，把发现捕获在一个一次性的 `research/<name>` 分支上，并从工单里留一条上下文指针。
6. 停——绘图是一个会话的工作；它不亲手解决任何东西。

### 走过地图

用户带着一张地图（URL 或编号）调用。工单是**可选**的——不给的话，**由你**挑下一个决策，而不是用户。

1. 加载**地图**——低分辨率视图，不是每张工单的正文。
2. 选工单。如果用户点名了一张，就用它。否则按顺序取第一张前沿工单。**认领它**：在做任何工作之前把它分配给自己。
3. 解决它——**按需放大**：按需取回任何相关或已关闭工单的完整正文；调用 `## Notes` 里点名的技能。有疑问就用 `/grilling` 和 `/domain-modeling`。
4. 记录解答：把答案作为一条**解答评论**发出，**关闭**该 issue，并**追加一条上下文指针**到地图的 Decisions-so-far。
5. 加入新浮出的工单（先创建再接线）；把答案已经变得可规格化的雾**毕业**——每块毕业的雾都从 **Not yet specified** 里清掉，让它的存在只剩新工单。如果答案揭示某张工单——这张或另一张——位于目的地之外，就**判定它范围外**，而不是在路线上解决它。如果该决策让地图的其他部分失效，更新或删除那些工单。

用户可能会并行跑多张已解除阻塞的工单，所以要预期其他会话在并发编辑追踪器。
