你在写**用户直接看到**的那一层。它的特点是：**错了会立刻被看见**，而且**回归最便宜**（改一行 CSS 就可能弄坏别的页面）。

**核心认知**：前端不是"把数据画出来"。前端是**状态归属**问题——AI 写前端最常见的失败，全都是"状态放错了地方"的各种变体。

---

## 一、四种"AI 写前端"的病（先认病，再谈纪律）

| 病 | 症状 | 根因 |
|---|---|---|
| **假后端** | 组件里写死 `const data = [...]`，看起来能跑 | 没人告诉它数据从哪来；它先让页面"好看" |
| **状态乱放** | 同一个数据在两三个地方各存一份，到处 `useEffect` 同步 | 没定**谁是唯一真相** |
| **每页一套样式** | 颜色/间距/圆角各写各的，硬编码 `#3b82f6`、`padding: 13px` | 没有设计令牌，或令牌没被强制使用 |
| **无休止重渲染** | 改个输入框卡一下；`useEffect` 循环 | 依赖数组写错 / 每次渲染新建对象 |

**这四种病的共同点**：**都能被机器或人一眼查出来**——所以下面每条纪律都配了"怎么验"。

## 二、状态归属：**先决定"谁是唯一真相"**

**写任何组件之前，先回答三个问题**：

```
1. 这份数据从哪来？（服务端 / URL / 用户输入 / 本地派生）
2. 它是【服务端状态】还是【客户端状态】？
3. 谁会改它？只有一个地方能改吗？
```

| 类型 | 例子 | 该放哪 | 纪律 |
|---|---|---|---|
| **服务端状态** | 订单列表、用户资料 | 查询层（React Query / SWR / 框架的 loader） | **不要复制到本地 state**——那是"两处真相"的起点 |
| **URL 状态** | 当前筛选、页码、选中的 tab | **URL（query params）** | 能被分享/刷新/前进后退，**别塞进组件 state** |
| **表单状态** | 输入中的值 | 表单库或组件本地 | 只在提交时"提升" |
| **派生状态** | 过滤后的列表、总价 | **算出来，不要存** | 存了就要同步，同步就会不一致 |
| **跨组件共享的 UI 状态** | 全局提示、主题 | 一个 store（**只有一个**） | 别一个页面一个 store |

### 硬规矩

1. **派生状态不许存。** `const total = items.reduce(...)` — 不要 `useState(total)` 再 `useEffect` 去同步它。
   > 这条能消灭一半的"状态不同步" bug。
2. **服务端状态不许复制进本地状态。** 用查询层的缓存，不要在 `useEffect` 里 `setData(fetch(...))`。
3. **能被 URL 表达的状态，就放 URL。** 筛选/分页/排序/tab 都属于此类。
4. **一个数据只有一个写入点。** 如果两个地方都能改它，你迟早会遇到"改了 A 看不见 B"。

**怎么验**：
- 全局搜索 `useEffect` ——**每一个都要能说出"它在同步什么"**。说不出就是状态放错了。
- 搜索同一个字段名出现在几处 —— 超过 2 处（定义 + 使用）就要怀疑。

## 三、组件边界：深模块思想用在前端

沿用 `codebase-design` 的**深模块**：**小接口，大量行为藏在里面**。

| 好 | 坏 |
|---|---|
| `<OrderList status="paid" onSelect={...} />` | `<OrderList orders={orders} isLoading={l} error={e} onRetry={r} selectedId={id} onSelect={s} sortBy={sb} onSort={os} page={p} onPage={op} />` |
| 组件内部自己取数据、管加载/错误 | 把 15 个 prop 从三层之上传下来（prop 钻孔） |

**判据**：
- **props 超过 7 个** → 大概率该在组件内部自己取数据，或拆成两个组件
- **同一批 props 在多个组件间重复传递** → 那是"数据泥团"（Fowler），该变成一个上下文或查询
- **组件名说不清它是什么** → 它的职责还没想清

**拆分的信号**（出现任一条就拆）：
1. 它有**两个以上不相关的状态**（如"列表 + 弹窗"）
2. 它同时**取数据**和**做复杂布局**
3. 它的测试要 mock 超过 3 个东西

## 四、设计系统：**令牌化，且强制使用**

**问题**：AI 每写一个新页面就发明一套颜色和间距 → 界面"能用但不像一个产品"。

**做法**：

1. **定义令牌**（放进 CSS 变量或主题文件），命名**语义化**而不是描述外观：
   ```
   ✅ --color-danger / --space-2 / --radius-md
   ❌ --red-500 / --padding-8px     ← 描述外观，换主题就全废
   ```
2. **禁止组件里出现裸值**：不许 `#3b82f6`、不许 `padding: 13px`、不许 `border-radius: 6px`。
   > 例外：**一次性的布局微调**（如 `margin-top: 2px` 对齐）可以，但**颜色和字号绝不允许裸值**。
3. **一个组件库，不要两个**。要么全用组件库，要么全自研——混用是最常见的"看起来不统一"来源。

**怎么验（可自动化）**：
```bash
# 找裸颜色值（应只出现在令牌定义文件里）
rg -n '#[0-9a-fA-F]{3,8}\b' src --glob '!**/tokens.*' --glob '!**/theme.*'
# 找魔法间距
rg -n 'padding:\s*\d+px|margin:\s*\d+px' src
```
**允许列表之外出现裸值 = 设计系统没生效。**

## 五、四种状态：**缺一不可**（这是最常被漏的）

任何"展示数据"的地方，必须**同时**实现：

| 状态 | 要求 | 常见漏法 |
|---|---|---|
| **加载中** | 骨架屏 / 转圈，**不白屏**；超过 ~1s 才显示（避免闪烁） | 只在本地快的时候测过 |
| **空** | 告诉用户"还没有数据" + **下一步怎么做** | 一片空白，用户以为坏了 |
| **错误** | 说清**发生了什么** + **能做什么**（重试/返回） | 静默失败或"未知错误" |
| **成功** | 正常路径 | — |

**外加两条**：
- **乐观更新要能回滚**（提交失败时界面退回去，不要停在乐观状态）
- **重复提交要防**（按钮禁用 + 服务端幂等）。**用户会双击。**

**怎么验**：每个列表/详情组件，**在测试或 Storybook 里手动触发这四种状态**（把请求 mock 成 pending / empty / reject / resolve）。
> 这一步能抓住近一半的"上线才发现"的问题。

## 六、可访问性：最低线（不是可选项）

不用做到完美，但这五条**必须**有——它们同时改善**所有人**的体验：

1. **语义标签**：按钮用 `<button>`，不要 `<div onClick>`（键盘和读屏都用不了）
2. **可聚焦**：所有交互元素 Tab 能到；焦点可见（别 `outline: none` 了事）
3. **表单有标签**：`<label>` 关联，或 `aria-label`；错误信息与字段关联
4. **图片有 alt**：装饰性图片用 `alt=""`
5. **颜色不是唯一信息载体**：错误不能只靠红色，要有文字/图标

**为什么它同时是"可测性"问题**：语义化做好之后，**Playwright 可以用角色+名称定位元素**（`getByRole('button', { name: '提交' })`），比 CSS 选择器稳得多——**界面重构不会弄坏测试**。

## 七、怎么证明界面真的对（**前端专属的验证纪律**）

前端的反馈回路比后端长得多。**"我改了代码"和"界面真的对了"之间隔着一整条链路**——所以要显式建回路。

| 层次 | 手段 | 抓什么 |
|---|---|---|
| **1. 类型/编译** | `tsc --noEmit` | 传错 prop、字段名错 |
| **2. 组件测试** | Testing Library / Vitest | 逻辑、四种状态、交互 |
| **3. 端到端** | **Playwright** | **真的能走通核心链路**（登录→主流程→付款） |
| **4. 视觉/语义快照** | Playwright 截图对比 / **ARIA 快照** | 样式意外回归；**语义结构变了** |
| **5. 人工一眼** | 截图给人看 | 只有人能判"丑不丑、像不像一个产品" |

**纪律**：

- **不许用"我看代码觉得对"当验证。** 必须至少跑到第 3 层（端到端）走一次核心链路。
- **ARIA 快照**特别适合 AI 场景：它把页面的**语义结构**固定下来，
  比像素对比稳定（不受字体渲染差异影响），又能抓住"我重构 UI 时把按钮改成了 div"这类退化。
- **视觉快照要限定区域**，别全页对比（否则内容一变就红，很快就没人看了）。
- **发布前跑一次真实浏览器**，不要只信组件测试——它们跑在 jsdom 里，没有真实布局和网络。

**终检清单**（上线前逐条过）：
```
□ tsc --noEmit 通过
□ 组件测试通过（含四种状态）
□ Playwright 跑通核心链路（真浏览器）
□ 移动端宽度下不溢出（至少 375px 看一眼）
□ 键盘能走完核心链路（Tab + Enter）
□ 控制台无错误/无警告
```

## 八、反模式清单

1. **组件里写死 mock 数据** → 假装有后端。**要么真调接口，要么显式标注 `// TODO: 接后端` 并让它在界面上可见**（"演示数据"标记）。
2. **`useEffect` 同步状态** → 派生状态算出来即可；服务端状态用查询层。
3. **`useEffect` 依赖数组漏项/乱写** → 无休止重渲染。**依赖写全，或用 lint 规则强制。**
4. **在渲染里新建对象/数组当 prop** → 每次渲染都变 → 子组件永远重渲染。用 `useMemo` 或提到组件外。
5. **裸颜色/魔法间距** → 设计系统失效。
6. **`<div onClick>`** → 不可键盘操作、读屏读不到。
7. **`outline: none` 去焦点框** → 键盘用户彻底迷路。要自定义就换成可见的替代样式。
8. **只做成功状态** → 加载/空/错误三态必漏。
9. **测 CSS 选择器** → 重构就红一片。用 `getByRole` / `getByLabelText`。
10. **"本地看着对"就算完成** → 真实浏览器 + 真实数据才算（对齐 `fullstack-delivery` 的"部署通过"要求）。

## 九、怎么跟其他技能配合

| 什么时候 | 加载什么 |
|---|---|
| 前端要接后端 | `fullstack-delivery`（契约先行：API 契约写成文件，前后端按契约并行） |
| 前端逻辑复杂（状态机、reducer） | `prototype` 做一次性原型验证状态模型，再落地 |
| 前端有难 bug / 性能回归 | `diagnosing-bugs`（**先建一个能对它变红的回路**） |
| 快上线了 | `production-readiness`（前端的检查项在 G 节之外，主要看错误上报与性能） |
| 要证明"用户真能走通付款" | **Playwright**（见 `payment-and-billing` 的上线前验证） |
| 界面要给真人看之前 | **截图给人确认**——这是唯一能判"像不像一个产品"的手段 |
