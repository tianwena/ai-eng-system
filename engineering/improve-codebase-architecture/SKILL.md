# Improve Codebase Architecture（改进代码库架构）

浮出架构摩擦并提出**加深机会**——把浅模块变成深模块的重构。目标是**可测试性**和**AI 可导航性**。

这个命令**受**项目的领域模型**启发**，并建立在共享的设计词汇上：

- 跑 `/codebase-design` 技能来获取架构词汇（**模块**、**接口**、**深度**、**接缝**、**适配器**、**杠杆**、**局部性**）及其原则（删除测试、"接口就是测试面"、"一个适配器 = 假想接缝，两个 = 真接缝"）。在每一条建议里**精确**使用这些术语——不要漂移到 "component"、"service"、"API" 或 "boundary"。
- `CONTEXT.md` 里的领域语言给好的接缝命名；`docs/adr/` 里的 ADR 记录了这个命令**不该重新争辩**的决策。

## 流程

### 1. 探索

**扫描之前先定范围——YAGNI。** 加深一个模块的回报是"让它未来的改动更容易"，所以**把额外的权重放在最近改动过的部分**。在**看**之前先决定**往哪看**：

- 如果用户指明了方向——某个模块、某个子系统、某个痛点——就用它，跳过下面的推断。
- 否则，回翻足够长的一段提交历史（`git log --oneline`），找出代码库的热点——反复出现的文件和区域——让这些路径先把你的注意力拉过去。如果改动很分散、没有明显热点，就把网撒大些。

先读项目的领域术语表（`CONTEXT.md`）和你所触及区域的任何 ADR。

然后起一个子 agent 走查代码库。不要套用死板的启发式——**有机地**探索，并记下你在哪里碰到摩擦：

- 哪里理解一个概念需要在许多小模块之间来回弹跳？
- 哪些模块是**浅**的——接口几乎和实现一样复杂？
- 哪里纯粹为了可测试性抽出了纯函数，但真正的 bug 藏在**它们怎么被调用**上（没有**局部性**）？
- 哪些紧耦合的模块越过自己的接缝漏了出来？
- 代码库的哪些部分没测试，或者很难透过它当前的接口来测试？

对你怀疑是浅模块的任何东西应用**删除测试**：删掉它会让复杂度**集中**，还是只是**搬家**？"是的，会集中"才是你要的信号。

### 2. 以 HTML 报告呈现候选

写一个自包含的 HTML 文件到操作系统临时目录，这样什么都不会落进仓库。写到 `<tmpdir>/architecture-review-<timestamp>.html`，让每次运行都得到一个新文件。

**临时目录与打开方式都要跨平台**（写错了在 Windows 上会静默失败）：

| 平台 | 临时目录 | 打开文件 |
|---|---|---|
| Linux / macOS | `$TMPDIR`，回退 `/tmp` | `xdg-open <path>` / `open <path>` |
| **Windows（PowerShell）** | **`$env:TEMP`** | **`Start-Process <path>`** |

> ⚠️ **别用 `start <path>`**：`start` 是 **cmd.exe 的内建命令**，不是独立程序。在 PowerShell 里
> `start` 是 `Start-Process` 的别名，参数语义不同——照抄 `start <path>` 到非交互 shell 里会**静默失败**。

告诉用户绝对路径（即使自动打开失败，他也能自己点开）。

报告用 **CDN 的 Tailwind** 做布局和样式，用 **CDN 的 Mermaid** 画图（当图/流/时序能可靠传达结构时）。把 Mermaid 和手写的 CSS/SVG 视觉混用——关系呈图状时（调用图、依赖、时序）用 Mermaid；想要更杂志化的表达时（体量图、剖面图、坍缩动画）用手搭的 div/SVG。每个候选都要有**前后对比可视化**。**要视觉化。**

对每个候选渲染一张卡片，包含：

- **Files（文件）** —— 涉及哪些文件/模块
- **Problem（问题）** —— 当前架构为什么造成摩擦
- **Solution（方案）** —— 用平实中文描述会改什么
- **Benefits（收益）** —— 用局部性和杠杆来解释，以及测试会如何改善
- **Before / After diagram（前后对比图）** —— 并排、手绘，展示"浅"与"加深"
- **Recommendation strength（推荐强度）** —— `Strong`（强）、`Worth exploring`（值得探索）、`Speculative`（推测性）之一，渲染成一个徽章

报告以 **Top recommendation** 小节收尾：你会先做哪个候选、为什么。

**领域用 `CONTEXT.md` 的词汇，架构用 `/codebase-design` 的词汇。** 如果 `CONTEXT.md` 定义了 "Order"，就说"Order 接入模块"——不要用 "FooBarHandler"，也不要用 "Order service"。

**ADR 冲突**：如果某个候选与既有 ADR 矛盾，只有当摩擦真实到值得重开该 ADR 时才把它摆出来。在卡片里明确标注（例如一条警告提示：_"与 ADR-0007 矛盾——但值得重开，因为……"_）。不要列出每一个被 ADR 禁止的理论重构。

完整的 HTML 脚手架、图表模式和样式指南见 [HTML-REPORT.md](HTML-REPORT.md)。

**先不要**提接口方案。文件写完之后，问用户："这里面你想探索哪一个？"

### 3. 逼问循环

用户挑定一个候选后，跑 `/grilling` 技能和他一起走决策树——约束、依赖、加深后模块的形状、接缝后面坐着什么、哪些测试能存活。

随着决策结晶，**副作用就地发生**——跑 `/domain-modeling` 技能，让你边走边保持领域模型最新：

- **给加深后的模块命名时用了 `CONTEXT.md` 里没有的概念？** 把该术语加进 `CONTEXT.md`。文件不存在就惰性创建。
- **对话中磨锋利了一个模糊术语？** 当场更新 `CONTEXT.md`。
- **用户用了一个**承重的理由**否决该候选？** 提议一份 ADR，话术是：_"要我把它记成 ADR，避免未来的架构评审再提这个吗？"_ 只有当未来的探索者确实需要这个理由来避免重新提议同样的事情时才提议——跳过临时性理由（"现在不值得"）和自明的理由。
- **想探索加深后模块的替代接口？** 跑 `/codebase-design` 技能，用它的 design-it-twice 并行子 agent 模式。
