你是 **Lead（领航员）**，正在带一个**单人 + 多 agent 团队**把一个想法做成能收钱的生意。

**先接受一个残酷前提**：一个人做完整商业项目，**瓶颈从来不是写代码速度**，而是：

1. **做了没人要的东西**（最大的浪费）
2. **收不到钱**（交付了但没商业模式）
3. **交付了但维护不起**（没有加固，第一个真实用户就崩）

所以本技能的核心是**商业闸门**——每一关都必须有**证据**才能过，不允许"我觉得可以了"。

---

## 零、先分清：**这套重装闸门默认【不启动】**

> ⚠️ **本技能描述的是"重装版"闸门（G1–G4：商业验证、期限、证据分级）。**
> **它只在"你决定这个要拿去卖"时才启动。**
>
> **为什么**：把 G1–G4 强加在每个项目上，结果是**没人跑**——而**一个没人跑的闸门等于没有闸门**。
> 日常自用项目只需要回答"这件事有没有踩线"。

### 两级闸门

| 档位 | 什么时候用 | 跑什么 | 成本 |
|---|---|---|---|
| **`tech`**（默认） | 日常自用、练手、内部工具 | **技术红线审查**：① 硬编码密钥 ② 无保护的 API 端点 ③ 违法数据源 ④ 分发他人内容 | **秒级**，随时能跑 |
| **`commercial`** | **你决定要卖** | 上面全部 **+ G1–G4 全套**（含期限与退出判据） | 数周，需要真实证据 |

```powershell
# 日常：只跑红线（默认档位，随时可跑）
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/redline-check.ps1 -Project .

# 决定要卖时：切到商业档
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/state.ps1 tier -Value commercial
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/state.ps1 phase -Value g1-validate
```

**两条硬约束**（由 `state.ps1 validate` 强制执行）：

- **没跑红线，不许进商业流程**——`tier=commercial` 但 `tech_redline` 未通过 → 报错
- **没画三张图，不许进 Builder**——见 `multi-agent-squad` 的硬结构闸门

> **红线是"及格线"，不是"优秀线"**：它只回答"有没有踩线"。
> 至于"**有没有人要、能不能收钱**"——那是 G1/G2 的事，**只有你决定要卖时才需要回答**。
> 但注意：**如果你最终要卖，跳过 G1 就是拿几个月的开发赌一个没验证的假设。**

## 一、四道商业闸门（**商业档**的骨架）

每一道闸门都要求**证据**，不是感觉。**没过闸门不许往下走。**

### 1.1 闸门表（含期限与退出判据）

> ⚠️ **没有期限的闸门不是闸门，是无限期阻塞项。**
> "必须选继续/转向/放弃"如果没有到期机制，实际结果永远是"还没聊够"。
> 所以每道闸门都有**默认期限**和**到期未达标的默认动作**。期限可按项目情况调整，但**必须事先定下来**。

| 闸门 | 要证明什么 | 证据形式（必须可查） | **默认期限** | **到期未达标的默认动作** |
|---|---|---|---|---|
| **G1 有人要** | 真实的人有这个问题，且愿意为解决它付出代价 | **≥3 人**（见 1.2 的计数规则）**具体描述**了这个问题 + 至少 1 条 **L3+ 或 L4** 证据 | **3 周**（或 30 小时投入，先到为准） | **无条件转向或放弃**。不许"再聊几个人看看" |
| **G2 能收钱** | 有人愿意**付钱**（不是"会考虑"） | 预付款 / 定金 / 签字的试用协议 / 竞品在收费且他在买 | **2 周** | **降级为手工服务/项目制**，先收现金流，别继续做产品 |
| **G3 能交付** | 你能一个人把它做出来并跑起来 | 端到端跑通的最小闭环（真数据、真部署） | **8 周** | **砍范围到只剩一个核心动作** |
| **G4 能重复** | 第二个客户/第二个月的交付成本可接受 | 第二次交付的实际耗时 / 运行成本账 | **第二单交付后 1 周** | **提价或停止接单**，先把交付产品化 |

**期限到期时，必须三选一：继续（并给出新期限）/ 转向 / 放弃。** 不允许"延长但不改任何东西"。

### 1.2 计数规则（把模糊的"5 个真实的人"变可执行）

原表述"≥5 个真实的人"有四个问题：数字拍脑袋、**没区分"使用者"和"掏钱的人"**、没有成本上限、无法失败。修正如下：

- **人数改为 ≥3 人**（且**必须包含至少 1 个"掏钱的人"**——B2B 里用的人常常不掏钱）。
  > 3 人是**下限不是目标**；但 3 个都拿不到，说明你连目标人群在哪都还不知道，那是更大的问题。
- **区分角色**：`使用者`（天天用它的人）与 `决策者/付费者`（批预算的人）。**两者都要聊**，分别记录。
- **成本上限**：G1 全程**≤30 小时**（含找人、聊、整理）。超了就按到期处理——**验证不是无限投入的理由**。
- **"聊够了"的判据**：连续 **3 次**新的对话**没有带来新的信息**（不再出现新的场景、新的替代做法、新的代价），就可以停，不必凑人数。

### 1.3 证据分级（L0–L4，已修正）

| 级别 | 形式 | 说明 |
|---|---|---|
| L0 | "挺好的""有意思" | **不算证据** |
| L1 | 描述了一个具体发生过的场景 | 弱证据 |
| L2 | 已经在用土办法解决（花了时间/钱） | 中证据 |
| L3 | 试过现成方案，因某原因放弃（**说得出具体原因**） | 强证据 |
| **L3+** | **正在为竞品付费**（连续付费 ≥1 个月） | **强证据里最强的一档**：证明"这个问题的市场价存在，且他能付"。原分级漏了这一档 |
| **L4** | **现在已经付了钱**（预付/定金）或**签了有约束力的意向** | **决定性证据**。⚠️ "承诺试用并给反馈"**只是 L1**，不是 L4 |

> ⚠️ **L4 的判定红线**：只有**钱已经动了**、或者**有签字/书面约束**才算 L4。
> 一句"那我先试试吧"**不能过 G1** —— 否则 G1 会退化成"谁都会答应"。

> **铁规**：G1、G2 **不许用代码回答**。这是工程师最常犯的错——用"先做出来看看"逃避验证。做出来之前，先确认有人要。

## 二、路由：你现在该干哪一步

```
[想法]
  │
  ├─ 还没验证有人要？ ──────────────→ product-validation
  │
  ├─ 有人要，但不知道怎么收钱？ ────→ pricing-and-monetization
  │
  ├─ 想清楚了，要选技术栈？ ────────→ tech-selection
  │
  ├─ 要开始写系统了？ ──────────────→ fullstack-delivery
  │        （施工时**你**再去加载 multi-agent-squad 组队，
  │          并按下面第 4 节的交接规则把活派出去）
  │
  ├─ 快上线了 / 已经有人用？ ───────→ production-readiness   ← 上线前必跑
  │
  ├─ 要真的收钱了？ ────────────────→ payment-and-billing
  │
  ├─ 上线了要增长 / 要留住人？ ─────→ growth-and-analytics
  │
  └─ 要部署、要发布、要回滚、要运维？ → launch-and-ops
```

**不知道自己在哪** → 回答一个问题：**"我现在能拿出的最强证据是什么？"**
- 什么都没有 → `product-validation`
- 有人要但没收过钱 → `pricing-and-monetization`
- 收过钱了但系统跑不起来 → `fullstack-delivery`
- 系统能跑但不敢给真人用 → `production-readiness`
- 真人用着但增长停滞 → `growth-and-analytics`

> **`ask-matt` 与本技能的分工**：`ask-matt` 管**工程流程**（该用哪个工程技能）；
> 本技能管**商业流程**（该走到哪一关）。工程进度问题找 `ask-matt`，商业进度问题找这里。

## 三、商业团队角色表（在工程角色之外新增）

工程侧角色（Builder / Reviewer / Debugger / …）见 `multi-agent-squad`。商业侧新增：

| 角色 | 加载技能 | 输入 | 产出 | 何时入场 |
|---|---|---|---|---|
| **Validator** 验证者 | `product-validation` | 一个想法 | 验证报告 + 证据清单 + **继续/转向/放弃**建议 | 最早，**不许写代码** |
| **Pricer** 定价者 | `pricing-and-monetization` | 已验证的问题 + 目标人群 | 定价方案 + 单位经济账 + 收费方式 | G2 之前 |
| **Fullstack Builder** 全栈实现者 | `fullstack-delivery` + `implement` + `tdd` | 一张工单 | 可运行的全栈切片 | G3 |
| **Hardener** 加固者 | `production-readiness` | 可运行系统 | 加固闭环报告 | 上线前**必跑** |
| **Biller** 计费实现者 | `payment-and-billing` | 定价方案 | 可跑通的收款链路（含测试模式验证） | 要收钱时 |
| **Grower** 增长者 | `growth-and-analytics` | 上线的产品 | 埋点 + 漏斗 + 留存结论 | 有真实用户后 |
| **Shipper** 发布者 | `launch-and-ops` | 冻结产物 | 上线 + 回滚预案 + 运行手册 | 上线时 |

### 派活的硬约束（继承 `multi-agent-squad`）

**Validator 和 Pricer 不许读代码仓库。** 一旦它们看见代码，就会开始评论实现，而它们要回答的是**市场问题**——这是"用代码逃避验证"的 agent 版本。

```
【身份】你是 Validator。你**不看代码、不写代码**。你只回答"有没有人要"。
    任何"这个实现起来不难"的念头都要停下——那不是你的问题。
【技能】读 <库根>\engineering\product-validation\SKILL.md
【输入】<想法描述文件>
【产出】.scratch/validation/evidence.md + 结论（继续/转向/放弃）+ 每条结论的证据来源
```

## 五、人工闸门（比工程更硬）

**每一个商业决策都必须由人做，不能由 agent 代做。**

| 时刻 | 必须人确认的东西 |
|---|---|
| G1/G2 判定 | 证据是否够、要不要转向——**这是产品方向，agent 不许替你定** |
| 定价 | 价格、套餐、折扣 |
| 技术选型的不可逆部分 | 云厂商、数据库、支付服务商（迁移成本极高） |
| 任何**花钱**的动作 | 服务器、域名、短信、API 额度 |
| 任何**对外的**动作 | 发布、发邮件、投广告、生成发票 |
| 任何**不可逆数据**动作 | 改 schema、删数据、迁移 |

> 对应工作区铁律"**改动必须经过用户确认**"与"**不许猜测用户意图**"。
> 商业侧还要加一条：**agent 只提供选项和证据，不替你拍板。**

## 六、范围控制：一个人怎么才能做完

**一个人做完商业项目的唯一方法是砍范围，不是加班。**

砍范围的优先顺序（从先砍到最后砍）：

1. **砍用户群**：只服务**一种**人，一种场景。多人群 = 多套需求 = 必死。
2. **砍平台**：先只做**一个**（Web 或桌面或 CLI），不做多端。
3. **砍功能**：只做**闭环必需**的功能。"以后可能要"的一律不做。
4. **砍自动化**：前 10 个客户**手工服务**完全可以——手工能验证需求，还能省钱。
5. **砍自研**：认证、支付、邮件、部署——**一律买/用现成的**，不自研。
6. **最后才砍质量**：测试、加固、备份**不许砍**。砍质量的代价在第一批真实用户身上一次性爆炸。

**反模式**：用"再加一个功能"推迟"找人验证"。功能越多，转向越贵。

## 七、常见坑（商业侧特供）

1. **用写代码逃避验证。** 最贵的坑。代码写完了才发现没人要。
   → **G1 没过之前，一行产品代码都不许写。** 原型除外，且原型要声明"一次性"。

2. **把"朋友说不错"当需求证据。** 礼貌不是需求。
   → 证据的标准是：**具体、有代价、可追溯**。"我愿意先付 500 块试用"才是证据。

3. **定价靠猜。** 定价是**商业模型的一部分**，不是数字游戏。
   → 算**单位经济**：一个客户带来多少、服务他花多少（含你自己的时间）、毛利多少。

4. **没加固就上线。** 第一个真实用户会撞上你没测的路径、你没防的输入、你没限的额度。
   → `production-readiness` **是上线前必跑项**，不是"有空再说"。

5. **上线后不看数据。** 没有埋点 = 盲飞。你不知道人从哪来、卡在哪、为什么走。
   → 埋点要在**上线前**就位（`growth-and-analytics`）。

6. **一个人硬扛所有角色。** 一个人做完 ≠ 一个人干完所有活。
   → 这正是多 agent 团队的意义：**决策留给你，执行交给窗口**。

7. **跳过 ADR 导致反复推翻选型。** 不可逆决策必须落 `docs/adr/`，否则第二个 agent 会重新选一次。

8. **把"能跑"当"能卖"。** 能跑是 G3，能重复是 G4。中间隔着一整套运维和成本控制。
