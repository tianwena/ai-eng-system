# Ask Matt

你不可能记住每一个技能，所以问就是了。

**流程（flow）** 是穿过技能的一条路径。大多数路径沿一条**主流程**走，另有两条**汇入口（on-ramp）**并入其中。其余的要么是独立技能，要么是跑在底层的**词汇层**。

> ⚠️ **本文里的 `/xxx` 是"技能名"的简写，不都是能敲的命令。**
> 在 DSH 里，**只有 user-invocable 技能**能靠 `/名字` 触发；model-invoked 技能是**让 agent 自己去加载**的。
> 判断办法：`/名字` 敲不出来时，就直接说"用 **`名字`** 技能"，或让 agent 加载它。
> 两类的区别与完整清单见 `SKILLS.md` 与 `DSH-INTEGRATION.md`。

## 主流程：想法 → 交付

大多数工作走的路线。你有个想法，想把它做出来。

1. **`/grill-with-docs`** —— 通过访谈把想法磨锋利。只要你**在一个工作目录里**，就从这里开始：它是有状态的，会把学到的东西留在 `CONTEXT.md` 和 ADR 里。（没有工作目录？用 `/grill-me`——见"独立技能"。两者跑的是同一个 `/grilling` 原语；`grill-with-docs` 是会留下纸面痕迹的那一个，所以只要有仓库可留痕，它就是两者中更好的。）

2. **分支——每个问题都能靠对话定下来吗？** 如果某个问题需要**能跑起来的答案**（状态、业务逻辑、必须看一眼的 UI），就绕道走原型；两个方向都用 **`/handoff`** 搭桥（原型自成一个目录，而这正是 `/handoff` 的用途——见"阶段边界"）：
   - **`/handoff`** 出去，然后针对那个文件开一个全新会话；
   - **`/prototype`** 用一次性代码回答那个问题；
   - **`/handoff`** 把学到的东西带回来，并从原来的想法讨论串里引用它。

3. **分支——这是多会话规模的工程吗？**
   - **是** → **`/to-spec`**（把讨论串变成规格说明），然后 **`/to-tickets`** 拆成曳光弹工单，每个声明自己的**阻塞边**。在本地追踪器上，这就是 `.scratch/<feature>/issues/` 下每张工单一个文件，人工按阻塞优先顺序推进；在真实追踪器上，阻塞边变成原生的 blocking 链接，于是任何一张"阻塞项已完成"的工单都能直接拿下——**每张工单跑一次 `/implement`，每次之间 `/clear` 上下文**。每张工单都是自足的，所以上一张的上下文可以随意丢弃。
   - **否** → 就在这儿 **`/implement`**，同一个上下文窗口里做完。

   两条路都一样：**`/implement`** 在内部驱动 **`/tdd`** 来建每个 issue——一次一个红绿切片——然后收尾时跑 **`/code-review`**，对 diff 做双轴审查（标准 + 规格），通过后再提交。当你只想不写完整规格、直接把一个具体行为测试先行地做出来时，单独用 **`/tdd`**；当你想针对某个固定点审查一个分支或 PR 时，单独用 **`/code-review`**。

### 上下文卫生

把第 1~3 步保持在**同一个未中断的上下文窗口**里——在 `/to-tickets` 之前不要 compact 或 clear——这样逼问、规格和工单都建立在同一套思考上。之后每个 `/implement` 都从头开始，从工单出发干活。

这件事的限制是 **智能区（smart zone）**：上下文窗口的**一部分**（经验值 ≈15%），模型在其中仍能犀利推理。
> ⚠️ **别把这个数字当固定值**：它随模型变。**先查当前模型的 `contextWindow`**，再按比例估。
> （写死一个数字会在换模型时变成错的，也会让人在只用掉一小部分容量时就白白换窗口。）

如果某个会话在 `/to-tickets` 之前就逼近它，别在降智状态下硬推——在最接近的**阶段边界**处做上下文决策，然后继续（见"阶段边界"）。

## 汇入口（On-ramps）

一种"先产生工作、再并入主流程"的起始处境。

- **bug 和请求堆成山** → **`/triage`**。它让 issue 走一遍分诊角色，产出 **agent 就绪**的 issue，之后由 **`/implement`** 接手。

  分诊只针对**不是你创建的** issue——别人报的 bug、外部来的功能请求、任何原始形态到达的东西。`/to-tickets` 产出的工单已经是 agent 就绪的，所以**不要对它们做分诊**。

- **有东西坏了** → **`/diagnosing-bugs`**。用于难啃的那些：一眼看不出原因的 bug、间歇性抽风、在两个已知良好状态之间悄悄溜进来的回归。它在拿到一个**紧密反馈回路**（一条命令，已经能对*这个* bug 变红）之前**拒绝提出理论**，然后用回归测试修掉。当它的复盘发现"真正的结论是这里根本没有好的接缝把这个 bug 锁死"时，就把它交给 **`/improve-codebase-architecture`**。

- **一大团雾气重重的工程——绿地项目，或大到一个会话装不下的大功能** → **`/wayfinder`**，本仓库认知负担最重的流程。当从这里到目的地的路还看不见时，它在 issue 追踪器上画出一张**共享地图**，由**决策工单**组成，逐个解决——产出的是**决策，不是交付物**——直到把雾推开、路径清晰。**`/grill-with-docs`** 磨的是你能在一个会话里握住的想法；wayfinder 处理的是你握不住的那种——它更慢、更密，所以只留给真正需要的场景，绝不要用在范围明确的普通功能上。

  地图变清晰后，**它是交接，不是施工**：在 **`/to-spec`** 处并入主流程，由它把地图里互相链接的决策**收敛成一份可施工的计划**，然后照常 `/to-tickets`、`/implement`。把地图直接接进 `/implement` 会跳过这次收敛，把那些互相链接的细节全丢掉——只有当这个工程最后发现确实很小的时候，才直接去 `/implement`。

## 商业落地流程：想法 → 收钱

> **本节不在工程流程上。** 上面那条主流程解决"**怎么把东西做出来**"；
> 这一条解决"**该不该做、能不能收到钱、怎么活着上线**"——**先走这条，再走上面那条**。
> 完整作战地图与四道闸门见 **`commercial-squad`**；这里只是告诉你**什么处境该去哪一步**。

**唯一的顺序原则**：每一关都要**拿到证据**才往下走，**没过就不许写产品代码**。

| 你现在的处境 | 去哪 |
|---|---|
| 有个想法，但**不确定有没有人要** | **`product-validation`** ← **从这里开始**。不要先写代码。 |
| 已验证有人要，但**不知道怎么收钱 / 毛利算不过来** | **`pricing-and-monetization`** |
| 想清楚了，要**选技术栈**（不可逆决策） | **`tech-selection`**（结论写进 `docs/adr/`） |
| 要**开始建系统**了 | **`fullstack-delivery`** → 它会把你接回上面的主流程（`/to-tickets` → `/implement`） |
| 要**组多 agent 团队**干活 | **`multi-agent-squad`**（三条铁律、角色表、三段式派活、DSH 机制映射） |
| 快上线了 / 已经有人用 | **`production-readiness`** ← **上线前必跑**（先跑自动闸门，再做人工项） |
| 要**真的收钱** | **`payment-and-billing`**（订阅状态机、Webhook 幂等、额度、对账） |
| 要**部署、回滚、运维** | **`launch-and-ops`** |
| 有真实用户了，要**看数据、留住人** | **`growth-and-analytics`**（北极星、埋点、漏斗、留存） |

**四条闸门**（`commercial-squad` 里有期限与退出判据）：**G1 有人要 → G2 能收钱 → G3 能交付 → G4 能重复**。

> ⚠️ **别把这条流程当"以后再说"**：`product-validation` 排在最前面，是因为**做出来才发现没人要**是这类项目最贵的失败。
> 反过来，**已经有人愿意付钱**再回来走主流程，才是正确的顺序。

## 代码库健康

不是功能开发，是保养。

- **`/improve-codebase-architecture`** —— 有空就跑，让代码库保持"适合 agent 在里面干活"。它浮出**加深机会**；挑中一个就**生成一个想法**，你可以把它带进主流程的 `/grill-with-docs`。它是**找出候选的体检**；**`/codebase-design`**（见下）是你设计选中的那个时所站的**工作台**。

## 底层词汇

两个模型调用的参考技能，跑在其他技能*下面*——各自是自己那套词汇的唯一事实来源。当出问题的是**词**而不是流程时，直接够它们；或者让上面的技能把它们拉进来。

- **`/domain-modeling`** —— 磨炼项目的*领域*语言：质疑一个模糊的词、解决一个过载词（"account" 身兼三职）、把难以逆转的决策记成 ADR。它是 `/grill-with-docs` 驱动的主动纪律，用来让 `CONTEXT.md` 保持一份干净的术语表。

- **`/codebase-design`** —— 设计模块*形状*时用的深模块词汇（模块、接口、深度、接缝、适配器、杠杆、局部性）：大量行为藏在干净接缝处的小接口后面。`/tdd` 和 `/improve-codebase-architecture` 都说这套语言。

## 前端

前端有它自己的纪律（状态归属、设计系统、四种状态、**怎么证明界面真的对**），**别拿后端的直觉硬套**。

- **`frontend-delivery`** —— 要写/改**用户直接看到的**那一层时用它。它专治 AI 写前端的四种病：
  **假后端**（组件里写死 mock 数据）、**状态乱放**（同一数据存三份到处同步）、
  **每页一套样式**（裸颜色/魔法间距）、**无休止重渲染**（`useEffect` 依赖乱写）。
  并给出**前端专属的验证链**：`tsc` → 组件测试 → **Playwright 端到端** → **ARIA 快照** → 人工一眼。
  > **关键判据**：前端改动**不许用"我看代码觉得对"当验证**——至少跑到端到端那层走一次核心链路。

- 前端要**接后端** → 先看 `fullstack-delivery`：**契约先行**（API 契约写成文件，前后端按契约并行）。
- 前端**逻辑复杂**（状态机、reducer） → 先用 `prototype` 验证状态模型，再落地。
- 前端有**难 bug / 卡顿** → `diagnosing-bugs`（**先建一个能对它变红的回路**）。

## 阶段边界

**阶段（phase）** 是会话内的一块工作——逼问、实现、QA。在两个阶段的**边界**上，你有五个选项，而在这五个之间做选择，是整张地图里最模糊的一个决策：

- **继续（Continue）** —— 原地不动。不花成本，也不丢东西。
- **开新窗口** —— 此处对接下来毫无意义时，直接开一个干净会话。（**不是 `/clear`**——DSH 没有这个命令。）
- **`/handoff`** —— 写一个可携带的 markdown 文件。范围很窄：只用于**换平台**、**换目录**、**给同事**，或在**阶段中途**分叉出一个支线任务。它买到的是**可携带性**。
- **子 agent（Subagent）** —— 把一个范围收得很紧的任务送到它自己的窗口，拿一份报告回来。DSH 里用后台子 agent / 工作流脚本；**派完不要空等**。
- **写交接文件后开新窗口** —— 想压缩上下文时用这个。（**不是 `/compact`**——DSH 没有这个命令；
  写文件比压缩更可靠，因为文件里能带上**推理**，压缩会丢 why。这是**默认选项**，位于决策树的底部，而不是伸手就够的第一个。）

> ⚠️ **DSH 命令现实**：`/clear`、`/compact` 在 DSH 里**不存在**。
> 漏掉这层映射的 agent 会"发明一个到不了的动作"，然后声称自己已经压缩了上下文——**这是静默错误**。
> 上面两条已给出等价做法。跨 harness 的完整对应表见 `多Agent团队协作编排指南.md` 第 8 节。

按顺序读 [PHASE-BOUNDARIES.md](PHASE-BOUNDARIES.md) 里的决策树——五个问题、每个分支背后的推理，以及为什么"一手来源的成本"让**继续**成为第一个该被排除的选项。要在**边界上**做决定；阶段中途，要么继续，要么把剩下的工作拆给子 agent。

## 独立技能

完全不在主流程上。

- **`/grill-me`** —— 和 `/grill-with-docs` 一样无情的访谈，但**无状态**：不在本地保存任何东西，也不建 `CONTEXT.md`。当你**不在工作目录里**时用它——磨一个计划、一个设计、一篇写作，任何下面没有仓库的东西。如果你在工作目录里，就用 `/grill-with-docs`：它跑同一场访谈还留下纸面痕迹，所以严格来说它是更好的那个。

- **`/grilling`** —— 访谈原语本身：轮次、前沿、事实是 agent 的活儿、决策是你的。`/grill-me` 和 `/grill-with-docs` 是两个具名的入口，`/triage`、`/wayfinder`、`/improve-codebase-architecture` 都在内部跑它。只有当你想要"没有任何包装的访谈"时，才直接够它。

- **`/resolving-merge-conflicts`** —— 逐块（hunk）处理进行中的 merge 或 rebase 冲突，按**追溯到各边一手来源的意图**来裁决，而不是挑几行留着，然后完成这次操作。它从不跑 `--abort`。独立技能，不在任何流程上：当你已经在冲突现场时够它。

- **`/prototype`** —— 一个小的一次性程序，回答一个设计问题：这个状态模型对不对，或者这个 UI 该长什么样。"一次性"是关于**怎么写这段代码**的约束，不是"要毁掉它"的承诺：答案会折进真实代码，而原型本身作为**一手来源**保留在从 main 分出的 `prototype/<name>` 分支上，由实现用的 issue 指向它。它是主流程第 2 步里的那个绕道，但任何时候只要一个设计问题在纸上很难定，都可以够它。

- **`/research`** —— 把读资料的跑腿活外包给一个**后台 agent**：它针对**一手资料**调研一个问题，然后在仓库里留下一份带引用的 Markdown 文件。它读的时候你继续干活。它产出的文件是拿来*带进*主流程 `/grill-with-docs` 的东西——研究**喂养**思考，不**替代**思考。

- **`/to-questionnaire`** —— 当卡住你的东西既不在你脑子里、也不在代码库里，而在**别人脑子里**时，这个技能替你写一份问卷让对方填。它是 `/grill-me` 的反面：不是就主题访谈你，而是就**这次投递**访谈你——要发给谁、需要拿回什么——然后把问题瞄准那个缺口。回来的东西是 `/grill-with-docs` 或 `/to-spec` 的素材。

- **`/wizard`** —— 用于**只有人**能做的步骤：开通基础设施、配置凭据或 CI 密钥、点完一个陌生的第三方后台、跑一次性的迁移或割接。它生成一个交互式 bash 脚本，逐个打开 URL、采集每个值、写进 `.env` 和 GitHub secrets——这样这套流程就不再是"每次都要向 agent 重新解释一遍"的东西。模型调用，所以 agent 一撞上"只有你能过"的墙就够它。如果 agent 自己能做，它就该自己做；这个技能是给"人确实在回路里"的场景。

- **`/wait-what`** —— 针对"没听懂的消息"的纠正手段。在对话中途用，可以在任何其他技能内部用，agent 会用你缺失的上下文、平实的中文、以及 `CONTEXT.md` 里的词汇，把它刚说的话重新讲一遍。它是事后补救；`/grill-with-docs` 才是事前的根治，因为早早议定的共享语言才是不让行话出现的原因。

- **`/teach`** —— 跨多次会话学习一个概念，把当前目录当作有状态的工作区。

- **`/writing-for-agents`** —— 怎么写 agent 消费的文档：skills、`AGENTS.md`、被指针指向的文档。

## 前置条件

**`/setup-workspace-discipline`** —— 在你第一次跑工程流程之前执行，用它配置其他技能所假设的 issue 追踪器、分诊标签和文档布局。自定义的 issue 追踪器也能用。
