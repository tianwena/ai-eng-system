# ADR 格式

ADR 存放在 `docs/adr/`，按顺序编号：`0001-slug.md`、`0002-slug.md`，依此类推。

**惰性创建** `docs/adr/` 目录——只有第一份 ADR 需要时才建。

## 模板

```md
# {决策的简短标题}

{1-3 句：背景是什么，我们决定了什么，为什么。}
```

就这些。一份 ADR 可以只有一个段落。价值在于记录**做过这个决策**以及**为什么**——不在于把各个小节填满。

## 可选小节

只在确实增加价值时才包含。大多数 ADR 用不上。

- **Status** frontmatter（`proposed | accepted | deprecated | superseded by ADR-NNNN`）—— 当决策会被重新审视时有用
- **Considered Options**（考虑过的选项）—— 只有当被否掉的替代方案值得记住时才写
- **Consequences**（后果）—— 只有当存在不明显的下游影响需要点明时才写

## 编号

扫一遍 `docs/adr/` 取现有最大编号，加一。

## 何时提议一份 ADR

以下三条必须**全部**成立：

1. **难以逆转** —— 以后改主意的成本是有分量的
2. **脱离上下文会令人意外** —— 未来的读者看着代码会想"他们到底为什么这么做？"
3. **是真实取舍的结果** —— 确实存在别的选项，而你出于具体理由选了这一个

如果一个决策很容易反悔，跳过——你直接改回来就行了。如果不令人意外，没人会问为什么。如果根本没有真正的替代方案，那除了"我们做了显而易见的事"之外没什么可记的。

### 什么算数

- **架构形态。** "我们用 monorepo。""写模型是事件溯源的，读模型投影进 Postgres。"
- **上下文之间的集成模式。** "Ordering 和 Billing 通过领域事件通信，而不是同步 HTTP。"
- **带锁定效应的技术选型。** 数据库、消息总线、认证服务商、部署目标。不是每个库——只是那些换掉要花一个季度的。
- **边界与范围决策。** "客户数据归 Customer 上下文所有；其他上下文只按 ID 引用它。" 明确说出的**不要什么**和**要什么**一样有价值。
- **对显而易见路径的有意偏离。** "我们用裸 SQL 而不用 ORM，因为 X。" 任何"合理的读者会假设是反的"的地方。这些能阻止下一个工程师去"修好"一个本来就是故意的设计。
- **代码里看不见的约束。** "因为合规要求我们不能用 AWS。""因为合作方 API 合同，响应时间必须在 200ms 以内。"
- **被否掉且否掉理由不明显的替代方案。** 如果你考虑过 GraphQL，出于微妙的原因选了 REST，记下来——否则半年后又会有人提议 GraphQL。
