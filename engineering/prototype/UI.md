# UI 原型（UI Prototype）

在**同一个路由**上生成**几个截然不同的 UI 变体**，通过一个悬浮底栏切换。用户在浏览器里来回翻转，挑一个（或者从每个里各偷一点），然后把其余的扔掉。

如果问题是关于逻辑/状态、而不是某东西长什么样——分支错了。用 [LOGIC.md](LOGIC.md)。

## 什么时候这是对的形状

- "这个页面该长什么样？"
- "定下来之前，我想看看这个 dashboard 的几种方案。"
- "给设置页试一个不同的布局。"
- 任何用户本来要在脑子里在三个模糊稿之间纠结一天的时候。

## 两个子形状——**强烈偏好子形状 A**

当一个 UI 原型**紧挨着 app 的其余部分**时，判断起来容易得多——真实的 header、真实的 sidebar、真实的数据、真实的密度。一个孤零零的一次性路由是真空：每个变体单看都还行。**只要有一个像样的既有页面能承载变体，就默认子形状 A。** 只有当原型确实没有附近的归宿时，才用子形状 B。

### 子形状 A —— 对既有页面的调整（首选）

路由已经存在。变体渲染在**同一个路由**上，由一个 `?variant=` URL 查询参数控制。现有的数据获取、参数和鉴权都保留——只换渲染。这是默认；除非有具体理由，都选它。

如果原型的对象还没有页面、但**天然会住在一个页面里**（dashboard 的一个新区块、设置页上的一张新卡片、既有流程里的一个新步骤）——那**仍然**是子形状 A。把变体挂载到宿主页面里。

### 子形状 B —— 新页面（最后手段）

只有当被做原型的东西确实没有可栖身的既有页面时才用它——例如一个全新的顶层界面，或一个没法嵌进任何合理位置的流程。

按项目已有的路由约定创建一个**一次性路由**——不要发明新的顶层结构。命名要明显是原型（例如路径或文件名里含 `prototype` 一词）。同样的 `?variant=` 模式。

在定下子形状 B 之前，先自我检查：**真的**没有既有页面能承载它吗？一个空路由会掩盖那些在内容充实的页面里会暴露出来的设计问题。

两个子形状里，悬浮底栏完全一样。

## 流程

### 1. 陈述问题并确定 N

默认 **3 个变体**。超过 5 个就不再是截然不同、而开始变成噪音——最多到 5。

把计划写成一行，放在原型的位置或文件顶部注释里：

> "设置页的三个变体，通过 `?variant=` 切换，落在既有的 `/settings` 路由上。"

无论用户此刻是否在场反驳，这都成立。

### 2. 生成截然不同的变体

草拟每个变体。每个都要守住：

- 页面的目的和它能访问的数据。
- 项目的组件库 / 样式体系（TailwindCSS、shadcn、MUI、纯 CSS，随便什么）。
- 一个清晰的导出组件名，例如 `VariantA`、`VariantB`、`VariantC`。

变体必须在**结构上不同**——不同的布局、不同的信息层次、不同的主要可供性，而不只是颜色不同。三张微调过的卡片网格不是 UI 原型，是壁纸。如果两份草稿出来太像，就用明确的"不要用卡片网格"重做其中一个。

### 3. 把它们接起来

在该路由上创建一个切换组件：

```tsx
// pseudo-code — adapt to the project's framework
const variant = searchParams.get('variant') ?? 'A';
return (
  <>
    {variant === 'A' && <VariantA {...data} />}
    {variant === 'B' && <VariantB {...data} />}
    {variant === 'C' && <VariantC {...data} />}
    <PrototypeSwitcher variants={['A','B','C']} current={variant} />
  </>
);
```

对子形状 A（既有页面）：把现有的数据获取全部保留在切换组件之上；每个变体只换渲染出来的子树。

对子形状 B（新页面）：`/prototype/<name>` 下的一次性路由挂载同一个切换组件。

### 4. 做悬浮切换器

屏幕底部居中一个小的固定定位条，由三部分组成：

- **左箭头** —— 循环到上一个变体（环绕）。
- **变体标签** —— 显示当前变体键，如果变体导出了名字，也显示那个名字。例如 `B — Sidebar layout`。
- **右箭头** —— 向前循环（环绕）。

行为：

- 点箭头更新 URL 查询参数（用框架的路由器——Next 上 `router.replace`、React Router 上 `navigate` 等），这样变体可分享、刷新后稳定。
- 键盘：`←` 和 `→` 方向键也能循环。当 `<input>`、`<textarea>` 或 `[contenteditable]` 获得焦点时，**不要**拦截方向键。
- 视觉上明显区别于页面（例如高对比药丸形 + 轻微阴影），让人一眼看出它不属于正在被评估的设计。
- 生产构建里隐藏——用 `process.env.NODE_ENV !== 'production'` 或等效检查兜住，这样即便有人误合了原型，这个条也不会送到用户面前。

把切换器放在一个共享组件里，让两个子形状都能复用。放在项目里共享 UI 所在的地方。

### 5. 交给他

把 URL（以及 `?variant=` 的键）给他。他方便时会翻着看。有意思的反馈通常是 **"我想要 B 的 header 配 C 的 sidebar"**——那才是他真正想要的设计。

### 6. 捕获答案并清理

一个变体胜出后，先捕获答案——哪个变体、为什么——再按 [SKILL](SKILL.md) 描述的方式捕获原型。把胜者折进真实代码，其余的移到一次性分支，不要进 main：

- **子形状 A** —— 把胜者折进既有页面；从 main 里删掉落选的变体和切换器。
- **子形状 B** —— 把胜出的变体提升为真实路由；从 main 里删掉一次性路由和切换器。

整套变体是一手来源，所以它落在一次性分支上，而不是垃圾桶里——留在 main 分支的变体组件和切换器烂得很快，会迷惑下一个读者。

## 反模式

- **只在颜色或文案上有区别的变体。** 那是微调，不是原型。真正的变体在**结构**上就不一致。
- **变体之间共享太多代码。** 共享一个 `<Header>` 没问题；共享一个 `<Layout>` 就毁了意义。每个变体都该能自由地扔掉布局。
- **把变体接到真实的写操作上。** 只读原型没问题。如果某个变体需要写，就指向一个桩——问题是"这该长什么样"，不是"后端通不通"。
- **把原型直接提升到生产。** 变体代码是在原型约束下写的（没有测试、最少的错误处理）。折进去的时候要**正式重写**。
