# 逻辑原型（Logic Prototype）

一个单文件、自包含的 HTML——一个**可分享的 demo**——让任何人通过点按钮来驱动一个状态模型。当问题是关于**业务逻辑、状态转移或数据形状**时用它——那种在纸上看着合理，只有推进到真实情形里才感觉出不对的东西。

因为它是单个文件、什么都不用装，你可以把它交给非开发者——设计师、PM、领域专家——让他们自己感受这个模型。所以它说的是**他们的语言**，不是代码的语言。

## 什么时候这是对的形状

- "我不确定这个状态机能不能处理先 X 再 Y 的边界情况。"
- "这个数据模型到底能不能表示……的那种情况？"
- "写之前我想先感觉一下这个 API 该长什么样。"
- 任何"有人想**按按钮、看状态变化**"的场景。

如果问题是"这个该长什么样"——分支错了。用 [UI.md](UI.md)。

## 流程

### 1. 陈述问题

写代码之前，先写下你在为哪个状态模型、哪个问题做原型。一段话，放在 demo 顶部（放在可见的引言里，不只是注释）。**一个回答错问题的逻辑原型是纯粹的浪费**——把问题显式写出来，以便日后核对，无论用户是现在看着还是离线回来再看。

### 2. 把逻辑隔离进一个可移植的模块

把真正的逻辑——回答那个问题的那部分——放进**一个** `<script>` 块，写成一个小的纯模块，**日后能整体拎出来直接丢进真实代码库**。它周围的页面是一次性的；**这个模块不是**。

对的形状取决于问题：

- **纯 reducer** —— `(state, action) => state`。当动作是离散事件、状态是单个值时好用。
- **状态机** —— 显式的状态与转移。当"此刻哪些动作合法"本身就是问题的一部分时好用。
- **一组作用于普通数据类型的纯函数**。当不存在隐式的当前状态、只有变换时好用。
- **一个有清晰方法面的类或模块** —— 当逻辑确实拥有持续的内部状态时。

选**最贴合所问问题**的形状，**不是**最容易接到页面上的形状。保持纯净：没有 DOM、没有 `document`、没有伸手进去的按钮处理器。页面调用它；没有东西朝反方向流。这正是让原型在自身生命周期之外仍然有用的原因：问题答完之后，被验证的 reducer / 状态机 / 函数集能自己拎进真实模块。

### 3. 构建可分享的 HTML 文件

一个文件，纯 HTML/CSS/JS——不用框架、不用打包器、不用服务器，所有东西内联，双击就能打开，也能通过邮件传来传去。**任何人打开它就能跑。**

**为非开发者写它。** 每个标签都用**领域语言**，不是代码——按钮和状态读起来像业务，而不是像 reducer。用平实的话解释正在发生什么。

用清晰的层次自上而下布局：

1. **标题 + 一行说明**这个 demo 让你探索什么（第 1 步的那个问题）。
2. **当前状态** —— 完整的相关状态，渲染成一个可读的面板（带标签的字段，不是裸 JSON dump），每次点击后重新渲染，让变化可见。哪里有助于非开发者跟得上，就点出刚刚变了什么。
3. **自由试玩按钮** —— 每个动作一个按钮，始终可用，这样任何人都能任意顺序戳这个模型。每次点击派发它的动作并重新渲染状态。
4. **引导式走查** —— 一组**场景**，一个标签一个。每个标签里有一段简短平实的场景描述——它设定了什么情形、要观察什么——下面是为该场景按顺序排列的**要按的按钮**。每一步都是真按钮：点击它就执行该动作并前进到下一步。启动一个走查会重置到已知的初始状态，所以场景每次都跑得一样。

挑选能展示尴尬情形的场景——happy path、刁钻的边界情况、一次本该非法的尝试——那些在纸上难以推理的。

**保持好看但克制**：干净的排版、慷慨的间距、一个强调色。不要动画、不要花招——任何与状态和按钮抢注意力的东西都不要。

### 4. 交给他

把文件发给他，或者帮他打开。他方便的时候会去点走查和自由试玩；有意思的时刻是他冒出"等等，这不该发生啊"或"咦，我以为 X 会不一样"的时候——**那些是"想法本身"里的 bug，而这正是全部意义**。如果他想要新动作或新场景，就加。**原型会演化。**

### 5. 捕获答案和原型

原型回答了它的问题之后，先捕获答案，再按 [SKILL](SKILL.md) 描述的方式捕获原型。逻辑分支特有的映射：被验证的 reducer / 状态机 / 函数集拎进真实模块（决策被吸收）；HTML 外壳跟着去那个保留原型作为一手来源的一次性分支——而因为它是单文件自包含的，在那里依然能轻松重跑。

## 反模式

- **不要加测试。** 一个需要测试的原型就不再是原型了。
- **不要接到真实数据库上。** 用内存状态，除非问题专门关于持久化。
- **不要通用化。** 不要"以后要是想支持 X 呢"。原型只回答一个问题。
- **不要把逻辑和页面搅在一起。** 如果那个纯模块引用了 DOM、`document` 或按钮处理器，它就不再可拎出。让页面做一个覆盖在纯模块之上的薄壳。
- **不要上框架、打包器或服务器。** 收件人双击的一个文件；一个 React app 或 dev server 就破坏了"可分享"。
- **不要把 HTML 外壳带进生产。** 这个页面是为"被人手点着玩"优化的。它背后那个逻辑模块才是值得留的部分。
