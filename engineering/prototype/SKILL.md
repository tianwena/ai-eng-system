# Prototype（原型）

原型是**回答一个问题的、一次性的代码**。**问题决定形状。**

## 先选分支

先确定正在回答的是哪个问题——从用户的提示、周边代码，或者直接问（如果用户在的话）：

- **"这个逻辑 / 状态模型感觉对吗？"** → [LOGIC.md](LOGIC.md)。做一个**单文件、可分享的 HTML**——自由试玩的按钮 + 分标签的引导式走查——把状态机推进到那些在纸上很难推理、且非开发者也能操作的情形。
- **"这个该长什么样？"** → [UI.md](UI.md)。在**同一个路由**上生成几个截然不同的 UI 变体，通过 URL 查询参数和一个悬浮底栏切换。

两个分支产出的东西差别很大——**选错分支会浪费掉整个原型**。如果问题确实含糊、又联系不上用户，就选更贴合周边代码的那个分支（后端模块 → 逻辑；页面或组件 → UI），并在原型顶部说明这个假设。

## 两者都适用的规则

1. **从第一天起就是一次性的，并且清楚标明。** 把原型代码放在它将来真正会被用到的位置附近（挨着它为之做原型的模块或页面），这样上下文一目了然——但命名要让随手翻到的人看出它是原型、不是生产代码。对一次性的 UI 路由，遵守项目已有的路由约定；不要发明新的顶层结构。
2. **跑起来要零门槛。** UI 原型从项目任务运行器的一条命令启动——`pnpm <name>`、`python <path>`、`bun <path>` 等。逻辑 demo 是用户双击就能开的单个 HTML 文件。无论哪种，启动时都不需要思考。
3. **默认无持久化。** 状态存在内存里。持久化是原型**正在检验**的东西，不是它该依赖的东西。如果问题明确涉及数据库，就打一个草稿 DB，或用一个名字带着明显"PROTOTYPE — wipe me"的本地文件。
4. **跳过打磨。** 不要测试、不要超出"能让原型跑起来"所需的错误处理、不要抽象。要点是**快速学到东西**。
5. **把状态显式呈现出来。** 每个动作之后（逻辑）或每次变体切换后（UI），打印或渲染完整的相关状态，让用户看到变了什么。
6. **做完就捕获它。** 把任何被验证的决策折进真实代码，然后把原型本身作为**一手来源**捕获下来：提交到一个从 main 分出的一次性分支上，并在实现用的 issue 上留一条指向该分支的上下文指针。**答案也要捕获**——结论以及它所解决的那个问题——记在 issue 或一次 commit 里。main 分支只保留被验证的决策。
