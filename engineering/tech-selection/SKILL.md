你在为**一个要活很久、且只有你维护**的商业系统选技术。评价标准和一个有 20 人团队的公司的选型**完全不同**。

---

## 一、四个评价标准（按重要性排序）

### 1. 无聊（Boring）—— 最重要

**选成熟、无聊、多年不变的技术。** 新技术带来的兴奋感，会在你半夜修 bug 时变成悔恨。

### 判据不是"年龄"，是"**稳定性证据**"

> ⚠️ **别把"至少 5 年"当硬门槛。** 那会一口气排除掉大量**已经足够成熟**的选择
> （很多主流框架/库的现代形态也就 2–4 年，但它们背后是 10 年积累的生态、且已被大规模验证）。
> **年龄是代理指标，别把它当门槛。**

真正要问的是**稳定性证据**：

| 问 | 为什么这么问 | 反例信号 |
|---|---|---|
| 有没有**大量**生产环境用户？ | 被你之外的人踩过坑，才是成熟 | 只有教程和 demo |
| 上一个 major 版本**破坏性变更**多不多？ | 频繁破坏 = 你会被迫跟着升级 | 每次大版本都要重写 |
| 维护者是谁？**单人还是团队/公司**？ | 单人维护的项目有"消失风险" | 半年没有提交/回复 issue |
| 有没有**长期支持（LTS）或明确版本策略**？ | 你能规划升级 | 版本号乱跳、无 changelog |
| 出问题时**搜得到答案**吗？ | 反馈回路速度 | 搜不到、只能读源码 |
| **退出成本**可控吗？（见第 4 节） | 真正成熟的东西迁得走 | 专有锁定 |

**经验的年龄下限**：**≥2 年且已过一整个大版本周期**（即它经历过一次 breaking change 并活下来）。
这比"5 年"更贴合真实风险——**你要的是"它扛过一次变革"，不是"它老"**。

**创新预算（Innovation Token）**：一个项目最多容忍 **1 个**新技术。其余全部选无聊的。
（比如：想用新语言 + 新数据库 + 新框架 + 新部署平台 = 你会花 80% 时间在胶水代码上。）
> 这条和上面的"稳定性证据"合起来才是完整判据：**允许 1 个新技术，但它必须仍然过得了上表。**

### 2. 一个人扛得住

- **托管优先，别自建。** 数据库用托管、认证用托管、支付用第三方、邮件用第三方。
  自建 Postgres 高可用、自建 auth、自建支付网关 = 你会变成运维而不是开发者。
- **一个仓库、一个部署单元**优先于微服务。**微服务是一个人做项目的自杀方式**——它把"改一个功能"变成"改三个服务 + 协调版本"。
- **类型安全优先**：静态类型能在 agent 写代码时抓住大量错误，反馈回路更短。这与 `tdd`/`diagnosing-bugs` 的"反馈速率"原则一致。
- **出错时有清晰报错**的技术，优于"魔法"多的技术。

### 3. 招得到人 / 问得到答案

- 遇到问题时，搜索引擎和社区里**有答案**吗？
- 未来要请人帮忙时，这个栈**好招人**吗？
- LLM 对这个栈**训练得充分**吗？（对小团队而言这是真实的生产力因素）

### 4. 迁得走（Exit Cost）

**问："如果这个服务明天涨价 10 倍或关门，我多久能换掉？"**

- 数据能不能导出成通用格式？（**必须能**）
- 有没有标准协议？（Postgres 协议、S3 API、SMTP、OpenID Connect）
- 专有 API 用得越深，迁出成本越高。
- **数据驻留（数据在哪、能不能不出境）** ← 对面向境内用户的商业项目是**法律门槛**，不只是技术偏好：
  - 能不能选**境内区域**？境外服务商有没有境内节点？
  - ⚠️ **调用境外大模型 API 处理用户数据，很可能触发"数据出境"合规问题**——
    这是 AI 产品最常踩的坑。选模型服务商时**把这条当硬约束**，不要等功能做完才发现。
  - 完整检查项见 `production-readiness` 的 **F3 数据出境**。

**优先选实现标准协议的东西**（如兼容 S3 的对象存储、兼容 Postgres 的数据库），而不是专有锁定。

## 二、决策流程

### 第 1 步：先写约束（不是先选技术）

```
【规模】现在多少用户？一年后现实预期多少？（别按"可能百万用户"设计）
【预算】每月能花多少钱？（含 API 调用）
【形态】Web / 桌面 / CLI / 移动？（先只做一个）
【你的熟悉度】哪些技术你已经会？（首选你会的，除非它明显错）
【数据敏感度】有没有合规/隐私要求？
【实时性】有没有必须实时/长连接的需求？
【离线】要不要能离线跑？
```

**红线**：约束里出现"以后可能会……"的东西，**一律划掉**。YAGNI 是小团队的生命线。

### 第 2 步：只选三件事（其余的都跟着定下来）

选技术栈时，真正要拍板的只有三个：

1. **语言 + 运行时**（以及它的后端框架）
   - 首选：**你会的** + 生态成熟 + 类型安全
   - 一个人做全栈的现实选择通常是：**一种语言贯穿前后端**（少一套心智负担、少一套构建）
2. **数据库**
   - 默认答案：**托管的关系型数据库**（Postgres 兼容）
   - 只有在有明确理由（图表关系、时序、超大规模全文检索）时才换
   - **一张表能解决的问题，不要引入 NoSQL**
3. **部署平台**
   - 你要的是**一条命令上线 + 能回滚**，不是"最强的平台"
   - 判据：**回滚要多久？** 超过 5 分钟的平台不要（见 `launch-and-ops`）

**其余（ORM、样式方案、测试框架、日志库）属于可逆选择——跟着上面三个走，不要开会讨论。**

### 第 3 步：算真实总成本（不是服务器账单）

```
月成本 = 服务器 + 数据库 + 对象存储 + 出口流量
        + 第三方 API（按预期用量 × 单价，要留 3 倍余量）
        + 托管服务订阅（认证/邮件/监控）
        + 域名/证书/短信
        + 【你】每月维护小时数 × 你的时薪      ← 最常被漏掉的一项
```

**必须做的敏感性分析**：如果用量涨 **10 倍**，账单涨多少？
- 线性的（如按量 API）→ 可控，但要设额度上限（见 `production-readiness`）。
- 有**断崖**的（如按席位/按连接数/出口流量）→ **危险**，要提前找替代方案。

### 第 4 步：写 ADR（不可逆决策必须落文件）

每个真正的决定写一份 `docs/adr/00XX-<标题>.md`：

```markdown
# ADR 0007：用托管 Postgres 而非自建

## 状态
已接受（2026-09-12）

## 背景
一个人维护，需要备份/恢复/升级都不占我时间。

## 考虑的选项
1. 托管 Postgres（¥XX/月）
2. 自建 Postgres on VPS（¥X/月，但要自己做备份/主从/升级）
3. SQLite + 定期快照（最省，但并发写和迁移能力受限）

## 决定
选 1。

## 理由
省下的运维时间价值远超差价；且 Postgres 协议标准，迁走成本低。

## 后果
- 好：零运维、自动备份、随时可迁
- 坏：月成本高 X 元；受制于该厂商的区域可用性
- 触发重新评估的条件：**月账单超过 ¥XXX**，或该厂商涨价 >50%

## 被否决的选项为什么不选
2：一个人做备份/主从恢复的出错概率太高，一次数据丢失就无法挽回。
3：并发写场景会退化，且未来迁移到 Postgres 要重写数据访问层。
```

> **ADR 在多 agent 团队里是硬需求**：没有它，第二个 agent 会**重新选一次技术栈**——因为它不知道你上次为什么这么选。

### 第 5 步：用一次性原型验证选型（不写产品代码）

有不确定的地方，用 `prototype` 做一个**一次性**验证：
- 性能：预期的数据量下，这个查询要多久？
- 集成：这个第三方 API 真的能完成我要的流程吗？
- 部署：这条链路真的能一条命令上线吗？

**原型明确声明为"一次性"**，绝不演变成产品代码。

## 三、常见选型陷阱

1. **拿"以后可能百万用户"来选型。** → 按现实规模设计，把扩展点留成**接口**而不是提前实现。
2. **微服务 / 过早拆分。** → 一个人做项目，单体 + 清晰模块边界（`codebase-design` 的深模块）几乎总是更优。
3. **自建认证。** → 认证的边界情况（找回、MFA、会话固定、暴力破解）足够写一个产品。用现成的。
4. **自建支付。** → 见 `payment-and-billing`。绝不自研支付逻辑。
5. **选没有退出路径的专有服务。** → 优先标准协议（Postgres / S3 / SMTP / OIDC）。
6. **用最新 major 版本。** → 等它活过一个版本周期。
7. **只看服务器账单。** → 加上你自己的维护时间；那通常是最贵的一项。
8. **不写 ADR。** → 三个月后你自己都不记得为什么，第二个 agent 更不知道。
9. **一个项目用四个新技术。** → 创新预算只有 1 个。
10. **忽略 LLM 训练充分度。** → agent 写不熟的栈会大量产出错误代码，你反而更慢。
