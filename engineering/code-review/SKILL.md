对 `HEAD` 与用户给出的固定点之间的 diff 做**双轴**审查：

- **标准轴（Standards）** —— 代码是否遵循本仓库成文的编码规范？
- **规格轴（Spec）** —— 代码是否忠实实现了来源 issue / spec？

两条轴都作为**并行子 agent** 运行，这样它们不会互相污染上下文，然后由本技能汇总它们的发现。

issue 追踪器应该已经提供给你了——如果 `docs/agents/issue-tracker.md` 缺失，先跑 `/setup-workspace-discipline`。

## 流程

### 1. 钉住固定点

用户说的就是固定点——一个 commit SHA、分支名、tag、`main`、`HEAD~5` 等。如果没说，问他。

把 diff 命令固定下来一次：`git diff <fixed-point>...HEAD`（三个点，所以是与 merge-base 比较）。也把提交列表记下来：`git log <fixed-point>..HEAD --oneline`。

在继续之前，先确认固定点能解析（`git rev-parse <fixed-point>`）且 diff 非空。坏的 ref 或空 diff 应该在这里失败——而不是在两个并行子 agent 内部失败。

### 2. 找出规格来源

按这个顺序找来源规格：

1. 提交信息里的 issue 引用（`#123`、`Closes #45`、GitLab `!67` 等）——用 `docs/agents/issue-tracker.md` 里的工作流取回。
2. 用户作为参数传进来的路径。
3. `docs/`、`specs/` 或 `.scratch/` 下与分支名或功能匹配的规格文件。
4. 如果什么都没找到，问用户规格在哪里。如果他说没有，**规格**子 agent 就跳过，并报告"没有可用的规格"。

### 3. 找出规范来源

仓库里任何记录了"代码该怎么写"的东西，例如 `CODING_STANDARDS.md` 或 `CONTRIBUTING.md`。

除了仓库成文的东西之外，标准轴**永远**携带下面的**坏味道基线**——一组固定的 Fowler 代码坏味道（《重构》第 3 章），即使仓库什么都没写也适用。两条规则约束它：

- **仓库优先。** 成文的仓库规范永远赢；它**认可**的东西如果被基线标记，就**抑制**那个坏味道。
- **永远是判断题。** 每个坏味道都是一个带标签的启发式（"可能的 Feature Envy"），永远不是硬性违规——而且和这里任何标准一样，工具已经强制的东西就跳过。

每个坏味道的读法是 *它是什么* → *怎么修*；拿它去匹配 diff：

- **神秘命名（Mysterious Name）** —— 一个函数、变量或类型的名字没有透露它做什么/装什么。→ 重命名；如果找不到诚实的名字，说明设计本身浑浊。
- **重复代码（Duplicated Code）** —— 同一个逻辑形状在这次变更的多个 hunk 或文件里出现。→ 抽出共享形状，两边都调它。
- **依恋情结（Feature Envy）** —— 一个方法伸手进另一个对象的数据，比用它自己的还多。→ 把方法搬到它所羡慕的数据上。
- **数据泥团（Data Clumps）** —— 同样的几个字段或参数总是一起旅行（一个想出生的类型）。→ 把它们捆成一个类型，传那个类型。
- **基本类型偏执（Primitive Obsession）** —— 用一个基本类型或字符串顶替一个值得拥有自己类型的领域概念。→ 给这个概念它自己的小类型。
- **重复的 switch（Repeated Switches）** —— 对同一类型的同一个 `switch`/`if` 级联在变更中反复出现。→ 换成多态，或两个地方共享的一张映射表。
- **霰弹式修改（Shotgun Surgery）** —— 一次逻辑改动迫使 diff 里许多文件零散地改。→ 把一起变的东西聚到一个模块里。
- **发散式变化（Divergent Change）** —— 一个文件或模块因为几个互不相关的原因被修改。→ 拆开，让每个模块只为**一个**原因而变。
- **夸夸其谈通用性（Speculative Generality）** —— 为规格并不存在的需求添加的抽象、参数或钩子。→ 删掉它；内联回去，直到真实需求出现。
- **过长的消息链（Message Chains）** —— 调用方不该依赖的长链 `a.b().c().d()`。→ 把这段行走藏到第一个对象的一个方法后面。
- **中间人（Middle Man）** —— 一个类或函数大部分只是往下转发。→ 砍掉它，直接调真正的目标。
- **被拒绝的遗赠（Refused Bequest）** —— 一个子类或实现者忽略或覆盖了它继承来的大部分东西。→ 放弃继承，改用组合。

### 4. 并行起两个子 agent

**标准轴子 agent 的提示词** —— 包含：

- 完整的 diff 命令和提交列表。
- 你在第 3 步找到的规范来源文件清单，**外加第 3 步的坏味道基线全文粘贴进去**——子 agent 没有别的途径拿到它。
- 简报："逐文件/hunk（相关处）报告：(a) diff 违反成文规范的每一处：引用该规范（文件 + 规则）；以及 (b) 你发现的任何基线坏味道：点名它并引用那个 hunk。区分硬性违规与判断题——成文规范的违反可以是硬的，但基线坏味道永远是判断题，且成文的仓库规范优先于基线。跳过工具已强制的东西。**400 字以内。**"

**规格轴子 agent 的提示词** —— 包含：

- diff 命令和提交列表。
- 规格的路径或已取回的内容。
- 简报："报告：(a) 规格要求但缺失或只做了部分的需求；(b) diff 里没有被要求的行为（范围蔓延）；(c) 看起来实现了、但实现看着不对的需求。每条发现都引用规格原文那一行。**400 字以内。**"

如果规格缺失，跳过规格子 agent，并在最终报告里注明这一点。

### 5. 汇总

把两份报告放在 `## Standards` 和 `## Spec` 标题下呈现，原样或轻度清理。**不要**合并或重新排序发现——两条轴是故意分开的（见《为什么是两条轴》）。

以一行摘要收尾：每条轴的发现总数，以及**每条轴内部**最严重的问题（如果有）。不要跨轴挑一个总冠军——那正是"分开"所防止的重新排序。

## 为什么是两条轴

一个变更可以通过一条轴而在另一条轴上失败：

- 代码遵循每一条规范，但实现了错误的东西 → **标准轴通过，规格轴失败。**
- 代码精确做了 issue 要求的事，但破坏了项目约定 → **规格轴通过，标准轴失败。**

分开汇报能防止一条轴掩盖另一条。
