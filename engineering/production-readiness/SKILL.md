你正在做**上线闸门**。任务不是让系统更好看，是让它**在真实世界的恶意输入、真实故障、真实账单下不倒**。

**核心纪律**：每一项都必须**有证据**。**没验证过的不许标"已完成"。**

---

## 零、先按档位选闸门（**别一上来做全审**）

本体系的核心铁规：**能自动化的闸门，就不要靠纪律。**
人（和 agent）在赶进度时一定会跳过手工检查——**让工具替你说"不"**。

### 先问一句：**这东西要给外人用吗？**

| 情形 | 跑什么 | 命令 |
|---|---|---|
| **自用 / 局域网演示 / 内部工具** | **技术红线审查**（4 项，秒级） | `powershell -NoProfile -ExecutionPolicy Bypass -File scripts/redline-check.ps1 -Project .` |
| **给真实外部用户用 / 要收费** | 红线 **+ 加固全审 + 质量闸门** | 红线 → `scripts/quality-gate.ps1` → 本技能下面 A–G 逐项闭环 |

```powershell
# 轻量：随时能跑，先过及格线
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/redline-check.ps1 -Project .

# 重装：给真人用之前
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/quality-gate.ps1 -Path . -IncludeTests -Json gate-report.json
```

> **为什么分两级**：加固全审（A–G 七个方面，逐项勾选、不许批量标绿）是给"有真实用户和账单"的系统准备的。
> 把它强加在自用项目上，结果是**没人跑**——而**一个没人跑的闸门等于没有闸门**。
> **红线回答"有没有踩线"；加固回答"敢不敢给真人用"。**

**加固全审的入口**（下面第二节起）：

```powershell
# 复制到项目：scripts/quality-gate.ps1
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/quality-gate.ps1 -Path . -IncludeTests -Json gate-report.json
```

它**零依赖即可运行**（只用 git / python / node），
专业工具（gitleaks / semgrep / pip-audit / ruff）**未装则自动 SKIP 并打印安装命令**——
不会因为"没装工具"而假装通过。退出码：`0` 通过 · `1` 有 FAIL · `2` strict 模式下有 SKIP。

**它的定位**：把本技能下面 A–G 中**能被机器判定的部分**一次性覆盖掉，
剩下的**必须人判**的部分才需要你逐项闭环（第一节）。

| 本技能的项 | 闸门脚本对应检查 | 还需人判吗 |
|---|---|---|
| A1 认证（哈希/强度/暴力破解） | — | ✅ **必须人判**（要看实现） |
| A2 授权（越权） | — | ✅ **必须人判**，且**越权测试要代码化**，不是"实测一次" |
| A3 输入与注入 | `C3` 危险模式扫描（eval/exec/shell=True/pickle/yaml.load） | 部分；边界校验仍需人判 |
| A4 密钥与配置 | `A1` `A2` `A3` `A4`（跟踪的敏感文件 / 硬编码凭证 / gitleaks / 忽略规则） | ❌ 机器可判 |
| A5 依赖与供应链 | `B1` `B2` `B3`（pip-audit / npm audit / 锁文件） | ❌ 机器可判 |
| B 数据（备份/恢复演练） | — | ✅ **必须人判**（且必须**真的做一次恢复**） |
| C 成本与滥用（额度硬上限） | — | ✅ **必须人判**（要改代码/配置） |
| D 可观测（日志/告警验证） | — | ✅ **必须人判**（告警必须**真的收到过一次**） |
| E 故障（超时/降级/回滚） | `D3` 运行手册存在性 | 部分；回滚必须**演练过** |
| F 合规 | — | ✅ **必须人判**（且需咨询专业人士） |
| G 部署 | `D2` CI 配置 / `D1` 环境示例 / `D3` 运行手册 | 部分 |

**接进 CI**：把 `scripts/quality-gate.workflow.yml` 复制成项目里的
`.github/workflows/quality-gate.yml`——这样**每次提交都自动跑**，而不是上线前才想起来。

> **红线的延伸**：如果某项被 SKIP（工具没装），**不许在报告里写"已覆盖"**。
> 要么装上工具让它真跑，要么在【未解决风险】里明写"该面未覆盖"。

## 一、执行方式：逐项闭环（不许跳、不许批量标绿）

> **只对上面表中"必须人判"的项做这一步**——机器能判的部分交给闸门脚本，别重复劳动。

对每一项，产出四个字段：

```
【现状证据】 我看到的是什么（命令输出 / 文件内容 / 实测结果）
【改动】     改了什么（没改就写"无需改动 + 理由"）
【验证方式】 怎么证明它现在是好的（可复现的命令或步骤）
【未解决风险】还有什么没覆盖（诚实写，别写"无"除非真的无）
```

**红线**：不写【现状证据】就标"已完成" = 造假。**宁可不做，不可假装做了。**

## 二、A. 安全

### A1 认证
- [ ] 密码用成熟库哈希（**不自研**）；有强度要求
- [ ] 暴力破解防护（失败次数限制 / 退避）
- [ ] 会话 token 足够随机；**登出后服务端真的失效**
- [ ] 找回密码流程不能被枚举用户（不管邮箱存不存在都返回同样的响应）
- [ ] 敏感操作要二次确认（改密码、改绑定、删账号）

### A2 授权（**最容易出事，逐端点过**）
- [ ] **每一个**端点都回答："这个请求凭什么访问这条数据？"
- [ ] 每条数据查询都带归属条件（`owner_id` / `tenant_id`）
- [ ] **越权测试**：用 A 用户的身份去请求 B 用户的数据，**必须失败**（实测，不是看代码）
- [ ] 权限判断在**服务端**（前端隐藏按钮不算控制）
- [ ] 管理接口有独立且更强的权限判断

### A3 输入与注入
- [ ] 所有入参在**边界处**校验（schema 校验 + 长度上限）
- [ ] 数据库查询**全部参数化**（不拼字符串）
- [ ] 文件上传：限制类型、限制大小、**不信任文件名**、存在不可执行的位置
- [ ] 渲染用户内容时转义（防 XSS）
- [ ] 出站请求防 SSRF（不许访问内网地址）
- [ ] 反序列化不信任外部数据

### A4 密钥与配置
- [ ] 密钥**不在**代码仓库里（检查 git 历史，不只是当前文件）
- [ ] `.env` 在 `.gitignore` 里（对齐工作区规范）
- [ ] 密钥**不回显**在日志/报错/回复里（对齐工作区规范）
- [ ] 生产密钥与测试密钥**分开**
- [ ] 有轮换密钥的方法（至少知道怎么换）

### A5 依赖与供应链
- [ ] 依赖漏洞扫描跑过，高危项处理（升级或说明为什么不能升）
- [ ] 锁文件提交了（构建可复现）
- [ ] 不再维护的依赖有替代计划

---

## 三、B. 数据（最不可逆的一类）

- [ ] **备份真的在跑**（不是"配了"——去看有没有成功的备份产物）
- [ ] **恢复演练做过**：从备份恢复到一个干净环境，数据完整
      > **没演练过的备份等于没有备份。** 这是本节唯一不可省的一项。
- [ ] 恢复目标明确：能丢多少数据（RPO）、能停多久（RTO）
- [ ] 迁移脚本有回滚路径，或显式标注不可回滚并准备了预案
- [ ] 删除操作：软删还是硬删已明确；级联影响已确认
- [ ] 有"误删恢复"的手段（至少：备份 + 明确的恢复步骤）
- [ ] 用户数据可导出（合规要求 + 客户信任）

---

## 四、C. 成本与滥用（一个人做项目最容易破产的地方）

- [ ] **每个花钱的外部调用都有硬额度上限**（在服务商侧也设）
      > 一个死循环、一次爬虫、一个 bug 就能在几小时内烧掉几个月预算。
- [ ] 限流：按用户 + 按 IP；登录、注册、发信、AI 调用**必须**限流
- [ ] 单次请求的资源上限（超大 payload、超长输入、超深递归）
- [ ] 有**支出告警**（云账单/API 用量到阈值就通知）
- [ ] 10 倍用量敏感性算过，有断崖的收费模式已识别
- [ ] 免费层/试用层不会被人刷爆

---

## 五、D. 可观测（出事时你能不能定位）

- [ ] **结构化日志**（不是 `print`）：带请求 id、用户 id、耗时、结果
- [ ] **不记录敏感数据**（密码、token、卡号、身份证）
- [ ] 关键业务动作有日志（注册、付款、额度扣减、权限变更）
- [ ] 健康检查端点（能区分"进程活着"和"依赖可用"）
- [ ] 至少有几个核心指标（QPS、错误率、延迟、队列积压）
- [ ] **告警真的会通知到你**（测试过一次：故意触发，确认收到）
- [ ] 错误上报（异常有堆栈、有上下文，且能去重）

---

## 六、E. 故障与韧性

- [ ] **所有外部调用有超时**（对齐工作区铁律"严禁无限等待"）
- [ ] 重试只对幂等操作，带退避 + 抖动
- [ ] 降级行为**显式标注**（对齐工作区铁律"失败降级要显式标注，不得虚构数据"）
- [ ] 启动时依赖不可用：能起得来并给出明确错误（不是静默半死）
- [ ] **回滚方案存在且演练过**：发布失败几分钟内能回到上一版
- [ ] 数据库连接用完归还（对齐工作区坑位 #1：连接泄漏）
- [ ] 资源泄漏检查（文件句柄、连接、后台任务）
- [ ] 时钟/时区处理正确（全 UTC 存，展示时转换）

## 七、F. 合规与法律（**必须由人决定，agent 只列问题**）

> ⚠️ **先确定法域，再看条款——法域搞错，后面全白做。**
> 本体系面向中文使用者，**默认法域是中国大陆**。若你的客户在境外（尤其欧盟/英国），
> 需要**另外**满足 GDPR 等当地法规——**两套可能同时适用**。

### F0 先回答：向谁提供服务？

| 情形 | 适用的主要法规（**需专业人士确认**） |
|---|---|
| 主体在中国大陆、客户也在中国大陆 | **《个人信息保护法》（PIPL）**、**《数据安全法》**、**《网络安全法》** |
| 主体在中国大陆、**客户在境外** | 上述 **+** 客户所在地法规；**且触发"数据出境"问题（见 F3）** |
| 主体在境外、客户在欧盟/英国 | **GDPR / UK GDPR**（告知同意、DPO、数据主体权利、跨境传输） |
| 面向未成年人 / 医疗 / 金融 | **额外前置审批或资质**——**不要靠猜，先咨询专业人士** |

### F1 通用（各法域都要有）

- [ ] 隐私政策 + 服务条款存在且**与实际行为一致**（**写了就要做到**——写了没做比不写更糟）
- [ ] 收集了什么数据、为什么、存多久——**有清单**（能把"我们收了什么"一页说清）
- [ ] 账号**删除权**：能不能真的把一个人的数据删干净？（含备份里的、日志里的、第三方那儿的）
- [ ] 数据**可导出**（客户要带走自己的数据时能提供）
- [ ] 退款条款、取消条款明确（见 `payment-and-billing`）
- [ ] 面向**消费者** vs 面向**企业**，规则不同（消费者保护更严）

### F2 中国大陆（PIPL / 数据安全法）

- [ ] **告知—同意**：收集前明确告知目的/方式/范围，并取得同意
- [ ] **最小必要**：只收实现功能所必需的数据（**这直接约束你的埋点设计** → 见 `growth-and-analytics`）
- [ ] **单独同意**：敏感个人信息（生物识别、行踪、医疗、金融账户等）需**单独**同意，不能混在总条款里
- [ ] 处理敏感个人信息 → 需**个人信息保护影响评估**
- [ ] 与其他处理者共享/委托处理 → 明确约定并告知
- [ ] 隐私政策的**中文版本**（面向境内用户时）
- [ ] 面向企业的**发票**要求（数电发票 / 开票系统对接——见 `payment-and-billing`）

### F3 数据出境（**跨境 SaaS 的第一道法律门槛，最容易被漏**）

- [ ] **判断是否构成"出境"**：数据传到境外服务器、境外第三方 API（**含大模型 API！**）都可能构成
- [ ] 若构成 → 评估适用路径：**安全评估 / 标准合同 / 认证**（三者适用条件不同，**必须咨询专业人士**）
- [ ] 选服务商时把这条纳入考量：**优先能境内落地的**（→ 见 `tech-selection` 的"迁得走"）
- [ ] ⚠️ **调用境外大模型 API 处理用户数据，很可能触发出境合规问题**——这是 AI 产品最常踩的坑

### F4 面向欧盟/英国（GDPR，仅当适用）

- [ ] Cookie / 追踪的告知与同意（**同意前不得加载非必要 Cookie**）
- [ ] 数据主体权利：访问、更正、删除、可携带、反对自动化决策
- [ ] 数据处理的法律依据（同意 / 合同履行 / 正当利益）——**必须选一条并说得出理由**
- [ ] 跨境传输机制（充分性认定 / SCC）
- [ ] 是否需要 DPO（数据保护官）

> **你（agent）的职责边界**：列出"需要用户决定的问题清单"，**不给法律结论**。
> 上表是**检查项**，不是法律意见——**具体条款请咨询专业人士**。
> 但**漏掉整个法域**（例如只提 GDPR 却对大陆客户不提 PIPL）是**实质缺陷**，不是"不够细"。

- [ ] 生产/暂存环境分离；暂存环境能反映真实配置
- [ ] 域名、HTTPS 证书、自动续期
- [ ] 静态资源/构建产物有版本（能回退）

## 九、输出：加固报告

```markdown
# 上线加固报告 — <项目> — <日期>

## 结论
可以上线 / 有条件上线（列出条件） / 不可上线（列出阻断项）

## 逐项结果
| 编号 | 项目 | 状态 | 现状证据 | 改动 | 验证方式 | 未解决风险 |
|---|---|---|---|---|---|---|
| A2 | 授权 | ✅ | 逐端点核对 + 越权实测通过 | 加了 owner 过滤 | `pytest test_authz.py` 全绿 | 管理后台未测 |
| C3 | 额度上限 | ⚠️ | 无上限 | 加了日限额 10万次 | 单测 + 实测触发 | 未在服务商侧设 |

## 阻断项（必须解决才能上线）
1. ...

## 有条件上线
条件：<...>  负责人：<人>  期限：<...>

## 上线后 24 小时重点观察
- <指标> / <日志> / <告警>
```

**状态只能是三种**：✅ 已闭环（有验证）／⚠️ 部分（写明差什么）／❌ 未做。
**不许**出现"应该没问题"。

## 十、反模式清单

1. **不演练恢复就信备份。** → 出事时才发现备份是空的/坏的。
2. **只在前端做权限。** → 直接调 API 就拿到别人的数据。
3. **外部调用没超时。** → 一个慢依赖拖死整个服务。
4. **没有额度硬上限。** → 一次 bug 烧掉几个月预算。
5. **告警没验证过。** → 告警发到一个没人看的渠道 = 没有告警。
6. **降级时返回假数据。** → 比报错更危险（对齐工作区铁律）。
7. **"本地测过了"当加固完成。** → 生产环境的配置/密钥/网络都不同。
8. **一次全做完再验证。** → 违反 `tdd` 的**垂直切片**纪律（一小环一小环）。**按 A→G 一节一节过，每节验证。**
9. **把合规判断交给 agent。** → 只列问题，人来决定并咨询专业人士。
10. **没验证就标 ✅。** → 这份报告就失去意义，等于没做。
