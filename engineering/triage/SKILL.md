# Triage（分诊）

让项目 issue 追踪器上的 issue 走一遍小型的分诊角色状态机。

如果本仓库把外部 pull request 当作一个请求面（见 issue-tracker 配置），分诊也覆盖它们：**一个 PR 就是"带着代码的 issue"**——同样的角色、同样的状态、同样的状态机，只是下面标注"for a PR"的地方有几处差异。按追踪器配置把裸的 `#42` 解析成 issue 或 PR。

分诊期间发到 issue 追踪器上的每条评论或 issue **必须**以这段免责声明开头：

```
> *This was generated by AI during triage.*
```

（中文：本条内容由 AI 在分诊过程中生成。）

## 参考文档

- [AGENT-BRIEF.md](AGENT-BRIEF.md) —— 怎么写耐用的 agent 简报
- [OUT-OF-SCOPE.md](OUT-OF-SCOPE.md) —— `.out-of-scope/` 知识库怎么运作

## 角色

两个**分类（category）**角色：

- `bug` —— 有东西坏了
- `enhancement` —— 新功能或改进

五个**状态（state）**角色：

- `needs-triage` —— 维护者需要评估
- `needs-info` —— 等待报告者提供更多信息
- `ready-for-agent` —— 已完整规格化，可供离线 agent 接手
- `ready-for-human` —— 需要人来实现
- `wontfix` —— 不会处理

对一个 PR，同样的状态要**针对附带的代码**来读：`ready-for-agent` 意味着已附上简报、应当由 agent 在现有 diff 上做下一步；`ready-for-human` 意味着已经可以由人合并。

每个分诊过的 issue 应当恰好带一个分类角色和一个状态角色。如果状态角色互相冲突，指出来，并在做任何事之前先问维护者。

这些是规范角色名——issue 追踪器里实际使用的标签字符串可能不同。映射关系应该已经提供给你了——如果没有，先跑 `/setup-workspace-discipline`。

状态转移：一个未打标签的 issue 通常先进 `needs-triage`；从那里转到 `needs-info`、`ready-for-agent`、`ready-for-human` 或 `wontfix`。报告者回复后，`needs-info` 回到 `needs-triage`。维护者可以随时覆盖——遇到看起来不寻常的转移，先指出来并询问，再继续。

## 调用方式

维护者调用 `/triage`，用自然语言描述他想要什么。理解请求并执行。例如：

- "给我看所有需要我关注的东西"
- "我们看看 #42"（issue 或 PR）
- "把 #42 移到 ready-for-agent"
- "有什么已经准备好让 agent 接手了？"

## 展示需要关注的东西

查询 issue 追踪器，呈现三个桶，最旧的在前：

1. **未打标签** —— 从未分诊过。
2. **`needs-triage`** —— 评估进行中。
3. **`needs-info`，且自上次分诊记录以来报告者有活动** —— 需要重新评估。

当 PR 在范围内时，把这些外部 PR 也纳入这三个桶，并给每行打上 `[PR]` 或 `[issue]` 标记。发现（discovery）只浮出*外部* PR（谁算外部由追踪器配置定义）——协作者正在进行的 PR 不是分诊工作。这个过滤只用于发现；**被点名指出的 PR 无论作者是谁都要分诊**。

显示数量，以及每个条目一行摘要。让维护者挑。

## 分诊一个具体的 issue 或 PR

1. **收集上下文。** 读完整的 issue 或 PR（正文、评论、标签、作者、日期；对 PR 还要读 diff）。解析任何过往的分诊记录，以免重复问已解决的问题。用项目的领域术语表探索代码库，尊重该区域的 ADR。对代码库跑两项检查：
   (a) **冗余** —— 按**领域概念**（不只是请求的措辞）搜索该行为是否已有实现，并报告你搜过哪里。如果找到了，它就是"已实现"的 `wontfix`（见第 5 步）。
   (b) **前置否决** —— 读 `.out-of-scope/*.md`，把任何与本次请求相似的条目摆出来。

2. **推荐。** 把你的分类和状态建议连同理由告诉维护者，再加上与该请求相关的简要代码库概览——包括它是否已经实现。等指示。

3. **验证主张。** 在任何逼问之前，先确认这个主张站得住脚。对 bug，按报告者的步骤复现。对 PR，确认 diff 做了它声称的事——检出它，跑相关测试或命令。报告结果：已确认（附代码路径）、失败，或细节不足（这是强 `needs-info` 信号）。**已确认的验证**能写出强得多的 agent 简报。

4. **逼问（如需要）。** 如果请求需要充实，把 `/grilling` 和 `/domain-modeling` 技能合起来跑——一轮问题一轮问题地逼它成形，磨砺领域术语，在决策落地时内联更新 `CONTEXT.md`/ADR。

5. **应用结果：**
   - `ready-for-agent` —— 发一条 agent 简报评论（[AGENT-BRIEF.md](AGENT-BRIEF.md)）。
   - `ready-for-human` —— 结构与 agent 简报相同，但注明为什么不能外包（需要判断的地方、外部访问、设计决策、手工测试）。
   - `needs-info` —— 发分诊记录（模板见下）。
   - `wontfix` —— 关闭，评论内容取决于*为什么*：
     - **已实现** —— 这个变更在代码库里已经存在。指出它在哪里；**不要**写进 `.out-of-scope/`（那个知识库是给**被否决的**请求用的，不是给已建成的功能）。
     - **被否决（bug）** —— 礼貌解释，然后关闭。
     - **被否决（enhancement）** —— 写进 `.out-of-scope/`，从评论里链接过去，然后关闭（[OUT-OF-SCOPE.md](OUT-OF-SCOPE.md)）。
   - `needs-triage` —— 应用该角色。如果已有部分进展，可选地留一条评论。

## 快速状态覆盖

如果维护者说"把 #42 移到 ready-for-agent"，相信他，直接应用该角色。先确认你即将做的事（角色变更、评论、关闭），然后执行。跳过逼问。如果在没有逼问会话的情况下移到 `ready-for-agent`，问一句他是否想写 agent 简报。

## Needs-info 模板

```markdown
## Triage Notes

**What we've established so far:**

- point 1
- point 2

**What we still need from you (@reporter):**

- question 1
- question 2
```

把逼问期间解决的一切都记到 "established so far" 下面，这样工作不会丢。问题必须具体、可执行，不能是"请提供更多信息"。

## 恢复上一次会话

如果该 issue 或 PR 上已有分诊记录，先读它们，检查报告者是否已回答了任何悬而未决的问题，呈现更新后的画面再继续。不要重复问已解决的问题。
