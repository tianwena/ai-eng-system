你在把系统**发布出去并让它活着**。判据只有一条：**出问题时你能多快恢复。**

---

## 一、上线前的三个"必须能"（缺一不可上线）

```
1. 能用一条命令部署（不是十几个手工步骤）
2. 能在 5 分钟内把【代码】回滚到上一个可用版本
3. 能在出事时知道出事了（告警验证过，不是"配了"）
```

**第 2 条是核心。** 只要回滚足够快，**发布就不再是高风险动作**——你可以小步快跑。
回滚慢的系统会让人不敢发布，于是攒大版本，于是发布越来越危险。

### ⚠️ "5 分钟"只对**代码**成立，对**数据库**不成立——这不是文字游戏

带 schema 变更的发布，**回滚承诺必须分开写**，否则你会承诺一个做不到的事：

| 变更类型 | 回滚目标 | 真实做法 |
|---|---|---|
| **只有代码**（无 schema 变更） | **≤5 分钟**（切回上一个构建产物 / 关特性开关） | 整体替换 + 快速回滚 |
| **带 schema 变更** | **不靠"回滚"，靠"向前兼容的发布序列"** | **expand–contract 三步走**（见第五节）：加新列 → 双写回填 → 切读删旧列。**每步都是一个独立的、可停可退的发布点** |

**为什么不能对 schema 承诺 5 分钟**：

- **删列 / 改类型** 天然不可逆——除非你有备份，而恢复备份远超 5 分钟
- 强行"回滚"一个已经跑过的数据迁移，会造出**新旧代码都能读到但语义不同**的数据（比不滚更糟）

**所以正确的纪律是**：

```
拆发布 → 让每一步都只做"可逆的一小步" → 于是你根本不需要"回滚 schema"，只需要"停在当前步"
```

> 这条与第五节的数据库变更三步走是**同一件事的两面**：**第 2 条的"5 分钟"是给代码的承诺；
> schema 的安全保障来自发布序列的设计，不来自回滚速度。**

## 二、环境与配置

| 环境 | 用途 | 要求 |
|---|---|---|
| **本地** | 开发 | 数据是假的；能一键起 |
| **暂存（staging）** | 上线前验证 | **配置与生产尽量一致**（差异处必须列出来） |
| **生产** | 真实用户 | 只从流水线部署，不手工改 |

**配置纪律**：
- 配置来自**环境变量**，不硬编码、不打包进产物。
- **密钥不进仓库**（检查 git 历史，不只是当前文件）。
- 生产密钥与测试密钥分开。
- 有 `.env.example` 说明需要哪些变量（不含真实值）。
- 有轮换密钥的步骤（至少写进 runbook）。

**反模式**：手工 SSH 上去改文件。那会让"这个环境到底是什么状态"变成不可知，回滚也无从谈起。

## 三、部署流水线（最少但要够）

```
提交 → 装依赖（锁文件） → 跑测试（必须全绿） → 构建 → 部署 → 冒烟检查 → 完成
                                                              ↓ 失败
                                                          自动回滚
```

**必须有的**：
- [ ] 测试不过就**不许部署**（这是测试唯一真正发挥威力的地方）
- [ ] 构建产物**有版本号/commit 标记**（出事时知道线上跑的是哪个版本）
- [ ] 部署后跑**冒烟检查**（健康端点 + 一条核心链路）
- [ ] 冒烟失败**自动回滚**或**立即告警**
- [ ] 部署有日志且能追溯到人/时间

**可以后加的**：多环境矩阵、蓝绿、金丝雀、特性开关。**先有可回滚，再谈高级策略。**

## 四、发布策略

| 策略 | 适合 | 说明 |
|---|---|---|
| **整体替换 + 回滚** | 一开始就用这个 | 简单、够用；靠快速回滚兜底 |
| **滚动发布** | 多实例 | 一个个人项目通常不需要 |
| **蓝绿** | 不能有停机时 | 成本翻倍，先别上 |
| **金丝雀** | 有流量能分流时 | 需要监控能力配套 |
| **特性开关（feature flag）** | 想把"部署"和"发布"分开 | **对小团队性价比最高** |

**特性开关为什么值**：它让你能**先部署代码（开关关着）再决定何时对用户开放**，出问题只需关开关，**不用回滚部署**。这是风险最低的方式。

**数据库变更与代码发布的关系（最容易出事）**：
```
❌ 一次性：改 schema + 改代码 + 同时部署
✅ 分三步：① 加新列（兼容旧代码）→ 部署
          ② 双写/回填 → 部署
          ③ 切读、删旧列 → 部署
```
**永远让新旧代码能同时跑**（因为部署过程中它们真的会同时跑）。

## 五、监控与告警（三级）

```
① 能知道活着吗    健康检查端点（区分：进程活着 / 依赖可用）
② 能知道跑得好吗  核心指标：请求量、错误率、延迟、队列积压、核心业务动作数
③ 能知道出事了吗  告警（错误率突增、延迟突增、任务堆积、额度异常、支出异常）
```

**告警纪律**（否则告警会变成噪音而被忽略）：
- **可执行**：每条告警都要有对应的"我该做什么"（写进 runbook）
- **有阈值和抑制**：避免一次故障刷 500 条
- **分级**：叫醒你的（P1）vs 明天看的（P3）——**别把所有事都设成叫醒**
- **必须验证过**：故意触发一次，确认你真的收到

**日志**：结构化、带请求 id、**不记敏感数据**、有保留期（日志也会花钱）。

## 六、备份与恢复

- **备份**：自动、定期、**异地**（不要和主库同盘同机房）
- **保留策略**：按 RPO 决定（能丢多少数据）
- **【必做】恢复演练**：从备份恢复到干净环境，验证数据完整
  > 没演练过的备份等于没有备份。
- **恢复步骤写进 runbook**，并标明耗时（RTO）

## 七、事故响应（出事时照这个做，别临场发挥）

```
1. 先止血，再找因
   → 回滚 / 关开关 / 扩容 / 限流。**用户的痛先解决，根因随后。**
2. 有人负责（一个人也要明确"现在是我在处理"）
3. 记录时间线（什么时候发现、做了什么、什么时候恢复）
4. 保留证据（日志、快照）——别急着清理
5. 恢复后：写复盘（不追责，只找机制缺口）
6. 补上"下次能更早发现"的告警 + "下次不用想"的 runbook 步骤
```

**反模式**：出事时直接在生产上边查边改（现场越来越乱）。**能回滚就先回滚**，然后在本地慢慢查。

## 八、运行手册（runbook）—— 必须存在

用 `wizard` 技能生成一个交互式脚本更好。至少包含：

```
【日常】
  - 怎么部署
  - 怎么查看日志 / 指标
  - 怎么进数据库（只读方式）

【故障】
  - 怎么回滚（步骤 + 预计耗时）
  - 怎么恢复备份（步骤 + 预计耗时 + 会丢什么）
  - 怎么重启服务 / 扩容
  - 常见告警 → 对应处理动作（每条告警都要有）

【变更】
  - 怎么加环境变量 / 轮换密钥
  - 怎么改域名 / 证书
  - 怎么加一个外部服务

【联系人】
  - 云厂商支持 / 支付服务商支持 / 域名商（各留入口）
```

## 九、上线当天检查清单

```
上线前（T-1天）
  □ 加固报告里的阻断项已全部闭环（见 production-readiness）
  □ 备份在跑 + 恢复演练做过
  □ 回滚演练过（真的演练，不是"应该可以"）
  □ 告警验证过（真的收到通知）
  □ runbook 写完且能照着做
  □ 支出告警已设
  □ 域名/证书有效且自动续期

上线时
  □ 用流水线部署（不手工）
  □ 冒烟检查通过
  □ 核心链路亲手走一遍（登录 → 主流程 → 付款/核心动作）

上线后 24 小时
  □ 盯：错误率、延迟、额度消耗、支出、用户反馈渠道
  □ 确认日志/告警在正常工作
  □ 记录第一天的真实问题（这是下一轮工作的输入）
```

## 十、反模式清单

1. **手工部署。** → 状态不可知，回滚无从下手。
2. **不能回滚就发布。** → 发布变成高风险动作，于是你不敢发布。
3. **测试不过也部署。** → 测试就白写了。
4. **换库和换代码一次做完。** → 部署中间态必炸。
5. **告警没验证。** → 发到没人看的渠道 = 没有告警。
6. **出事时先找根因再止血。** → 用户多痛半小时。
7. **没演练过恢复。** → 备份是心理安慰。
8. **日志记敏感数据。** → 日志泄露 = 数据泄露。
9. **没有 runbook。** → 半夜出事的你（或接手的 agent）会从零开始想。
10. **一次上齐所有高级发布策略。** → 先要"可回滚"，再谈金丝雀。
