**钱是唯一不能出错的模块。** 出错的代价不是 bug，是**客户信任 + 法律风险**。

---

## 一、三条绝对铁规

1. **绝不自研支付逻辑。** 卡号、3D Secure、风控、PCI 合规——**一律交给支付服务商**。你的系统永远不接触卡号。
2. **Webhook 是**唯一**的付款事实来源。** 前端回调不可信（用户能伪造），跳转成功页不可信（网络会断）。**只有服务端收到的、验签过的 webhook 才算数。**
3. **一切幂等。** Webhook 会**重发**（这是正常行为，不是异常）。同一个事件处理两次，结果必须和处理一次相同。

## 二、选支付服务商

先问清这些约束（**这些是人做的商业决策**）：

| 约束 | 影响 |
|---|---|
| **收款主体在哪** | 决定可选服务商（境内主体 vs 境外主体差异极大） |
| **客户在哪** | 境内客户 vs 全球客户，支持的支付方式不同 |
| **要不要开发票** | 境内面向企业基本必须；影响是否需要额外系统 |
| **结算周期** | 钱多久到你账上（影响现金流，尤其早期） |
| **费率** | **境内与境外结构不同，别混用一套算式**（见下表）；**小额交易时固定费占比极高** |
| **是否支持订阅/自动扣款** | 不是所有服务商都支持 |
| **是否支持按量计费** | 支持的话省一套计量系统 |

**落地要点**：
- 把服务商**包在一个接口后面**（`PaymentProvider`），业务代码不直接依赖它的 SDK。
  理由：① 换服务商是真实需求；② 测试时能换成假实现（**这是能测支付的关键**）。
- **费率进单位经济账**（见 `pricing-and-monetization`）。**别按一个想当然的百分比算**——见下表。

### 费率结构：境内 vs 境外（**结构不同，算式也不同**）

| 场景 | 典型结构 | 对小额/大额的影响 |
|---|---|---|
| **境内**（微信支付 / 支付宝 / 银联等） | **纯百分比**（量级约 0.6% 上下，按行业与资质浮动） | 小额与大额的**费率相同**，成本随金额线性 |
| **境外**（Stripe 等国际收单） | **百分比 + 每笔固定费**（如 2.9% + 固定金额） | **小额订单被固定费吃掉比例极高**（一笔 1 元的单可能费率超过 30%） |

**三条推论（直接进你的定价模型）**：

1. **面向境内客户的定价，不要按"3%+固定费"算成本**——那会高估成本、把价格定虚高。
2. **面向境外或全球客户，且客单价低**（比如按量计费的小额扣款）→ **固定费会杀死毛利**，
   这时应改成**预充值/额度包**（一次大额扣款摊薄固定费），而不是每笔小额扣。
3. **费率一定要用服务商当时的真实报价**，别抄本文的量级——它是**举例说明结构差异**，不是报价。

## 三、订阅状态机（最容易写错的地方）

**不要自己发明状态。** 把服务商的状态映射到你自己的状态，并**明确定义每个状态的权限**：

```
trialing   试用中        → 有权限（可限额度）
active     正常付费      → 有权限
past_due   扣款失败      → **宽限期内仍有权限**（这是关键决定）
canceled   已取消        → 当期结束前仍有权限，之后无权限
expired    已过期        → 无权限（数据保留，可恢复）
paused     暂停          → 无权限（数据保留）
```

### 必须显式决定的三件事（系统会长出未定义状态，如果你不决定）

1. **扣款失败怎么办？**
   标准做法：失败 → `past_due` → **宽限期（3~7 天）内重试** → 仍未成功 → 降级。
   **红线**：不要**立刻**断权限（会误伤正常的卡过期用户）；也不要**永远**不断（你会被白用）。
2. **取消是立即生效还是当期结束生效？**
   推荐**当期结束**（客户已付钱）。但要在界面上**说清楚是哪天**。
3. **降级/升级怎么算钱？**
   升级通常按比例补差（proration）；降级通常下期生效。**无论选哪种，都要在界面上显示金额。**

### 权限判定的唯一方式

```
canAccess(user) = 查用户当前订阅状态是否在"有权限集合"内
```

**不要**用"付款成功时间 + 30 天"这种**算出来的**过期时间——时钟、重试、时区都会让它出错。
**以状态为准，不以时间推算为准。**

## 四、Webhook 处理（照这个模板写）

```
1. 验签（用服务商的密钥；验不过直接拒绝）
2. 取事件 id
3. 幂等检查：这个事件 id 处理过吗？→ 处理过就直接返回 200
4. 【关键】先把事件**存表**（原始 payload + 收到时间），再处理
5. 更新本地状态（订阅状态 / 订单 / 额度）
6. 记录：谁、什么事件、改了什么、什么时候
7. 返回 200
```

**为什么第 4 步要"先存再处理"**：
- 出问题时你**有原始证据**（否则只能求服务商后台翻记录）
- 可以**重放**（修好 bug 后重新处理历史事件）
- 可以看到"服务商发了什么"和"我以为发了什么"的差异

**必须处理的现实**：

- **乱序**：事件可能**不是按发生顺序**到达的（用户快速连点、服务商重试、网络抖动都会导致）。
  **规则必须写死，不能停在"比较一下"**：

  ```
  判定顺序的唯一依据：服务商的 event.created（事件**发生**时间），不是收到时间、不是你的本地时间。
  规则：last-writer-wins —— 若新事件的 event.created **早于**该对象已记录的 event.created，则**丢弃**（记日志，不应用）。

  三个必须做对的细节：
  ① 【先落库再比较】把"该对象当前最新的 event.created"持久化（或直接用带版本号的字段做乐观锁），
     不要拿内存里的值比——进程重启就丢，且并发下会互相覆盖。
  ② 【别用 arrived_at 比】到达时间在乱序场景下就是错的依据。
  ③ 【未知事件类型要优雅忽略】服务商随时会加新事件类型，别让它把你的处理打崩。
  ```

  > **为什么这条值得单独写**：Stripe 一类的 `Subscription.updated` 乱序是**经典事故源**——
  > 一个几秒前的旧事件后到，就会把"已升级"覆盖回"未升级"，而且你事后很难看出来。

- **重复**：同一事件多次到达（**这是正常行为，不是异常**）。幂等键 = 事件 id；处理过就直接返回 200。
- **丢失/失败**：返回非 200 会被重试；处理失败**不要在事务里静默吞掉**（对齐工作区规范"禁止用兜底/超时/吞异常当修复"）。
- **延迟**：webhook 可能几分钟后才到。前端要能显示"处理中"，别让用户以为没成功而重复付款。

## 五、额度与用量计费

如果按量收费（AI 调用、存储、短信——**边际成本不为零的东西**）：

```
1. 计量：每次消耗记一条流水（谁、什么时候、用了多少、关联什么业务对象）
2. 扣减：从余额/额度扣（幂等！同一个业务操作不能扣两次）
3. 阈值告警：80% 提醒用户，100% 按约定处理（拒绝或超额计费）
4. 硬上限：**必须有**，防止一个 bug 或一次攻击让你破产（见 production-readiness）
5. 对账：每日核对"我方计量总额" vs "服务商账单"，差异要能解释
```

**红线**：
- **计量流水只增不改**（要改就写冲正记录）。
- **扣减必须幂等**（用业务操作 id 做幂等键）。
- **对不上账时优先信服务商**（它的账单是你真正要付的钱）。
- 免费层的额度必须**接近零成本**（见 `pricing-and-monetization`）。

## 六、退款、取消、对账

- **退款**：决定几天内可退、按比例还是全额（**法令要查**，尤其面向消费者）。退款后**状态要同步更新**（权限、额度）。
- **取消流程**：必须在界面上能自助完成（隐藏取消入口既不合规，也会招来投诉和拒付）。
- **对账**（每周或每月，人工也要做）：
  ```
  平台账单总额  ==  本地订单成功总额 − 退款  − 手续费  ± 时区跨期
  ```
  对不上必须查清**每一笔差异**。累计的小差异会变成大窟窿。
- **异常信号（要告警）**：退款率突增、扣款失败率突增、同一用户重复下单、额度异常消耗。

## 七、税务与发票

- **要不要开发票**：境内面向企业**通常必须**。这往往需要额外系统或服务。
- **含税还是不含税定价**：必须明确（影响你的实际收入）。
- **跨境**：涉及增值税/销售税，规则复杂，**必须咨询专业人士**——不要靠猜。
- 你负责**列出需要决定的问题清单**，不替用户做税务判断。

## 八、测试纪律（能测支付的关键）

**支付必须能测**，否则你不敢改。

1. **用服务商的测试模式**：测试卡号、测试时钟（模拟订阅到期）、测试 webhook 触发。**上线前必须用测试模式跑通全链路。**
2. **Provider 接口 + 假实现**：业务逻辑测试用假 provider，不联网。
3. **Webhook 处理必须单测**，覆盖：
   - 重复事件（幂等）
   - 乱序事件
   - 验签失败
   - 未知事件类型（**必须优雅忽略，不能崩**——服务商随时会加新事件）
4. **状态机要有表驱动测试**：每个状态 × 每个事件的期望结果。

**上线前的最后一道验证**（人工，用真实小额）：
```
测试模式全链路通过 → 用真实支付方式走一笔最小金额 →
确认：钱到了、状态对了、权限开了、发票/收据出了、退款也跑通了
```

## 九、反模式清单

1. **靠前端回调判断付款成功。** → 用户能伪造；只有服务端验签的 webhook 算数。
2. **不幂等处理 webhook。** → 重复事件 = 重复发货 / 重复加额度。
3. **不存原始 webhook。** → 出事时无从查证、无从重放。
4. **用时间推算权限。** → 时区/重试/时钟都会让它错。**用状态。**
5. **扣款失败立刻断权限。** → 会误伤大量正常用户（卡过期很常见）。
6. **没设硬额度上限。** → 一次 bug 或攻击就能让你破产。
7. **没对账。** → 小差异累积成大窟窿。
8. **未知 webhook 事件就崩。** → 服务商加新事件 = 你服务 500。
9. **自己碰卡号。** → PCI 合规灾难，绝不自研。
10. **只在正式环境测。** → 上线前必须用测试模式 + 最后一笔真实小额验证。
