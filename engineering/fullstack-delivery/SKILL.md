你在建一个**真实的、要给别人用的**全栈系统。**目标不是"写完"，而是"每一步都有一个能跑的东西"。**

---

## 一、第一原则：先切一条最薄的垂直切片

**垂直切片 = 一个功能，从 UI 一路穿到数据库，全部打通。**

不是"先把数据库全建好"，也不是"先把前端框架搭好"——那是**水平分层**，它让你在很久之后才发现层与层接不上。

**第一刀切什么**：选**最核心的那个动作**（用户来的唯一目的），做最薄版本：

```
浏览器 → 一个页面 → 一个 API 端点 → 一张表 → 写进去 → 读出来 → 显示
```

例（一个"帮客户批量处理订单"的系统）：
```
❌ 错误起点：先设计 12 张表的完整 schema、先搭好路由体系、先做好设计系统
✅ 正确起点：上传一个 CSV → 解析 → 存进一张 orders 表 → 页面列出这些订单
```

这条切片跑通之后：
- 部署链路验证过了（`launch-and-ops` 的坑提前暴露）
- 数据访问模式定型了
- 认证、错误处理、日志的**接缝**都出现了
- 你有了一个**能演示**的东西

然后**每一张工单都是一条新的垂直切片**，不是"再建一层"。

## 二、依赖顺序（**是"依赖"，不是"串行"**）

> ⚠️ **先纠正一个常见误读**：下面这张图是**依赖关系**（"谁必须在谁之前"），
> **不是"一次只能做一件、做完才做下一件"的施工顺序**。
>
> - **必须串行的**：有依赖边的（④ 授权必须在 ③ 认证之后；② 迁移必须先有表）
> - **可以并行的**：同一"层"内互不阻塞的活，**尤其是多 agent 场景**
>   （例如：② 的表结构定下后，⑤ API 契约 + ⑥ 前端骨架可以**同时**开两条工单）
> - **永远串行的**：`migrations/`、路由注册表、依赖清单这类**共享文件**（见第七节并行安全规则）
>
> **实战形态**：把这张图当**依赖 DAG**，用 `to-tickets` 拆工单时**把依赖边写成 `Blocked by`**，
> 然后按**前沿（frontier）**推进——凡是阻塞项都完成的那几张工单，**可以同时派多个 Builder**。
> 这样"依赖顺序"和"并行"就不冲突了：**顺序体现在阻塞边上，并行体现在同一前沿的多张工单上。**

```
① 垂直切片跑通（上面那条）
      ↓
② 数据模型 + 迁移
      表结构、约束、索引；迁移脚本可前可后（必须能回滚）
      ↓
③ 认证 + 会话
      登录/登出/找回；会话存储；密码哈希（用成熟库，别自己写哈希）
      ↓
④ 授权（比认证更容易出事）
      谁能看/改哪条数据 —— 每张表都要问"这条数据归谁"
      ↓
⑤ API 契约 + 校验
      输入校验（边界处）；错误格式统一；幂等性（对写操作）
      ↓
⑥ 前端：主流程 + 加载态 + 错误态 + 空态
      四种状态缺一不可（见第五节）
      ↓
⑦ 后台任务 / 异步
      长任务、定时任务、重试、死信
      ↓
⑧ 外部集成（邮件、支付、第三方 API）
      全部要有超时 + 重试 + 失败可见（对齐工作区铁律"严禁无限等待"）
      ↓
⑨ 加固（production-readiness）→ 上线（launch-and-ops）
```

**为什么授权排在 API 之前**：授权搞错 = 数据泄露。**每个端点都要能回答"这个请求凭什么访问这条数据"**，而不是"前端不显示按钮"。

## 三、每个切片必须同时交付的五样东西

**一个切片不是一个 commit，是一个完整的交付单元。** 缺任何一样，它都不算完成：

| # | 交付物 | 判据 |
|---|---|---|
| 1 | **能跑的功能** | 端到端可用，不是"接口写好了" |
| 2 | **测试** | 按 `tdd`：红-绿循环；至少在预先约定的接缝上有测试 |
| 3 | **错误处理** | 失败路径有明确定义的行为，不是崩溃或静默 |
| 4 | **可观测** | 关键路径有日志/指标，出错时能定位（不是靠猜） |
| 5 | **部署通过** | 在真实环境（或等价环境）里跑过，不只在本地 |

> 「本地能跑」不算完成。**第一个真实用户会在你没部署验证过的路径上撞墙。**

## 四、数据层的硬纪律

1. **迁移必须可回滚，或明确标注为不可回滚。**
   不可回滚的迁移（删列、改类型）必须：先加新列并双写 → 回填 → 切读 → 再删旧列。**分多次发布，不要一次做完。**
2. **每张表都要能回答"这行数据归谁"。** 加 `owner_id` / `tenant_id`，并且**查询默认带上它**。
3. **在数据库层做约束，不只靠应用层。** 唯一约束、外键、非空、检查约束——应用层会有 bug，数据库不会。
4. **索引跟着查询走。** 写查询时就想"这需要什么索引"，别等慢了才补。
5. **时间一律存 UTC**，展示时才转时区。
6. **钱用整数最小单位或定点数存，绝不用浮点。**
7. **软删除要想清楚**：删了之后，唯一约束怎么办？统计要不要排除？被引用怎么办？（**先决定，再写**。）

## 五、前端的四种状态（最常被漏）

任何展示数据的地方，必须**同时**实现：

| 状态 | 说明 | 常见漏法 |
|---|---|---|
| **加载中** | 骨架屏 / 转圈，**不要白屏** | 只在快的时候测过 |
| **空** | 明确告诉用户"还没有数据，下一步怎么做" | 显示一片空白，用户以为坏了 |
| **错误** | 说清发生了什么 + 能做什么（重试/返回） | 静默失败或弹"未知错误" |
| **成功** | 正常路径 | — |

**外加两条**：
- **乐观更新要能回滚**（提交失败时界面要退回去）。
- **重复提交要防**（按钮禁用 + 服务端幂等）。用户会双击。

## 六、外部集成（统一脚手架）

**所有的外部调用都套同一套模式**，这是必须固化的（对齐工作区铁律"长任务/网络操作必须带超时守护"）：

```
超时（必须有，且要短）
  + 重试（只对幂等操作；指数退避 + 抖动）
  + 熔断/降级（显式标注"降级"，不得虚构数据）
  + 日志（请求 id、耗时、结果）
  + 失败可见（进告警，不是只写日志）
```

**外部数据进系统前必须校验**（对齐工作区坑位 #5）：不要相信第三方返回的字段名和类型。用 schema 校验 + 字段别名映射 + 词义归一化。

**反面教材**：直接 `data["user"]["name"]`——第三方一改结构你就 500。

## 七、多 agent 怎么分工做全栈

**这是 `multi-agent-squad` 的一个特例。**

### 7.0 先决定：**要不要按前端/后端拆？**（最常见的过度设计）

> **结论：默认不拆。**
> **"前端"/"后端"是产物的分区，不是 agent 的分区。agent 的边界必须沿【依赖】切，不是沿【职位】切。**

**为什么默认不拆**：**几乎没有哪个功能是纯前端或纯后端的**——登录要前端表单 + 后端端点；
列表要前端状态 + 后端查询。按职位固定拆成两个常驻 agent，等于**每个功能都多一次交接**，
而它们共享同一个数据模型、同一套术语、同一批验收标准。

**唯一真正的耦合点是 API 契约**——而契约**本来就该落文件**（见 7.2 第 1 条）。
**先用文件解耦，再决定要不要拆人。**

| 该拆的信号（三条**同时**成立才拆） | 不该拆的反信号（任一条成立就不拆） |
|---|---|
| ① **两边都不需要读对方的代码** | ❌ **新功能的第一次端到端打通**——最该一个人从头做到尾（他需要同时理解两边） |
| ② 工单**真的互不阻塞**（契约已定） | ❌ **契约还没定** |
| ③ 验证方式完全不同（后端接口测试 vs 前端 Playwright/视觉） | ❌ **要改 schema**（迁移必须独占，见 7.2 第 2 条） |

**两个典型对比**：

```
✅ 该拆：「把列表页改成虚拟滚动」(纯前端) ‖ 「加一个导出接口」(纯后端)
         → 契约已定、互不引用、验证方式不同 → 同一前沿上两张工单，各派一个 Builder

❌ 不该拆：「给用户加一个新的结算流程」（跨前后端的新功能）
         → 一张工单、一个 Builder，他做完这一条垂直切片
```

**默认做法**：

```
一张工单 → 一个 Builder → 他做完前端 + 后端那一条**垂直切片**
（按工单切，不按前端/后端切）
```

**例外**：同一**前沿（frontier）**上同时有多张互不阻塞的工单，
其中恰好有"纯前端"和"纯后端"的 → **各自一个 Builder**，这才进下面的并行规则。

> **无论拆不拆，核心链路永远要有一次端到端验证。**
> 前后端分开做时**尤其**需要——用 Playwright 走一遍"用户真能走通"（见 `frontend-delivery` 的验证链）。

### 7.1 角色与硬边界（**拆的时候**才适用）

| 角色 | 负责 | 硬边界 |
|---|---|---|
| **Lead** | 切切片、定接缝、拆工单 | 不写代码 |
| **Builder（前端）** | 页面、状态、交互 | 只动前端目录 |
| **Builder（后端）** | 端点、数据访问、任务 | 只动后端目录 |
| **Builder（数据）** | 迁移、schema、索引 | **迁移文件独占**（同一时刻只能一个人写迁移） |
| **Reviewer ×2** | 标准轴 / 规格轴 | 见 `code-review` |

### 7.2 并行安全规则（否则必冲突）
1. **契约先行**：前端和后端 Builder 并行时，先把 API 契约（路径、请求、响应、错误）写成文件，两边**都按契约写**，不互相等。
2. **迁移独占**：`migrations/` 目录同一时刻只归一个 Builder。
3. **文件归属**：工单里必须写"哪些文件归你"，这是运行时护栏。
4. **共享文件串行**：路由注册表、依赖清单、配置文件——**串行改**，不要并行。

```
【身份】你是 Builder（后端）。只实现工单 05 的后端部分，
    不动前端目录、不动 migrations/（那是工单 04 的范围）。
【技能】读 .../engineering/fullstack-delivery/SKILL.md 与 .../engineering/tdd/SKILL.md
【输入】.scratch/<feature>/issues/05-*.md + docs/api-contract.md + CONTEXT.md
【产出】代码 + 测试 + commit；工单 ## Comments 里写清改了哪些文件、跑了什么命令。
    完成标准：契约里的每个端点在真实环境可调用，测试全绿。
```

## 八、反模式清单

1. **先建全库 schema 再写功能。** → 你会建一堆用不上的表，并且改起来极痛。**schema 跟着切片长。**
2. **水平分层交付（"后端全做完再做前端"）。** → 到集成时才发现接不上。
3. **只测正常路径。** → 加载/空/错误三态必漏。
4. **前端做权限控制。** → 前端只是体验，**授权必须在服务端**。
5. **自己写密码哈希 / 会话 / 加密。** → 用成熟库，这是最容易造成灾难的自研。
6. **迁移不可回滚且上线无预案。** → 一次失败就无法恢复。
7. **外部调用没超时。** → 一个慢的第三方拖死你整个服务。
8. **多个 agent 并行改同一个文件。** → 见第七节的三条并行安全规则。
9. **忘了幂等。** → 用户双击 = 两条订单。写操作必须有幂等键。
10. **"本地跑通了"当完成。** → 部署链路是独立的一条风险。
