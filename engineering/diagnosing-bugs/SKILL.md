# Diagnosing Bugs（诊断 Bug）

针对难 bug 的一套纪律。**只有在明确正当的情况下**才跳过某个阶段。

探索代码库时，读 `CONTEXT.md`（如果存在）以获得相关模块的清晰心智模型，并检查你所触及区域的 ADR。

## 脱敏（Redact）

这个技能会让你展示命令、输出和捕获的产物。**先把每一个密钥脱敏**——在原处写 `<REDACTED>`。把回路建立在**环境变量**上，这样凭据留在环境里，而不是留在你展示的东西里。捕获的产物带认证头：只引用携带信号的那几行。

如果脱敏后的输出不足以诊断这个 bug，就说出来并问用户。

## 阶段 1 —— 建反馈回路

**这个技能就是这个。** 其余全是机械劳动。如果你对这个 bug 有一个**紧密**的通过/失败信号——一个能对**这个** bug 变红的信号——你就能找到原因；二分、假设检验、埋点，全都只是消费它。如果你没有，再怎么盯着代码也救不了你。

在**这里**投入不成比例的努力。**要激进。要创造性。拒绝放弃。**

### 构造回路的方法——大致按这个顺序试

1. **失败测试**，在能触及该 bug 的任意接缝上——单元、集成、e2e。
2. **Curl / HTTP 脚本**，打向一个运行中的 dev server。
3. **CLI 调用**，配一个 fixture 输入，把 stdout 与已知正确的快照做 diff。
4. **无头浏览器脚本**（Playwright / Puppeteer）——驱动 UI，对 DOM/console/network 做断言。
5. **重放一份捕获的轨迹。** 把一次真实的网络请求 / payload / 事件日志存到磁盘；隔离地把它重放进代码路径。
6. **一次性脚手架（harness）。** 起一个最小的系统子集（一个服务、mock 掉依赖），用一次函数调用练到 bug 的代码路径。
7. **属性 / 模糊测试回路。** 如果 bug 是"有时输出错误"，跑 1000 个随机输入，找那个失败模式。
8. **二分脚手架。** 如果 bug 出现在两个已知状态之间（commit、数据集、版本），把"在状态 X 启动、检查、重复"自动化，这样你就能 `git bisect run` 它。
9. **差分回路。** 把同一个输入跑过旧版本 vs 新版本（或两套配置），diff 输出。
10. **HITL 脚本。** 最后手段。如果必须由人点击，就用 `scripts/hitl-loop.template.ps1`（Windows）或 `scripts/hitl-loop.template.sh`（POSIX）**驱动人**，这样回路依然是有结构的。捕获的输出回喂给你。
    > ⚠️ **`.ps1` 必须存成 UTF-8 带 BOM**，否则中文会让 PowerShell 5.1 报 `missing the terminator`。

建对反馈回路，bug 就 90% 修好了。

### 收紧回路

把回路当作一个**产品**。一旦你**有了**一个回路，就**收紧**它：

- 能更快吗？（缓存 setup、跳过无关初始化、缩小测试范围。）
- 信号能更锐利吗？（断言具体症状，而不是"没崩"。）
- 能更确定吗？（钉死时间、给 RNG 播种、隔离文件系统、冻结网络。）

一个 30 秒的 flaky 回路比没有回路好不了多少；一个 2 秒的确定性回路是**紧密**的——是调试的超能力。

### 非确定性 bug

目标不是干净的复现，而是**更高的复现率**。把触发循环 100 次、并行化、加压、收窄时间窗口、注入 sleep。50% 概率的 flake 可调试；1% 不可调试——持续提高复现率直到可调试。

### 当你**确实**建不出回路时

停下来，明确说出来。列出你试过什么。向用户要：(a) 能复现它的那个环境的访问权限，(b) 一份脱敏的捕获产物（HAR 文件、日志转储、core dump、带时间戳的录屏），或 (c) 允许添加临时的生产埋点。**没有回路就不要**进入提假设环节。

### 完成标准——一个紧密、能变红的回路

阶段 1 完成的条件是：回路**紧密**且**能变红**：你能点名**一条命令**——一个脚本路径、一次测试调用、一个 curl——你**已经至少运行过它一次**（展示该调用及其输出，已脱敏），并且它满足：

- [ ] **能变红** —— 它驱动真正的 bug 代码路径，并断言**用户的确切症状**，所以它能对这个 bug 变红、修好后变绿。不是"跑起来不报错"——它必须能**抓住这个具体的 bug**。
- [ ] **确定性** —— 每次运行结论相同（flaky bug：按上文钉死一个高复现率）。
- [ ] **快** —— 秒级，不是分钟级。
- [ ] **agent 可运行** —— 你能无人值守地跑它；只有在 `hitl-loop.template.ps1` / `.sh` 里才需要人在回路。

如果你发现自己在**这条命令存在之前**就读代码建理论，**停下——直接跳到假设，正是这个技能要防止的失败。** 没有能变红的命令，就没有阶段 2。

## 阶段 2 —— 复现 + 最小化

跑回路。看着它变红——bug 出现了。

确认：

- [ ] 回路产生的失败模式是**用户**描述的那个——不是碰巧在旁边的另一个失败。**错的 bug = 错的修复。**
- [ ] 失败在多次运行中可复现（或对非确定性 bug，复现率足够高到可据以调试）。
- [ ] 你已经捕获了确切的症状（错误信息、错误输出、慢的时序），这样后面的阶段能验证修复真的解决了它。

### 最小化

变红之后，把复现缩到**仍然会变红的最小场景**。**一次一个地**砍掉输入、调用方、配置、数据和步骤，每砍一刀就重跑回路——只保留对失败**承重**的东西。

为什么要费这个劲：最小复现缩小阶段 3 的假设空间（更少的活动部件可怀疑），并在阶段 5 变成干净的回归测试。

完成条件是**剩下的每个元素都承重**——去掉任何一个都会让回路变绿。

在**复现且最小化**之前不要往下走。

## 阶段 3 —— 提出假设

在测试任何假设之前，生成 **3~5 个排序过的假设**。只生成一个假设会锚定在第一个看似合理的想法上。

每个假设都必须是**可否证的**：说出它做出的预测。

> 格式："如果 <X> 是原因，那么 <改 Y> 会让 bug 消失 / <改 Z> 会让它更严重。"

如果你说不出预测，这个假设就是一团感觉——丢弃或磨锋利它。

**在测试之前把排序清单给用户看。** 他们往往有领域知识能瞬间重排（"我们刚部署了一个 #3 的变更"），或者知道他们已经排除过的假设。便宜的检查点，省大时间。不要卡在这里——用户离线时按你的排序继续。

## 阶段 4 —— 埋点

每个探针都必须映射到阶段 3 的一个具体预测。**一次只改一个变量。**

工具偏好：

1. **调试器 / REPL 检查**，如果环境支持。一个断点胜过十条日志。
2. **定点日志**，打在能区分假设的边界上。
3. 永远不要"什么都打日志然后 grep"。

**给每条调试日志打标签**，用唯一前缀，例如 `[DEBUG-a4f2]`。最后清理就变成一次 grep。没标签的日志会活下来；有标签的会死。

**性能分支。** 对性能回归，日志通常是错的。改为：先建立基线测量（计时脚手架、`performance.now()`、profiler、查询计划），然后二分。**先测量，后修复。**

## 阶段 5 —— 修复 + 回归测试

**在修复之前**写回归测试——但只有当存在**正确的接缝**时才写。

正确的接缝，是指测试能在调用点复现**真实的 bug 模式**。如果唯一可用的接缝太浅（bug 需要多个调用方时却只有单调用方测试、无法复现触发链的单元测试），在那里写回归测试只会给**虚假的信心**。

**如果不存在正确的接缝，这本身就是一项发现。** 记下它。代码库的架构正在阻止这个 bug 被锁死。把它标记给下一阶段。

如果存在正确的接缝：

1. 把最小复现变成该接缝上的一个失败测试。
2. 看着它失败。
3. 应用修复。
4. 看着它通过。
5. 针对原始的（未最小化的）场景重跑阶段 1 的反馈回路。

## 阶段 6 —— 清理 + 复盘

宣称完成之前必须做到：

- [ ] 原始复现不再复现（重跑阶段 1 的回路）
- [ ] 回归测试通过（或者"没有接缝"已被记录在案）
- [ ] 所有 `[DEBUG-...]` 埋点已移除（grep 该前缀）
- [ ] 一次性原型已删除（或移到明确标记的 debug 位置）
- [ ] 最后被证明正确的那个假设写进了 commit / PR 信息——让下一个调试者能学到

**然后问：什么本可以阻止这个 bug？** 如果答案涉及架构变更（没有好的测试接缝、调用方纠缠、隐藏耦合），带着具体细节交接给 `/improve-codebase-architecture` 技能。建议要在修复**落地之后**提，不是之前——你现在比开始时掌握了更多信息。
