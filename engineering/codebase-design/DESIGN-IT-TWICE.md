# 设计两次（Design It Twice）

当用户想为一个已选定的加深候选探索替代接口时，用这个**并行子 agent** 模式。基于 Ousterhout 的 "Design It Twice"——你的第一个想法不太可能是最好的。

使用 [SKILL.md](SKILL.md) 里的词汇——**模块**、**接口**、**接缝**、**适配器**、**杠杆**。

## 流程

### 1. 框定问题空间

在起子 agent 之前，为选定的候选写一份面向用户的**问题空间说明**：

- 任何新接口都必须满足的约束
- 它会依赖的依赖，以及它们属于哪个类别（见 [DEEPENING.md](DEEPENING.md)）
- 一份粗略的、示例性的代码草图，用来把约束落到实处——不是提案，只是让约束变具体的一种方式

把它给用户看，然后**立刻**进入第 2 步。子 agent 并行工作时，用户正好边读边想。

### 2. 起子 agent

**并行**起 3 个以上子 agent。每个都必须为加深后的模块产出一个**截然不同**的接口。

给每个子 agent 一份**独立的技术简报**（文件路径、耦合细节、来自 [DEEPENING.md](DEEPENING.md) 的依赖类别、接缝后面坐着什么）。简报独立于第 1 步那份面向用户的问题空间说明。给每个 agent 一个不同的设计约束：

- Agent 1："最小化接口——最多 1~3 个入口点。最大化每个入口点的杠杆。"
- Agent 2："最大化灵活性——支持大量用例和扩展。"
- Agent 3："为最常见的调用者优化——让默认情形变得微不足道。"
- Agent 4（如适用）："围绕端口与适配器来设计跨接缝依赖。"

简报里同时包含 [SKILL.md](SKILL.md) 的词汇和 `CONTEXT.md` 的词汇，让每个子 agent 的命名既符合架构语言、也符合项目的领域语言。

每个子 agent 输出：

1. 接口（类型、方法、参数——外加不变量、顺序、错误模式）
2. 使用示例，展示调用者怎么用它
3. 实现在接缝后面藏了什么
4. 依赖策略与适配器（见 [DEEPENING.md](DEEPENING.md)）
5. 取舍——杠杆高在哪、薄在哪

### 3. 呈现并比较

**逐个**呈现设计，让用户能吸收每一个，然后用文字比较它们。按**深度**（接口处的杠杆）、**局部性**（改动集中在哪里）、**接缝位置**来对照。

比较之后，给出你自己的推荐：你认为哪个设计最强、为什么。如果不同设计里的元素能很好地组合，提出一个混合方案。**要有主张**——用户要的是一份强有力的判断，不是一个菜单。
