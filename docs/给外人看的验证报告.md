# 验证报告：这套体系在真实项目上跑了什么（给外人看的一页）

> 这份是给**没参与开发的人**看的：不讲内部术语，只讲**测了什么、怎么测的、结论有多硬、哪里还不确定**。
> 不用读其它文档也能看懂。
>
> ⚠️ **本文已更新过一次**（原版只覆盖第一轮：一个狼人杀项目）。后来又跑了两轮：
> **另外三个性质不同的真实项目**，以及**由它们照出的一条工具缺陷线**。更新时**改掉了原版一句被推翻的话**——
> 具体是哪句、为什么必须改，见第一节。**原文不删，改法留痕**，这是这套体系自己的规矩。

---

## 一、一句话结论

**它在四个真实的、做到一半的项目上跑通了，照出二十多个真问题——其中大部分是「项目自己的问题」，但也有「工具自己的问题」。**

> **这里更正原版的一句话。** 原版写的是：「照出了 12 个真实问题——而这些问题里，**没有一个是"工具本身出错"**」。
> **这句话后来被推翻了**：第二轮（三个项目）实测发现工具自己有两处不达标，其中一处格外刺眼——
> **工具在"不支持某项检查"时，顶层结论照样打了"通过"**。也就是说，它犯了自己最不该犯的错：
> **把"没查"说成了"查过、没问题"**。
>
> 为什么这件事值得摆在第一句：**它正是这套方法在起作用的样子。**
> 这套体系的活不是"证明自己行"，而是**把"文档里被记下的风险"变成"闸门上判定的失败"**——
> 这次被判定失败的是**它自己**，然后它被改了（5 个提交、5 轮独立复审、自动自检从 43 条长到 55 条）。
> 一个只会证明自己没问题的验证工具，是不值得信的；**能照出自己问题的**才值得。

换句话说：它的**可靠性**在这一轮里站住了（照出来的问题绝大多数是真的、可复现的）；
它**真正的短板不在"准不准"，而在"有没有人真的用它"**（见第五节）。

## 二、被测项目（真实，不是玩具）

**第一轮：一个项目**

| 项目 | 一个「狼人杀 AI 对局平台」 |
|---|---|
| 体量 | 19 个 Python 文件（约 200 KB）、有 7 个测试文件、有真实的 git 提交历史 |
| 状态 | **做到一半**：功能相当完整，但从未被这套体系正式登记过 |
| 为什么选它 | 它是"**已经在跑、但还没收口**"的项目——最能暴露"体系只会纸上谈兵"这类问题 |
| 数据来源 | 全部结论都可复跑：命令、文件、行号都在下面注明 |

**第二轮：另外三个项目（性质互不相同，专门用来交叉验证）**

| 项目 | 性质 | 为什么选它 |
|---|---|---|
| 一个量化交易研究项目 | 有数据库、有定时任务、有 A/B 实验记录 | 测"数据类项目"上的表现 |
| 一个 RPG 小游戏 | 桌面程序、无版本控制、根目录很乱 | 测"工程习惯很差的项目"上的表现 |
| 一个思维导图小工具 | 前后端都有、测试齐全、无版本控制 | 测"看着挺健康"的项目上会不会漏掉要命的东西 |

> 三个项目**都不是 git 仓库**——这不是刻意挑的，但它恰好把工具的一个真实短板照了出来（见第五节）。

## 三、怎么测的（三种方法，互相独立）

| 方法 | 做法 | 为什么可信 |
|---|---|---|
| **本机全量自检** | 一条命令跑完全部自动检查 | 可复跑；"没跑成"会被单独标出，**不许混进"通过"** |
| **干净房间复现** | 把整个体系 clone 到临时目录、`npm ci` 装依赖、**刮干净环境**再跑一遍 | 等价于"换一台机器还能不能跑"，排除"只有作者机器上才能过" |
| **独立审计** | 找一个**不知道任何内情**的审查者，只给它改动内容和"声称解决了什么"，让它自己判断 | 改的人看不出自己的错；上一轮它抓到的多条问题，作者本人没想到 |
| **真实项目实测** | 让一个**全新会话**（零上下文）在这个项目上独立作业，**判据在看到结果之前就写死** | 防止"看到结果再定标准"——那等于自己给自己打分 |

> **最后一条最重要**：判据是跑之前定好的（十条，覆盖"有没有照规矩走、有没有把没跑成说成通过、有没有替我下业务决定"等），
> 结果是 **10 条全部达到**。这个分数本身意义有限，**有意义的是"标准不是事后凑的"**。

## 四、它照出了什么（第一轮 12 条，按严重度）

> ⚠️ **这些全是「项目自己的问题」，不是「工具的问题」**——这正是本次验证想证明的事：
> 这套体系的价值是**把"文档里被记下的风险"变成"闸门上判定的失败 + 可执行的清单"**。

### 🔴 严重（4 条）

| # | 问题 | 证据 |
|---|---|---|
| 1 | **项目根躺着一份"假绿"报告**：它写着"检查全过"，而真跑的结果是"有失败项" | 旧报告与真跑结果的检查项数量、失败数**直接矛盾**；且旧报告缺生成时间字段，无法判断新旧 |
| 2 | **所有对外接口都没有鉴权**，服务还监听所有网卡 | 接口定义文件里检索鉴权相关写法 → **零命中**；启动脚本监听的地址是"所有网卡" |
| 3 | **花钱的接口没有任何额度上限** | 全项目检索"限流 / 额度 / 预算" → **零命中**；唯一的限制是"最多同时 6 个并发"，只管并发不管总量 |
| 4 | **虚拟环境是空壳，但启动脚本优先用它** | 该环境里依赖目录为空，`import pytest` 直接报"没有这个模块"；而启动脚本的判断是"只要它存在就用它" |

### 🟡 中等（5 条）

| # | 问题 |
|---|---|
| 5 | 意图契约（`CONTEXT.md`，51 KB）和运行手册**没进版本库**——而契约是团队唯一的共享内存 |
| 6 | **克隆了真人声音**的产物已入库（原始素材已正确排除，运行时也不外发素材；问题在**授权**） |
| 7 | 没有许可证文件、没有依赖锁文件（依赖版本不可复现） |
| 8 | 代码检查的 209 条告警里**混着真问题**（不全是风格债）：如"异常被静默吞掉"多处，正好对应契约里自己记的"保存失败没人知道" |
| 9 | 健康检查**分不清"进程活着"和"依赖可用"**：上游服务挂了它照样报正常 |

### ⚪ 轻微（3 条）

| # | 问题 |
|---|---|
| 10 | 全部日志用 `print`，没有结构化日志、没有错误上报（服务降级了也没人知道） |
| 11 | 对局存档接口无鉴权 + 房间号只有 6 位（这条契约里已经记过，独立复核确认成立） |
| 12 | 文档小漂移：运行手册记的闸门项数比脚本实际的**少了一个**（脚本早加过检查项，文档没跟） |

### 📌 一条必须说清的话

那个项目的意图契约**第 7 节早就把这些洞记下来了**（无鉴权、无费用上限，带文件行号、标了红黄绿）。
新会话**独立复核**了其中三条，全部成立。

> **所以真实状态不是"没人发现问题"，而是：问题被写进了意图契约，代码一行没改。**
> 跑闸门得到"通过"指的是**结构齐备**，**不是"这些洞已经堵上"**——它没有把这两件事混起来，这点做对了。

### 第二轮（三个项目）照出的东西 —— 这一轮更值钱

| 项目 | 最值钱的发现 |
|---|---|
| 量化项目 | **A/B 战绩已经静默不入库 9 天**：一处漏写的 `import` 导致每次记录都抛错，而错误被一个"吞掉所有异常"的写法**静默咽了**。数据侧吻合：统计表里只有 3 行、最新一条停在 9 天前。**没有任何告警、没有任何日志** |
| 游戏项目 | **用一次性补丁脚本代替版本控制**：根目录那批脚本全是"就地重写源码"的，而且**全部过期**（其中一个只因换行符格式不符才侥幸没生效）；两条绝对路径写死盘符（换台机器会**静默降级**）；**整套测试永远不会被闸门跑到**（测试放在根目录，闸门只找 `tests/`）；根目录那几个空的乱码文件名，查出是**文档抽取事故**留下的 |
| 思维导图 | **全部接口零鉴权，而且数据模型里根本没有"用户"这个概念**（只靠绑死本机地址挡着）；接口文档页默认开着，等于主动把接口地图递出去；**测试全绿、覆盖率很高、真实数据完好**——看着很健康的项目，但**没有版本控制也没有备份，那份数据库是唯一一份真实数据** |

> 上表刻意**不写精确条数**：那些是**别的项目的内部数字**，真值与证据留在存档
> （`docs/reviews/2026-09-13-three-projects-protocol.md`）里。同一个数字有两份出处，
> 就是这套体系自己在防的"第二真相源"。

### 同一轮还照出了「工具自己」的问题（这是原版那句话被推翻的地方）

| # | 工具的问题 | 后果 | 现在 |
|---|---|---|---|
| 1 | **不支持某项检查时，顶层结论照样打"通过"** | 项目不是 git 仓库时，"硬编码密钥"这一项**整项没执行**，而结论是 `PASS（带警告）` —— 读起来像"查过一遍、没问题" | 已改成三档结论 + 单独一段"**没跑成**"；凡"整项没查"一律降档，机器通道（`-Quiet`）也照打 |
| 2 | **体检本身在项目里留垃圾** | 三个项目根都被留下缓存目录（其中一个 42 个文件）——**是我的闸门造成的**，而这三个项目**没有版本控制、改不回去** | 已改成跑完不留痕（缓存改到临时目录） |
| 3 | 危险写法检查**假阳性** | 两个项目同时误报（词边界没写对） | 已修 |
| 4 | 测试发现只看 `tests/` 一层 | 两个项目的**整套测试永远不被跑到**（一个在根目录、一个在更深层） | 已改成往深处找 |

> **第 1 条最贵**：它不是"报错了"，而是"**没查却说查过**"——正是这套体系存在的理由。
> 它自己的原话是「**没跑成 ≠ 通过**」，而它自己违反了。发现渠道也值得记：
> **是三个独立作业的新会话如实报告"这一项我查不了"，才把工具本身的问题顶出来的**——
> 换句话说，**是"要求如实报告"这条纪律抓到了工具**。

## 五、哪里还不确定（**如实说，不粉饰**）

### 这一轮**没能跑成**、因此**没有结论**的检查

| 没跑成的检查 | 为什么 |
|---|---|
| 依赖漏洞扫描 | 撞上沙箱临时目录权限，报错退出 —— **不是"扫过没问题"** |
| 静态安全扫描（SAST） | 工具在沙箱里崩溃 —— **不是"扫过没问题"** |
| 项目自身的测试（闸门内置那一次） | 因为上面的第 4 条（空壳环境）判失败；**换解释器补跑时全部通过** |
| 真实模型 / 语音的端到端 | 需要真密钥；按纪律不去动它 |
| 浏览器端行为 | 没起服务、没开浏览器 → 前端状态与可访问性**本轮未实测** |
| 备份 / 恢复演练 | 项目没有数据库，存档就是文件；**没有备份机制**——这是"没做"，不是"不需要" |
| **给工具的最后一轮独立复审** | 起了但**当时网络中断**（界面报取数据失败），审查者没产出结论 → 按规矩记成"**没跑成**"，**不算通过**（那个提交仍有自动自检与变异测试） |

> 最后一行是"没跑成 ≠ 通过"这条规矩在**现实中**的样子：**断网也算一种"没跑成"**，
> 而正确的做法不是"反正大概没问题"，是**明写这一格没有结论**。
> 同样的道理也适用于前六行：它们没跑成，**所以关于它们的任何"没问题"都不成立**。

### 这套体系**自身的**已知短板

| 短板 | 说明 |
|---|---|
| **很年轻** | 诞生的时间很短，验证来自少数几次实测，**不是被很多真实项目长期验证过的成熟产品** |
| **很多技能只有纸面依据** | 自带技能里真正在真实项目里跑过的只是其中一部分 |
| **偏向某一款 AI 工具** | 机制层是为一款具体工具实测出来的；换工具要重做配置，**流程本身仍可用** |
| **偏向 Windows** | 核心脚本为 Windows 写的；CI 模板同时给了 Windows 与 Linux 两条，**Linux 那条没在真机上验证过** |
| **文档偏重** | 为了让规则不被遗忘写了不少说明文件——所以有"给非技术用户的指南"这份只讲人话的入口 |

### 这一轮里，**测试脚本自己**出的错（都已修）

真机上一共红了七次，**七次全是我这边测试脚手架的缺陷，没有一次是被测代码的问题**：
期望写错、变异选错内容、变异字符串过期、通过语义写反、断言了会乱码的中文输出、
一个"只看标签"的入口放得太晚导致超时、静态断言没跟着代码搬家。

**改工具那条线（第一轮之后）又出了九次**，同样**没有一次是产品的错**：

| # | 脚手架的错 | 怎么被发现的 |
|---|---|---|
| 1 | 断言写成**恒真**（钉了一个到处都出现的词 → 等于没测） | 独立复审 |
| 2 | 注释写着"跳过就要报出来"、**代码里那行没写** | 自己复查注释 |
| 3 | 输出里**指了一个不存在的地方**（"完整清单见另一处"，而那处也截断） | 自己 + 独立复审 |
| 4 | 断言写的是"我期望的实现"而不是"正确的行为" → 假红 | **提交钩子**（不是我自己） |
| 5 | 断言与真实输出**差一个空格** → 假红，报得像产品 bug | 自己写独立诊断脚本复现 |
| 6 | **把猜的当实测写进注释** | 自己去核数 |
| 7 | **没验证别人报的缺陷前提就照做** → 引入一个真回归（数字算重） | 下一轮独立复审 |
| 8 | 新用例**污染控制台编码**，导致同环境下下一轮自检假报 10 条失败 | 自己复现那个异常分数 |
| 9 | 一处"假通过"（进程都没起来，而代码把空值当成了"成功"） | 自己诊断异常时 |

> **为什么值得写出来**：它说明"验证"这件事本身也会出错，而**能照出自己脚手架的错误**，正是这套方法的价值之一。
> 这九条有一个共同点：**全都是"输出/断言说的话与事实不符"**——跟第一节那个工具缺陷是**同一种病**。
> 工具在治这个病，写工具的人在同一天里用九种姿势又犯了一遍。**这就是为什么它坚持要"另一个 agent 来判"**。

## 六、这套东西适合谁、不适合谁

| 适合 | 不适合 |
|---|---|
| 一个人（或很小团队）要把想法做成**能收钱的系统** | 想要"一键生成产品"的人——它**不写业务逻辑**，它管纪律与闸门 |
| 愿意在**动手写代码之前**先去找真人验证需求的人 | 想跳过验证直接开写的人（第 1 关就是为了拦这个） |
| 想每一步都留下**证据和边界**、而不是靠感觉推进的人 | 讨厌被问问题、讨厌"到点必须做决定"的人 |

**它不保证你成功。** 有没有人要、愿不愿意付钱，最终只有市场能回答。
它做的所有事，都是让你**更早、更便宜地知道答案**。

## 七、给想自己验证一遍的人

这一轮的方法**完全可复用**，不需要相信这份报告：

1. 挑一个**已经在跑、但没做过体检**的真实项目（半成品最好）
2. **先写下判据**：什么算通过、什么算失败——**必须在看到结果之前写**
3. 开一个**全新会话**，工作目录设成那个项目，让它按体系自己的入口文档走
4. 它给出的结论里，重点核三件事：
   - 它**跑没跑成**（"没跑成"必须单独列出，不许混进"通过"）
   - 它的结论**能不能落到文件与行号**
   - 它有没有**替你签**那些只有你能确认的事（比如素材授权、要不要外发）
5. 最后把结果按"**入口缺陷 / 技能缺陷 / 工具缺陷 / 项目缺陷 / 测试设计缺陷**"五类归因 ——
   其中**"项目缺陷"越多，说明这套体系越有用**（它的活就是照出这些）

> 完整的判据表与逐条结果留在体系仓库的 `docs/reviews/` 里，**三份存档分别对应三轮**：
>
> | 存档 | 记的是什么 |
> |---|---|
> | `2026-09-13-real-project-protocol.md` | 第一轮（一个狼人杀项目）：十条判据**在看到结果之前写死**，逐条结果 |
> | `2026-09-13-three-projects-protocol.md` | 第二轮（三个项目）：判据口径、逐条判定（**10 条达标、1 条不达标**）、照出的项目缺陷、工具缺陷、以及体检的副作用 |
> | `2026-09-13-30fd4dd.md` | 第三轮（改工具这条线）：一个缺陷从被发现到收口的全过程 —— 5 个提交、5 轮独立复审、**我自己犯的九条错**、七条遗留取舍 |
>
> 三份都遵守同一条规矩：**判据先写死、结果不许再改**；事后补齐的内容**以"事后补记"标注**，不去动原来的判据原文。
> 最后一份里还有一个反面样板：**某一轮独立复审因断网没跑成，就如实记成"没跑成"，不算通过**。
