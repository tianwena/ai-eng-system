> 面向技术评审。本文只讲**机制、设计取舍、以及每条声明怎么自行验证**；不讲愿景。
> 写作基点：2026-09-13 · master（HEAD `87920d3`）。
> 文中所有"关于体系自身的数字"都有机器可核的真值源（见第九节）；
> 结论性的验证材料（判据、逐条结果、复审记录）在 `docs/reviews/`。

## 一、定位与组成

### 1.1 它是什么 / 不是什么

**是什么**：一套跑在本机、面向"单人 / 小团队 + AI 协作"的**工程纪律层**。四件事被做成可执行机制：

1. **意图对齐**——写代码之前，三张图（实体关系 / 状态机 / 接口契约）+ `CONTEXT.md` 必须过一道机器闸门；
2. **风险检查**——密钥、依赖漏洞、静态分析、部署配置、测试等，按"轻量红线（秒级）→ 加固闸门（分钟级）"两级执行；
3. **结论语义**——所有检查器区分**通过 / 失败 / 没跑成**三种结论，退出码 `0 / 1 / 3` 与之对应；
4. **证据留痕**——状态、判据、复审结论全部落文件，可复跑、可追责。

**不是什么**：

- 不写业务逻辑、不生成产品代码；
- 不替代 CI、SAST、linter——它**包在这些工具外面**，管的是"它们没跑成时结论怎么说、问题归谁"；
- 不是"一键通过"工具：红线是**及格线**，不是优秀线。

### 1.2 规模与组成

| 项 | 数量 | 真值源（见第九节） |
|---|---|---|
| 36 个技能 | 其中工程类 29、通用类 7、自研 10 | 含 `SKILL.md` 的目录数 |
| 18 个脚本 | 库根 2 个 + `scripts/` 下 16 个 | 文件系统计数 |
| 15 项检查 | 加固闸门全部检查项（不带测试时 14 项检查） | `Add-Result` id 集合 |
| 4 项红线 | 轻量闸门 | `redline-check.ps1` 检查项 |
| 57 个用例 | 检查器自检（变异测试） | `self-test.mjs` 的 `CASES` |
| 6 个检查器 | 一条命令全跑（`verify-all.mjs`） | `EXPECTED_STEPS` 总闸 |

## 二、设计出发点：五个实测失效模式

这套体系的每一项机制，都能追溯到一次**真实翻车**（不是假想风险）：

| # | 失效模式 | 真实实例 | 对应机制 |
|---|---|---|---|
| 1 | **静默失败**：功能在跑，数据没落地，无人知晓 | 一个量化项目的 A/B 战绩因一处异常被吞掉，**静默停写九天**（无日志、无告警） | "没跑成"独立成类；日志/告警要求写入技能与闸门 |
| 2 | **"没查"被说成"查过"** | 非 git 项目里"硬编码密钥"整项未执行，顶层结论照样 `PASS`（内部编号 N1） | 三态结论 + 三档 verdict + 退出码 3 |
| 3 | **文档与真值漂移** | 历史上四次数字腐烂（检查项 13/14、技能数、脚本清单漏项） | `facts.json` 单一真值源 + 锚点 + 未登记数字拦截 |
| 4 | **检查器自身失效**（空转 / 恒真判据 / 狼来了） | 三个检查器 bug 实例：只认非加粗错误行、契约铺垫被当端点块报假警、正则只匹配到 2/10 行 | 变异测试自检 + "变异必须真改到"指纹闸 + 基线必须绿 |
| 5 | **检查行为改变被检对象** | 体检在无 git 项目里留下缓存目录与日志，且**不可回滚** | 环境隔离（缓存移出项目）+ 副作用如实登记 |

其中第 2 条是本体系最核心的一条戒律：**"没跑成"不等于"通过"**。它同时被用来要求项目、要求 agent、也要求工具自己。

## 三、体系结构（四层 + 一条命令入口）

```
                    ┌────────────── 唯一入口 ──────────────┐
                    │  从这里开始.md：读完一页，知道跑哪条命令  │
                    └───────┬──────────────────────┬───────┘
                            ▼                      ▼
             ┌──────────────────────┐   ┌──────────────────────────┐
             │ 技能层（怎么做事）      │   │ 检查器层（怎么判定）        │
             │ 36 个 SKILL.md        │   │ 18 个脚本：                │
             │ 两个路由器：           │   │ 结构闸门 / 红线 / 加固闸门  │
             │ ask-matt（工程）      │   │ 自检 / 一致性 / 完整性 /   │
             │ commercial-squad（商业）│  │ 干净房间 / 状态机 / 钩子    │
             └──────────┬───────────┘   └────────────┬─────────────┘
                        └───────────┬────────────────┘
                                    ▼
                     ┌───────────────────────────────┐
                     │ 协议层（怎么留痕与复查）          │
                     │ 判据先写死 · 独立复审 · 五类归因  │
                     │ 记录归档 docs/reviews/           │
                     └──────────────┬────────────────┘
                                    ▼
                     ┌───────────────────────────────┐
                     │ 状态与证据层                    │
                     │ .scratch/state.json（单一事实源）│
                     │ CONTEXT.md · 报告快照           │
                     └───────────────────────────────┘
```

### 3.1 技能层

36 个技能（`SKILL.md`），分两类调用策略：**model-invoked**（模型可自动加载）与 **user-invoked**（只能人敲）。使用者不需要记全部名字，只需知道两个路由器：工程问题问 `ask-matt`，商业问题问 `commercial-squad`。技能的正文本身就是给 agent 读的工作规程（写作规范见 `writing-for-agents` 技能）。

### 3.2 检查器层（18 个脚本，按职责分类）

| 类别 | 脚本 | 职责 |
|---|---|---|
| 结构闸门 | `verify-structure.mjs` | 三张图 + 接口契约的硬结构校验；退出码 1 = 停下补图，不许开写 |
| 轻量红线 | `redline-check.ps1` | 4 项：硬编码密钥、无保护 API、违法数据源、分发他人内容（后两项人确认）；秒级返回 |
| 加固闸门 | `quality-gate.ps1` | 15 项检查，分 A–E 五段（见 4.3）；输出 stdout 判定 + JSON 快照 |
| 检查器自检 | `self-test.mjs` | 变异测试：注入已知错误，断言闸门必须拦住 |
| 一致性与完整性 | `check-consistency.mjs`、`verify-gate-integrity.mjs`、`extract-cheatsheets.mjs`、`verify-ps1.mjs` | 文档数字 ⇄ 真值；闸门清单 ⇄ 钉住清单；速查卡 ⇄ 正文；`.ps1` 的 BOM 与语法 |
| 环境复现 | `verify-clean-clone.mjs` | clone 到临时目录 + 干净环境复跑（本机复现 CI 的核心收益，零外泄） |
| 状态机 | `state.ps1` + `state.schema.json` | 项目阶段 / 闸门 / 产物 / 阻塞项的唯一写入口 |
| 钩子与工具 | `install-git-hooks.ps1`、`scripts/git-hooks/pre-commit`、`ruff-label.ps1` | 提交前自检（随仓库走）；ruff 规则集标签 |
| 总入口 | `verify-all.mjs` | 收敛 6 个检查器，不依赖任何本地状态（换机器 / CI 用同一入口） |

### 3.3 协议层

- **判据先写死**：任何一次验证/复审，判据必须在看到结果之前登记；事后只许新增"补记"，不许改判据原文；
- **独立复审**：改了 `scripts/` 或 `tests/`（检查器 / 闸门 / 钩子 / 夹具）**必须**起独立上下文的 reviewer；技能正文与文档不强制（避免规则被形式化架空）。reviewer 提示词有固定模板，只回答三问：真的解决了声称的问题吗？新引入了什么？哪些本该被检查却没有？
- **五类归因**：入口缺陷 / 技能缺陷 / 工具缺陷 / 项目缺陷 / 测试设计缺陷——不许笼统说"没做好"；
- **留痕**：复审结论落到 `docs/reviews/<日期>-<基点 sha>.md`。留痕不强制（伪造空文件零成本），但真做过就留下。

### 3.4 状态与证据层

- `.scratch/state.json` 是项目状态的**单一事实源**，schema 递归校验（类型 / 深层必填 / 枚举 / `const` / 未声明字段）；`state.ps1` 是**唯一写入口且只有 Lead 能调用**（其余角色只读），所有写入记 `updated_by` 与 `history`，可事后审计；
- `CONTEXT.md` 是意图契约（团队共享记忆）；
- 闸门报告（如 `gate-report.json`）是**某次运行的快照**，不是状态：带 `generated_at`，缺它即视为不可判断新旧。

## 四、运行机制

### 4.1 状态机：阶段 / 闸门 / 产物 / 档位

`state.ps1` 维护的模型（与 `state.schema.json` 一致）：

- **阶段（phase）**：`idea → tech-review → g3-build`（技术档）；商业档插 `g1-validate`、`g2-price`，之后 `g4-repeat`；另有 `hardening`、`shipped`、`paused`。注意"写完图"是 `tech-review`（对齐），**正式开工是 `g3-build`**；
- **闸门（gate）**：`tech_redline`、`g1`–`g4`，记录通过状态与证据；
- **产物（artifact）**：`context_md`、`er_diagram`、`state_diagram`、`interface_contract`、`api_contract_path`——硬结构产物**只有真实存在**才允许标 true；
- **档位（tier）**：`tech`（日常自用，跑红线即可）/ `commercial`（要收钱，强制 G1–G4）。

设计取向上有一条硬结论：**G1–G4 默认不启动**——"一个没人跑的闸门等于没有闸门"。商业档才挂 G1–G4 的期限与退出判据。

### 4.2 四条主路径

| 路径 | 场景 | 命令链 |
|---|---|---|
| A 新项目 | 开始写代码 | `install-skills.ps1` → `state.ps1 init` → 写三图 + 契约 → `verify-structure.mjs`（过了才开写） |
| B 上线/交付 | 给别人用 | `redline-check.ps1`（自用/局域网）或 `quality-gate.ps1 -IncludeTests`（对外/收费） |
| C 商业化 | 决定收钱 | 先过红线 → `state.ps1 gate tech_redline -Passed` → `tier commercial` → G1–G4 |
| D 维护体系本身 | 改技能/脚本 | `verify-all.mjs`（本地）/ 提交钩子（拦截）/ `verify-clean-clone.mjs`（复现 CI） |

### 4.3 一次加固审查（`quality-gate.ps1`）的完整链路

15 项检查分五段：

- **A 密钥与敏感文件**：被跟踪的敏感文件、硬编码凭据、gitleaks 历史扫描、`.gitignore` 覆盖；
- **B 依赖**：`pip-audit`、`npm audit`、锁文件存在性；
- **C 静态分析**：`semgrep`（SAST）、`ruff`（带规则集标签）、危险模式（`eval`/`exec`/`shell=True`/`pickle` 等，**带词边界**）；
- **D 部署与运维**：部署配置探测（递归 + 按形态 + Makefile 目标）、CI 配置、RUNBOOK、密钥类文件探测（D4）；
- **E 测试**：解释器与依赖可用性诊断（E1）、测试发现（**递归找 `tests/`，兼容根下 `test_*.py`**）、跑测试。

每条检查**必须产出且只产出一条结果行**（`Add-Result`），否则触发"少项总闸"（见 5.2）。

### 4.4 结论语义与退出码

| 退出码 | 含义 | 谁在用 |
|---|---|---|
| 0 | 全部通过 | 所有检查器 |
| 1 | 有检查**真的失败**（内容/行为有问题） | 所有检查器 |
| 2 | strict 模式下有跳过项 → 覆盖不完整 | `quality-gate.ps1 -Strict` |
| 3 | **有检查压根没跑成**（环境不具备）→ 没有结论 | `verify-all` / `verify-gate-integrity` / `verify-clean-clone` / `verify-ps1` / `quality-gate` |

`quality-gate` 的 JSON `verdict` 是同一语义的机器可读版：
`BROKEN`（有检查没上报）> `FAIL` > `NOTRUN` > `INCOMPLETE`（strict）> `PASS (with skips)` > `PASS`。

一个刻意的设计：`verify-all --fast`（跳过自检）**也返回 3**——因为 CI 和 agent 只看退出码，跳过"证明其他闸门还活着"的那一步，就不是完整结论。

### 4.5 用户不在线时的降级规则（三档）

"含糊先问、不许猜"在用户离线时会死锁，因此把降级写死为三档：

| 情况 | 处理 |
|---|---|
| 事实类问题（用什么框架、有几个端点） | 自己查；查不到就标明"查不到" |
| 决策类问题（选型、定价、范围） | 可带假设前进，但三条同时满足：假设落文件（写入 `CONTEXT.md` 待确认一节）、改起来便宜、**不许越过闸门** |
| 不可逆 / 花钱 / 对外动作 | **一律停下**，交出问题清单等裁定 |

判据一句话：**假设能写进"待确认"一节 ≠ 可以做**。动代码/配置、发布、花钱、删数据，永远要人点头。

## 五、关键技术机制（逐条）

以下每条按【问题 → 设计 → 落点 → 验证方式】展开。

### 5.1 "没跑成"是一等公民

- **问题**：工具在"不支持某项检查"时若只说"通过（带警告）"，读者会把"没查"读成"查过没问题"（N1 实例）。
- **设计**：检查项的结果只有四种状态——`PASS` / `FAIL` / `SKIP`（项目不需要或工具没装，覆盖缺口显式列出）/ `NOTRUN`（环境不具备，**没有结论**）。顶层结论把"有 N 项没跑成"独立成最高优先的一档；`-Quiet`（机器通道）也照打这一档，不允许被静默。
- **落点**：`redline-check.ps1` 的 `$notRun` 类别与三档结论行；`quality-gate.ps1` 的 `NOTRUN` 块与 `verdict`；`verify-all.mjs` 的 exit 3。
- **验证**：对空目录跑 `redline-check.ps1`，必须出现"有 N 项没跑成"而不是光秃秃 `PASS`；`self-test.mjs` 有对应变异用例。

### 5.2 不许静默少项：双层护栏

- **问题**：删掉一条检查、或某条检查因异常没产出结果，摘要照打"checked N"，**没有任何迹象**表明少了一项——漏报会被读成"该项没问题"。
- **设计（两层，缺一不可）**：
  - **内部总闸**：每条结果必须有 Id、恰好一条、不许重复、不许空 Id（空 Id 以前会同时躲开"少项"和"重复"判据）；
  - **外部钉住清单**：`verify-gate-integrity.mjs` 顶部的 `PINNED_GATE_IDS`（15 项）**钉在闸门之外**，拿真实运行产出的 JSON 报告逐项比对；同时钉住 `verify-all` 各步骤跑的脚本、以及 `facts.json` 的 id 清单。
- **为什么不能"从源码现算期望清单"**：那等于把手抄副本换成自动生成的副本——删掉一项检查，源码和现算结果**一起变小**，照样全绿。判据必须放在被评判对象之外。
- **验证**：把某条 `Add-Result` 注释掉 → `verify-gate-integrity` 必须报"这些检查项在代码里已经没有 Add-Result 了"并退出 1。

### 5.3 变异测试：证明闸门没坏

- **问题**：闸门全是检查器，但检查器自己**没有回归测试**——判据可能永远为真、永远为假、或干脆空转（有实测：删掉整个检测块而全套自检全绿）。
- **设计**：`self-test.mjs` 把库复制到临时目录 → **注入一个已知错误** → 断言检查器必须报 FAIL 且报对地方；同一用例还断言"**什么都不改时必须 PASS**"（防"狼来了"）。附加一道硬闸：**变异必须真的改到东西**——跑完指纹比对，文件没变 = 用例坏了，直接报红（专门防"等长替换"式的静默落空）。
- **落点**：57 个用例，覆盖闸门各检查项、红线、状态机、编码路径（含 936 控制台）等。
- **验证**：`node scripts\self-test.mjs`；任一用例失败即说明某道闸门形同虚设。

### 5.4 数字真值登记：`facts.json`

- **问题**：文档里的数字散落各处，改一处忘一处（历史上四次漂移）。更隐蔽的失败：**把措辞一改，声明就从检查器视野里消失**。
- **设计**（`scripts/facts.json`）：
  - 每条声明 = `claim`（带捕获组的正则）+ `anchors`（**钉到具体文件的唯一一行**，用稳定子串做见证）+ `truth`（真值**现算**：数目录、数 `Add-Result`、数用例……）；
  - 四条硬规则：每个锚点必须恰好命中一行；该行本身必须能被 claim 匹配；文件里 claim 的命中数必须等于登记的锚点数（复用已登记数字的合法重复除外）；数字必须等于真值；
  - `registeredNumbers`：文档里"数字 + 登记过的名词"的组合必须登记在册，否则拦截；中文数字与全角数字规范化后同表核对；
  - 已知局限如实登记：**未登记的新名词它看不见**（放宽会制造大量中文散文误报）——这是明确的取舍，不是遗漏。
- **验证**：`node scripts\check-consistency.mjs`；把 README 里的技能数改错一个 → 必须红。

> 完整解剖（字段定义、四条硬规则、失败模式对照、已知盲区）见 `docs/深潜-数字真值登记机制.md`。

### 5.5 报告是快照，不是状态

- **问题**：一份写着 `fail=0` 的旧报告躺在项目根，会被下一个人（或下一个 agent）当成当前结论（实测：旧报告 `fail=0` vs 真跑 `fail=2`）。
- **设计**：JSON 报告必带 `generated_at`；`verdict` 把"闸门自己坏了"（`BROKEN`）与业务失败分开；**写失败必须如实报错**（旧版目录不存在时抛错、下一行照样打印"written"，属于工具撒谎）；文档建议把报告写到项目外或临时目录。
- **落点**：`quality-gate.ps1` 的 `-Json` 分支；入口文档第五节第 5 条。

### 5.6 扫描覆盖的诚实语义

- **问题**："未发现硬编码密钥"最常见的说谎方式，是密钥恰好在**没扫到的形态里**（白名单外扩展名、当代密钥格式、被忽略的 `.env`）。
- **设计**：
  - 文件选择用**反向列**（只排除确知是二进制/资源的），不再用扩展名白名单（白名单永远列不全，实测被证伪）；
  - **被跟踪**文件命中 = 硬失败；**未跟踪 / 被忽略**文件命中 = 警告（要不要处理取决于"这个目录会不会被打包/同步/上传"，是人的判断）；**非 git 项目**回退扫描整个工作区；
  - **跳过必须报出来**：依赖目录、二进制、超过 2MB 三类各自计数，写在汇总行的范围注里；
  - **行内豁免**（`redline-allow`）：豁免必须写在命中那一行里（不是全局开关、不是整文件通配），在 diff 里看得见、可评审；**豁免条数与文件:行号会被报出来**，`-Quiet` 也报。
- **落点**：`redline-check.ps1`；重型侧同源（gitleaks 的 `.gitleaks.toml`、semgrep 的同行 `nosemgrep`，**一行标记、两个扫描器都放行**）。

### 5.7 环境隔离：把检查的写入移出被检项目

- **问题**："只读体检"并不真的只读——跑测试、跑 linter 都会写盘；对**没有 git** 的项目，这些写入**不可回滚**。
- **设计**：闸门跑测试时用**进程级**环境隔离：`-p no:cacheprovider`（关掉 pytest 自身缓存目录）+ `PYTHONPYCACHEPREFIX`（字节码重定向到系统临时目录，而不是 `PYTHONDONTWRITEBYTECODE=1` 把编译关掉——那会让测试明显变慢）；ruff 用 `--no-cache`；两类环境变量跑完立刻还原，不影响后续步骤。
- **验证**：体检前后对项目做文件指纹比对；实测曾照出 `.ruff_cache/`（42 个文件）与 `__pycache__` 残留，现均已消除。

### 5.8 平台与编码适配（Windows 实测经验工程化）

被实测踩过、并已变成检查项的细节：

- `scripts/*.ps1` 是 **UTF-8 带 BOM**；改动会吃 BOM → `verify-ps1.mjs` 强制校验并支持 `-Fix`；
- PowerShell 5.1 的 `Get-Content` 默认按 GBK 解码 UTF-8 文件 → 读文件**必须**显式 `-Encoding UTF8`（曾把一个读取方式问题误判成"写入乱码"，后经字节级反证撤回）；
- 控制台代码页 936 会让中文断言假红 → 自检开头把代码页归一到 65001、`exit` 钩子还原（曾因不还原导致同控制台下一轮自检假报 10 条失败）；
- `git ls-files` 的中文路径默认八进制转义 → `-c core.quotePath=false` + 临时文件中转 + 显式 UTF-8 解码；
- `ConvertTo-Json` 把非 ASCII 转成 `\uXXXX` → 写状态文件前还原为真字符，保证 git diff 可读。

### 5.9 状态机与单一写者

- **问题**：多 agent 协作下，状态散落在各文件里靠人拼，慢、费 token、易看错；并发写会互相踩踏。
- **设计**：`state.ps1` 是**唯一**写 `state.json` 的入口，纪律上**只有 Lead 能调用**（脚本不校验身份，靠技能正文与工单约束，但所有写入记 `updated_by` 与 `history`，可事后审计）；`validate` 按 `state.schema.json` 递归校验（含深层必填 / 枚举 / 未声明字段）。
- **一个被留档的判断实例**：给半成品项目补登记时，agent 主动拒绝把 `artifact` 标 true——理由是"**现状登记 ≠ 开工前契约**，标 true 等于假称 Builder 闸门已过"。

### 5.10 复审纪律的机械化与两档范围

- **问题**：改检查器的人看不出自己的错（实测三次检查器 bug，两次靠独立 agent、一次靠负向测试才现形）；但把每处措辞改动都要求复审，只会让规则被当成形式后忽略。
- **设计**：
  - **两档**：重装档（`scripts/`、`tests/`——改错了会静默关掉一整类保护）→ 强制独立复审；轻量档（技能正文/文档——已有机器检查）→ 不强制；
  - 复审用**固定三问**的模板（真的解决了吗 / 新引入什么 / 哪些本该被查），判据来源是改动 diff + 相关 SKILL.md + 检查器里"为什么这么判"的注释，**不给改动者的理由**；
  - 提交钩子（`core.hooksPath` 随仓库走）在 `commit` 时自动跑检查并提示复审；`--no-verify` 可绕，但**那次既无检查也无提醒、且不留痕**。
  - 一条被写进纪律的边界：`self-test` 只能证明"判据仍然成立"，**证明不了"判据选对了"**——后者没有机器能验，只能靠独立复审。

## 六、可信度证据（这套东西怎么被检验过）

### 6.1 外部验证方法

四个真实项目上的验证（一个狼人杀平台 + 另外三个性质不同的真实项目），方法固定为：

1. **判据先写死**——通过标准在看到结果**之前**登记，事后只许新增补记；
2. **独立作业**——全新会话（零上下文）在真实项目上独立跑，或独立 reviewer 只拿 diff 与"声称解决了什么"做判断；
3. **可复跑**——结论全部落到 `文件:行号 / 命令输出`，作者抽验复核；
4. **五类归因**——结果按"入口/技能/工具/项目/测试设计"五类分账，其中"项目缺陷"是主要产出。

结果摘要（详见 `docs/给外人看的验证报告.md` 与 `docs/reviews/`）：照出二十余条真实问题，绝大多数属于"项目自己的问题"；同时**也照出了工具自己的四个问题**（含 5.1 的 N1）。

### 6.2 一条缺陷线的发现与收口

"N1"（非 git 项目上"没查"被说成"查过"）从被发现到收口的全过程留档于 `docs/reviews/2026-09-13-30fd4dd.md`：

- 发现渠道：三个独立作业的新会话**如实报告"这一项我查不了"**，把工具的语义问题顶了出来；
- 修复：连续多个提交（三档结论 → 非 git 回退扫描 → 跳过必须报出 → 豁免按行 → 编码路径），每轮按纪律起独立复审，复审的"必改项"逐条处置并留变异验证（其中**有一轮复审因断网没跑成，如实记为"没跑成"，不算通过**）；
- 附带产物：一张"作者自己犯错"的清单（恒真断言、假红、把猜的当实测写进注释、控制台编码污染、没验证前提就照做……），每条都配了现在的护栏。

### 6.3 记录文化（比机制更少见的资产）

- 复审**没跑成**（断网）时，如实记成"没跑成"，不算通过；
- 结论被推翻时，**原文不删、改法留痕**（验证报告里保留着"照出的问题里没有一个是工具本身出错"这句被推翻的话及其更正）；
- 一条错误指控（"状态脚本写中文乱码"）在字节级反证后被**主动撤回**，并把成因（读取方没写 `-Encoding`）写进文档。

这三点构成一个信号：**它的输出可信度会随错误累积而上升，而不是下降。**

## 七、已知局限与设计取舍（诚实清单）

| 局限 | 说明 |
|---|---|
| 平台偏置 | 核心脚本为 Windows / PowerShell 5.1 实测；CI 模板同时给了 Windows 与 Linux 两条，**Linux 未在真机验证** |
| 工具偏置 | 机制层为某一款 AI 开发工具实测；换工具需重做配置（流程本身可移植） |
| 启发式判据 | "没跑成"的识别（如依赖扫描）依赖对错误输出措辞的匹配；换工具版本/语言可能漏判。这是**已知局限** |
| 覆盖取舍 | 被跟踪且大于 2MB 的文件不扫（可见且会报出的取舍）；红线 ③④ 的确认**无内容校验**（`-Note "x"` 也是合法确认，输出会朗读依据原文供人判断）；依赖机器人（dependabot 类）未覆盖 |
| 退出码差异 | 红线脚本保持 0/1（用户裁定），"没跑成"只体现在结论行与三档文案里，机器侧靠 stdout |
| 年轻 | 全部证据来自四轮真实项目 + 少数几轮自审，**不是被长期大规模验证的成熟产品** |
| 技能成熟度不均 | 36 个技能中，真正在真实项目上跑过的只是其中一部分 |
| 文档偏重 | 规则为防遗忘而写了很多说明文件，这是**已知成本**；已用"单入口 + 路由器 + 速查卡"缓解 |
| 数字护栏的盲区 | `facts.json` 只认登记过的名词；新的"数字 + 新名词"组合它看不见（取舍理由见 5.4） |

## 八、常见质疑与回应

> 完整问答集（含样本量、误报、维护成本、平台偏置、退出码差异等）见 `docs/技术FAQ-常见质疑与回应.md`。

| 质疑 | 回应 |
|---|---|
| "这不就是 CI + linter 吗？" | 它是**叠加层**：CI 给你绿/红，它给绿/红/**没跑成**三态语义；CI 管构建，它管"写代码前意图是否对齐、AI 作业是否留痕、结论归谁"。且它不替代 CI——`verify-clean-clone.mjs` 用本机复现 CI 的核心收益（含"忘了提交文件"这类只有 clone 才照得出的失败） |
| "自己给自己打分，可信吗？" | 判据先写死 + 独立复审 + 变异测试 + 判据钉在被评对象之外（5.2/5.3/5.10）。它明确写了自己的边界：**自检证明不了判据选对了** |
| "会不会过度工程？" | 三条硬约束在挡：G1–G4 默认关闭（"没人跑的闸门等于没有闸门"）；红线做到秒级；"加护栏前先问有没有更便宜的检查"写进纪律。**红线是及格线不是优秀线** |
| "文档里的数字可信吗？" | 数字不靠自觉：真值现算 + 锚点钉行 + 未登记数字拦截（5.4），且已知盲区如实登记 |
| "为什么不用现成框架/工具？" | 它不重复造轮子：gitleaks / semgrep / ruff / pip-audit / npm audit / pytest 都在其内直接调用；本体系补的是**结论语义、协议与留痕**——这层在现有生态里没有等价物 |

## 九、如何自行验证（本文所有声明都可复跑）

### 9.1 命令

```powershell
# 全量自检：6 个检查器（技能体检 / BOM 语法 / 内容一致性 / 闸门完整性 / 速查卡 / 自检 57 例）
node scripts\verify-all.mjs

# 检查器自检（变异测试；约一分钟）
node scripts\self-test.mjs

# 闸门完整性：钉住的期望清单 ⇄ 真跑出来的结果
node scripts\verify-gate-integrity.mjs

# 干净房间：clone 到临时目录 + 干净环境复跑（验的是已提交版本）
node scripts\verify-clean-clone.mjs

# 红线（任意项目，秒级）
powershell -NoProfile -ExecutionPolicy Bypass -File scripts\redline-check.ps1 -Project .

# 加固闸门（任意项目，含测试）
powershell -NoProfile -ExecutionPolicy Bypass -File scripts\quality-gate.ps1 -Path . -IncludeTests -Json gate-report.json
```

### 9.2 数字真值源

| 数字 | 真值来源 |
|---|---|
| 36 个技能 / 29 / 7 / 10 | 含 `SKILL.md` 的目录计数（`facts.json` → `truthSources`） |
| 18 个脚本 | 库根 `*.ps1`/`*.mjs` + `scripts/` 下全部文件（不含点文件） |
| 15 项检查 / 14 项检查 | `quality-gate.ps1` 中不同 `Add-Result` id 个数；外部由 `PINNED_GATE_IDS` 比对 |
| 4 项红线 | `redline-check.ps1` 的检查项 |
| 57 个用例 | `self-test.mjs` 的 `CASES` 条数 |
| 6 个检查器 | `verify-all.mjs` 的 `steps` 条数（`EXPECTED_STEPS` 总闸） |

### 9.3 退出码就是语义

复跑任何命令时请连同**退出码**一起读：`0` 通过、`1` 真失败、`3` **没跑成（没有结论——既不是通过，也不是失败）**。这套体系里，把 3 读成 0 就是它最想拦住的那类事故。

## 十、适用边界

**值得用**：一个人或小团队、以 AI 为主要生产力、项目有真实后果（钱 / 数据 / 对外发布）。
**不值得用**：一次性脚本、接受后果的快速原型；或者期待"一键生成产品"的用法。
**它不保证成功**：有没有人要、能不能收钱，只有市场能回答；它保证的是——**你会更早、更便宜地知道答案，而且每个结论都带着它是怎么来的。**

## 附录 A · 术语表

| 术语 | 含义（本文口径） |
|---|---|
| 技能（Skill） | 给 agent 读的工作规程，`SKILL.md`，按需自动加载或人工唤起 |
| 检查器（Checker） | 有明确判据、可独立运行、给出 PASS/FAIL/NOTRUN 结论的脚本 |
| 闸门（Gate） | 检查器的组合 + 状态机里的通过记录（`tech_redline`、`g1`–`g4`） |
| 红线（Redline） | 轻量、秒级的 4 项及格检查；商业档的前置条件 |
| 硬结构闸门 | 三图 + 接口契约的结构校验（`verify-structure.mjs`），不过不许开写 |
| NOTRUN（没跑成） | 检查**没有执行**或无法执行——第三种结论，不允许折算成通过 |
| 快照 vs 状态 | 报告（带 `generated_at`）是一次运行的结果；状态是 `state.json` |
| 基点 sha | 一次复审所针对的提交范围（`<基点>..HEAD`），留档文件按它命名 |
