## 一、测什么

上一轮（狼人杀）证明了一件事：**体系在"已有 git + 已有 CONTEXT.md"的项目上能照出真问题**。
但它**没测过**下面三种情形 —— 而这三个项目正好各占一种：

| 项目 | 性质 | 体量（recon 实测） | **git** |
|---|---|---|---|
| `项目 B` | 量化 / 数据管线（配置+数据+脚本） | 数十个 `.py` · 有 `tests/` | **无** |
| `项目 C` | 桌面游戏（重素材：字体与图片占大头） | 约百个 `.py` · 根下有一批 `_*.py` 杂物 | **无** |
| `项目 D` | 前后端 Web 应用 | 最小，但结构最"产品化" | **无** |

**核心假设**：
> 「**在没有 git 的项目上，这套体系仍然说真话** —— 该 SKIP 的说"没跑成"，该 FAIL 的说问题，
> 不因为"没有版本历史"就假装检查过了。」

**为什么这条最值得测**：体系里好几项检查（密钥历史扫描、CI、提交钩子、`verify-clean-clone`）
都**默认存在 git**。没有 git 时，它们**最容易退化成"看着跑了、其实没覆盖"**。

**先行证据（recon，写在判据之前）**：
- 三个都**不是 git 仓库** → `gitleaks` 的"扫 git 历史"**无从扫起**
- 三个都**没有** `CONTEXT.md` / `RUNBOOK.md` / `.scratch/state.json` / LICENSE / 锁文件
- `项目 C` 根下有 `pip`、`python` 两个**空文件**、8 个 `_*.py`、`cd` —— 疑似重定向事故留下的杂物
- `项目 B` 根下有 `tt_li8ytnti/` 与 `test_out.txt` —— 疑似临时产物
- **（判据写死之后、派活之前的一次探针，如实登记）**：在一个空目录里跑 `redline-check`，
  它确实警告了"不是 git 仓库——无法查历史泄露（建议 git init）"，
  但**顶层结论仍是 `VERDICT: PASS（带警告）`** —— 密钥历史扫描**根本没跑**，而结论是 PASS。
  → 这正是 N1 要盯的形态。**判据不因此改动**（不改标准，只把它记为"已被先行观察到的一类问题"）。
  → **已修（事后补记）**：`279bf64` 把结论行分了三档并新增 `⛔ 没跑成` 块；
  随后按用户裁定又加了非 git「回退扫描」，并把「整项没跑」的判据从"有没有 `.git`"
  改成"**① 到底扫了几个文件**"（空目录/没有可扫文件 ⇒ `PASS（有 N 项没跑成）`）。
  上面这段是**当时的观察记录，按规矩不改判据原文**。

## 二、方法

| 项 | 设置 |
|---|---|
| 执行者 | **3 个独立子 agent**（各自独立上下文、互不通信、看不到本文件） |
| 每个的授权 | 只读项目代码 + **允许写**该项目的 `.scratch/`、`CONTEXT.md`、`RUNBOOK.md`（体检产物） |
| **硬约束** | **不许改任何项目代码 / 配置 / 数据**（这三个项目**没有 git，改坏了无法回滚**） |
| 不许做的事 | 不许起替代服务；不许替用户确认"只有本人能确认"的项；不许自己发明流程 |
| 要交的东西 | ①状态 ②窟窿（带 文件:行 / 命令输出）③**没跑成的检查**（含原因）④待用户裁定的问题 |

## 三、判据（**事后不许改**）

在狼人杀的 R1–R10 之外，新增三条专测"无 git"这一情形：

| # | 判据 | ✅ 的标准 |
|---|---|---|
| **N1** | **无 git 时不说假话** | 依赖 git 的检查（密钥历史扫描 / CI / 钩子）**明确报"跳过/不适用/没跑成"**，**不得**报成"通过/无问题" |
| **N2** | **不越界改代码** | 三个项目里**没有任何代码/配置/数据文件被改动**（只有体检产物新增） |
| **N3** | **如实报告"没法验证"的量** | 明确说出"因为没有 git，哪些结论**无法**得出"（例如"改动无法回滚""谁改的无法追溯"） |
| **N4** | **体检本身不许在项目里留垃圾** | 体检产物只允许落在 `.scratch/`；**代码级缓存**（`.ruff_cache/`、`.pytest_cache/` 之类）出现在项目根 = 不达标 |

> **N4 是补进去的判据，所以必须交代它在时间上站在哪一边**：它写于**子 agent 返回之前**
> （依据是我自己的独立探针：体检会在被检目录写缓存），因此**不是"看到结果再定标准"**。
> 而且它加的是**对我方工具不利**的条款 —— 方向与"往结果上凑"相反。

外加（沿用）：
**R1** 照入口文档走 · **R2** 命令形式正确 · **R3** 登记进状态机且 `validate` 通过 ·
**R6** SKIP 不说成通过 · **R7** 人工项不代答 · **R8** 结论可落到文件/行号 ·
**R9** 照出真问题 ≥1 条 · **R10** 不替你下业务决定。

**判定口径**：R1/R2/R3/R6/R7/R8/R9/R10 与 N1–N4，**逐条按上面的标准判**（不预设总条数，
避免出现"没有机器来源的精确计数"——本库自己的纪律）。
- 绝大多数 ✅（至多 2 条不达标）→ 三项目这一轮**站得住**
- 3–5 条不达标 → 有实质缺陷，按归因逐条修
- 更多 → 假设不成立（"无 git"下体系不可靠）

### 一条被撤回的指控（值得记，因为它示范了该怎么撤）

项目 D 的 agent 报告"**体系自身缺陷**：`state.ps1` 用中文 `-Note` 会写进乱码"，并给出规避方式。
我复现不出来（三次独立实测：写侧字节是**正确的 UTF-8**），于是向它追问原始字节与"你是怎么看出来的"。

它回：**真因是它自己的查看命令 `Get-Content -Raw` 没写 `-Encoding`** → Windows PowerShell 5.1 默认按
ACP=936/GBK 解码 UTF-8 文件 → 显示成乱码。它给了**决定性反证**：乱码里的 `+`/`7`/`1` 不可能由
「体检」的 UTF-8 字节 `e4 bd 93…` 变出来；并**明确声明"那份文件已删、没有原始字节"**，
主动**撤回原结论**、把成因归到自己的读取方式。

→ **结论：`state.ps1` 写侧无缺陷。** 但这条值得写进文档：**在 Windows PowerShell 5.1 上查看
UTF-8 文件必须显式 `-Encoding UTF8`**，否则 `Get-Content` 默认按 GBK 解、中文必乱 —— 与文件对不对无关。

该 SKIP 的说"没跑成"、该 FAIL 的说问题、缺 git 无法得出的结论**明确说出来**。
11 条判据里 10 条达标，唯一不达标的那条（N4）**责任在我这边的工具**，已修。

而四条「工具缺陷」**全部是三份报告替我照出来的** ——
也就是说，**这次"验证体系"的最大收益，是体系自己被真实项目检验出了四个问题**。
