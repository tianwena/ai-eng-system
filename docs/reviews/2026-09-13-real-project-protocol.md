## 一、这次要验证什么（与上次冷启动的区别）

上次（2026-09-12）测的是：**"零上下文的 agent 只靠入口文档，能不能走对流程"** —— 用的是玩具项目。
这次测的是**另一件事**：

> 「**这套体系在一个真实的、做到一半的项目上，能不能照出真问题。**」

被测项目：`<项目 A 根>`（一个"AI 对局平台"）。
**它是真实项目**：约 20 个 `.py`、有 `tests/`（数个测试文件）、是 git 仓库（有真实提交历史）。
它**已经做过一次冷启动的场景 B**（"能不能给真人用"），所以 `CONTEXT.md` 已存在。

**核心假设（要证伪的那句）**：
> 「体系的价值不在"玩具项目上跑通"，而在**真实项目上能照出人看不见的窟窿**。」

**已知的先行证据（recon，写在判据之前）**：
- `CONTEXT.md` 34 KB，**过硬结构闸门**（9 实体 / 9 状态 / 14 迁移 / 23 端点块，无占位符）
- **没有** `.scratch/state.json`（从没被正式登记进状态机）
- 项目根躺着一份 **`gate-report.json`，没有 `generated_at`/`verdict`**（修"旧报告假绿"之前的版本）
  → 这是"旧报告会被当成当前结论"的活样本

## 四、失败归因分类（**不许笼统说"没做好"**）

| 类别 | 表现 | 归谁 |
|---|---|---|
| **入口缺陷** | 找不到该跑哪条命令 / 漏了某道闸门 | 修入口文档 |
| **技能缺陷** | 打开的 SKILL.md 没写清 / 写错了 | 修对应 SKILL.md |
| **工具缺陷** | 检查器本身报错、误报、或把"没跑成"说成"通过" | 修 `scripts/`（**改动要独立复审**） |
| **项目缺陷** | 项目**自己的**问题（密钥、依赖、配置、文档分叉） | 记进项目的待办，**不算体系的锅** |
| **测试设计缺陷** | prompt 让它误解了任务 | 记下来，下次改测试 |

> **注意**：这次**项目缺陷**是**好结果**（R9 要的就是它）——体系的价值正是照出这些。
